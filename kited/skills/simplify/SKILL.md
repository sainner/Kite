# simplify

流程：四个只读审查子代理并行找问题，回报齐了由你去重，再直接改。

这一次要提高的是改动代码的质量，不是找 bug。从复用、简化、效率、层级四个角度审查，再把找到的问题改掉。不找正确性 bug，那是 code-review 的事。

用户在 `/simplify` 后面写了审查目标时，审查那个目标。

## 第 0 步：取得 diff

用 shell 跑 `git diff @{upstream}...HEAD` 拿到要审查的统一 diff；没有上游时改用 `git diff main...HEAD` 或 `git diff HEAD~1`。有没提交的改动，或这个范围的 diff 是空的，再跑 `git diff HEAD`，把工作区里的改动也算进来，因为审查常在提交之前做。用户给了 PR 号、分支名或文件路径时，改审那个目标。这份 diff 就是审查范围。

## 第 1 步：四个子代理并行审查

在同一条回复里调四次 agent_start，开四个只读审查子代理（role 用 `kite.review`），每个负责下面的一个角度，四个同时跑。子代理和你在同一个工作区，看到的文件和你一样。每个 prompt 都要自成一体，写清：

- 审查范围，以及第 0 步实际跑的那几条取 diff 命令，让它自己跑；不要把整份 diff 贴进 prompt；
- 它负责的那个角度，原样抄下面对应的一节；
- 只找问题、不改代码；
- 最后一条回复只写问题清单，每条一行：`路径:行号 — 一句话说明问题；具体代价（什么重复了、白费了或更难维护了）`，没有问题就写「无」。回报只带最后一条回复的末尾约 3000 字，清单写短。

开完就结束这一回合。

### 复用

找出新代码里重新实现了代码库已有功能的地方：用 rg 搜共享模块、工具模块和改动旁边的文件，指出应该改调的那个现成函数。

### 简化

找出 diff 加进来的不必要的复杂度：多余的或能推导出来的状态、稍作改动的复制粘贴、过深的嵌套、留下的死代码。指出能做同样事情的更简单的写法。

### 效率

找出 diff 带来的白费功夫：重复计算或重复 I/O、本可同时做却依次执行的独立操作、加到启动或热路径上的阻塞工作。还要找用闭包或捕获的环境构造的长寿对象：对象活多久，整个外层作用域就跟着活多久，外层持有大的值时就是内存泄漏；宜改用只拷贝所需字段的类或结构体。指出更省的做法。

### 层级

检查每处改动是否在合适的深度修了根因，而不是给症状贴一块脆弱的补丁。在共享的基础设施上叠加特例，说明修得不够深：宁可对底层机制做更简单、更通用的修改，也不要加特例，并指出那处修改。

## 第 2 步：收齐回报后改

子代理做完时，宿主把它最后的回复作为一条输入投给你，每来一份你会开始一个新回合。没收齐四份之前只记下结果、不改代码，一句话说明还在等哪几个角度，然后结束回合。某个子代理失败或被停下时，那个角度由你自己审。

四份都到了以后，把指向同一行或同一机制的问题合并，剩下的逐条直接改。会改变预期行为的、要改到审查范围之外很远的地方的、你判断是误报的，跳过并记一句原因，不争辩。最后简短总结改了什么、跳过了什么；什么都不用改时说明代码已经干净。

## 没有 agent_start 时

工具里没有 agent_start，或者建不了 `kite.review` 的代理时，在当前上下文里按上面四个角度依次自己审一遍，不因为不能并行就跳过某个角度。每个角度记下问题的文件、行号、一句话说明和具体代价，然后照第 2 步合并、修改、总结。总结里写明这次是在当前对话里单遍审查的，没有开四个子代理，免得读的人误会实际跑了什么。
