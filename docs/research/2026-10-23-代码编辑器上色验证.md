# 代码编辑器上色验证（2026-10-23）

历史验证材料，保留当时的条件与结果，不代表以后的系统版本或编辑器实现仍然如此。探针与复现方法见 [spikes/code-editor](../../spikes/code-editor/README.md)。

## 问题

浏览窗口要能编辑代码文件，选型是系统文本视图（Mac 的 NSTextView、iPhone 的 UITextView，都用 TextKit 2）加 tree-sitter 语法高亮，上色这一层自己写（ChimeHQ/Neon 的作者写明没能在 TextKit 2 上做到打字时不闪）。动手做编辑器之前要回答：

- 打字时颜色跟不跟得上，画出来的那一刻颜色对不对；
- 打了 `/*`、`"""` 这类让后面一大片变色的字，屏幕跟不跟着变；
- 拼音还没上屏时上色会不会打断输入法；
- 普通文件和 2 MB 的文件上打开、打字、滚动各多久。

## 条件

- Mac：Mac14,2，macOS 27.2（26B118），Xcode 27.1（27A9275）。iPhone 17，iOS 27.2（24B5099f）。
- tree-sitter 0.25.10，Swift 绑定 tree-sitter/swift-tree-sitter cbe31cb，Swift 语法 alex-pinkus/tree-sitter-swift 82bb3a5。
- 测试文本由探针生成：一段有代表性的 Swift 反复接起来。普通约 1000 行（34,630 个 UTF-16 字），大文件约 2 MB（1,856,876 字、53,953 行）。只测了 Swift 一种语言。
- 下面的数字除注明的以外都来自开了优化的 Debug 版（`-O`、`-Os`、整模块）；不开优化时 tree-sitter 的 C 代码慢几倍。

## 方法

探针编进 App，带 `-editorProbe` 启动时只显示编辑器，按顺序做：首屏、跳到中间、逐字打一行（含中文和引号）、在行首打 `/*` 再删掉、输入法、打 `"""` 加换行再删掉、从头滚到尾 21 步。字由文本视图的输入接口送进去（Mac `insertText(_:replacementRange:)`，iOS `insertText`），两字之间等 60 ms；输入法用 `setMarkedText` 模拟拼音、再用 `insertText` 上屏，不是真键盘。

- 颜色对不对：换掉排版管理器的代理，各段换成核对用的片段。片段每次画的时候，拿语法树按当时的文字算一遍各字的颜色，和要画的颜色逐字比（空白不算）。每一步结束后再把屏幕上的各段不等画核对一次（事后核对），那时还错的是真错，只在画的那一刻错的是闪一帧。比的是要画的颜色数据，不是截图像素。
- 系统重不重画：数改动之后被画的段数。
- 计时：「每个字从按下到处理完」是送进一个字的同步耗时，含解析和文本视图自己的处理，不含之后的绘制。

## 结果

### 走不通的做法

- **用显示颜色（rendering attributes）上色。** TextKit 2 的 `renderingAttributesValidator` 只在一段第一次排的时候来问颜色，排好的段落再改、再露出来都不再问。标成颜色失效（`invalidateRenderingAttributes`）以后，没有再来问，画出来是没颜色；连排版一起作废也没用。改动途中 TextKit 会来问颜色，但它随后才按这次改动挪动已有的显示颜色，于是错位（`import` 的颜色落在第 1～7 个字）或留下一个字的空洞（输入法上屏后下一行中间缺一个字的颜色）。最关键的是：直接给画好的段落改显示颜色，之后一段都没重画，把整个文本视图标成需要重画也不重画；数据改对了，屏幕还是旧的。
- **不折行。** 不折行时 TextKit 要排完全文才知道最宽的一行：大文件打开到第一次显示 11.3 秒（未优化的 Debug 版），5.4 万段全排了一遍。改成折行以后只排屏幕附近的 169 段。

### 走通的做法

内容存储生成段落时按语法树加上字色（`NSTextContentStorageDelegate` 的 `textParagraphWith`），文字存储里不放颜色；打字时在文字存储处理改动的回调里同步增量解析，改到的段落随即重新生成；语法树说别处颜色也变了的，在这一轮事件末尾、画出来之前对那些范围发一次只改属性的编辑（`edited(.editedAttributes)`），让内容存储重新生成。折行。

| | Mac 普通 | Mac 2 MB | iPhone 普通 | iPhone 2 MB |
|---|---|---|---|---|
| 整份解析 | 7 ms | 338 ms | 8 ms | 247 ms |
| 打开到第一次显示（不含解析） | 209 ms | 812 ms | 129 ms | 127 ms |
| 每打一个字，平均 / 中位 / 最大 | 3.0 / 2.9 / 8.2 ms | 9.1 / 8.7 / 22 ms | 7.0 / 5.2 / 16 ms | 15～26 / 13～23 / 28～109 ms |
| 滚动每步（排版加画） | 8.6 ms | 12.7 ms | 0.3 ms | 0.3 ms |
| 画的那一刻颜色不对 | 0 | 0 | 2 段（见下） | 0 |

- Mac 的打开时间是探针为了换成核对用的片段整份重设一次以后量的；iPhone 的两行打字数字取自只计时的跑法（不换 UITextView 自己的排版代理 `_UITextKit2LayoutController`）。换了代理时 iPhone 普通文件每字平均 13.5 ms、大文件 49 ms。
- iPhone 大文件只计时跑了三次，每字平均 15、26、26 ms，有一次单个字 818 ms；其中编辑器自己（增量解析、维护行号）每字平均 7.2 ms 和 14.1 ms（两次），其余是 UITextView 自己的处理。
- 打 `/*`、`"""`：两端事后核对都对；`"""` 之后 Mac 普通文件重画 43 段、大文件 20 段，iPhone 13 段，说明重新生成的段落会重画。
- 输入法：两端拼音没上屏时标记文字一直在，再打两个字母仍在，上屏后字对、颜色对。
- iPhone 普通文件打字时画的那一刻对不上的 2 段，画的是改动之前的旧段落（旧段落的字色对当时的文字是对的，探针拿新的语法树比），事后核对为 0。
- 跳到大文件中间（`scrollRangeToVisible`）时 UITextView 把前面的段落都生成了一遍：iPhone 生成约 3 万段、710～750 ms。

## 结论与适用范围

- 系统文本视图加 tree-sitter 可行，上色走「生成段落时加字色」，不用显示颜色；编辑器折行。
- 普通大小的代码文件两端打字都在一帧以内。2 MB 的文件在 iPhone 上打字偏慢、偶有长卡顿，一下跳到中间要 0.7 秒；大文件的解析放后台、跳转不靠 `scrollRangeToVisible` 是以后的优化方向，没有验证。
- 没覆盖：真键盘和真输入法、Swift 以外的语言、真实项目里的文件、iPad、截图像素级的核对、Release 构建。
