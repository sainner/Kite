# Tailscale 官方组网实测（2026-10-15）

历史验证材料，保留当时的条件与结果，不代表各家服务和网络一直如此。脚本与复现方法见 [spikes/tailscale-official](../../spikes/tailscale-official/README.md) 与 [spikes/apple-serverless](../../spikes/apple-serverless/README.md)。

## 问题

[分布式架构](../分布式架构.md) 把组网与身份交给 Tailscale 官方服务，推送与执行权见证交给 CloudKit。要回答：官方登录在 Mac 的 tsnet 与 iPhone 内嵌的 TailscaleKit 上能否走通；「同一 Tailscale 用户」的判定能否沿用；直连与走中继时的延迟；CloudKit 能否用现有的签名团队开通。

## 条件

- 一台 Mac mini，家庭宽带，只用 IPv4；所在网络会在本地接管 TCP 连接，TCP 建连耗时不能当延迟用。一台 iPhone 17，先在同一 Wi-Fi 下，再切到蜂窝网络（只用 IPv4）。
- Mac 端是 tsnet（tailscale.com v1.104.0）起的独立节点，ControlURL 留空即官方服务；iPhone 端是内嵌 TailscaleKit（libtailscale 59d4bb8）的实验 App。新建的 tailnet 用 Apple 登录（隐藏邮件地址），与现有的 Headscale 网络分开。
- 延迟取 Mac 每 15 秒一次的 disco 探测，HTTP 耗时由 iPhone 连访 Mac 节点的 80 端口读出。

## 结果

| 项目 | 结果 |
|---|---|
| Mac 登录 | 启动后 2～7 秒拿到登录地址；用户确认后 1 秒内上线 |
| 首次登录体验 | 浏览器里先后遇到两次错误页：GitHub 登录返回 403（原因未查明）；Apple 登录提示已登着另一个 tailnet、目标 tailnet 不存在，重试后才新建。失败过的登录地址不再生效，要重启节点重新取 |
| iPhone 登录 | 内嵌 TailscaleKit 的网页登录可用：App 打开登录地址，登录后上线；重启 App 不用再登录，约 3 秒上线 |
| 身份 | 隐藏邮件地址登录时，tailnet 名与用户名都是转发邮箱。WhoIs 给出用户 ID、登录名与节点标签，iPhone 来访被判为同一用户、无标签，kite-net 现有的判定可以直接用 |
| Mac 的 netcheck | UDP 可用，NAT 映射不随目标变化；最近的官方中继是东京约 97 毫秒、香港约 148 毫秒；到自建香港中继的 STUN（UDP 3478）不通 |
| 同一 Wi-Fi | 局域网直连，往返 7～8 毫秒 |
| iPhone 蜂窝到 Mac 家宽 | 打不了洞，经东京官方中继，往返 376～406 毫秒；一次 HTTP 请求约 500 毫秒。现有自建网络在同样条件下也是经香港中继，那边的延迟没有测 |
| iOS 的 ATS | 明文 HTTP 访问组网地址要在 Info.plist 里放开 ATS，Kite App 已经放开 |
| CloudKit | 签名团队是个人（免费）开发者团队，Xcode 拒绝 iCloud 能力；推送同样需要付费团队。CloudKit 的推送与租约实验没有做 |

## 经路由器认证通道的直连

这台 Mac 所在的网络不允许宿主直接用固定端口出网。网络管理员给出的做法是：Kite 的组网模块经一条只跨局域网的 WireGuard 通道连到路由器，路由器验证身份后给这条通道原生出站；STUN、探测与点对点 UDP 都走这条通道，认证失败就不发，不退回未认证的直连。实现见 [spikes/tailscale-official](../../spikes/tailscale-official/README.md)：

- 给 tailscale 打了一个小补丁，让 tsnet 可以注入自定义 UDP 监听，并在注入时关掉端口映射。
- 进程内用 wireguard-go 加 gvisor 网络栈建通道，系统里不出现网卡。
- 通道私钥只存在登录钥匙串，由实验程序创建；临时签名的程序每次重新编译，钥匙串都会再问一次。

| 项目 | 结果 |
|---|---|
| 通道握手 | 路由器侧要用会自动学习客户端端点的标准 WireGuard 服务端，换掉之后才握手成功；之后约两分钟重握手一次，一直保持 |
| 经通道的 IPv4 | STUN 得到一致的公网映射（端口被改写）。手机在蜂窝网络下 IPv4 是对称型 NAT，每个目标映射不同端口，与路由器只放行发过包的对象的 NAT 打不通，仍经中继，往返 311～1804 毫秒 |
| 经通道的 IPv6 | 路由器给通道分了全局 IPv6。宿主网卡没有 IPv6 时，magicsock 不做 IPv6 的 STUN，要把这个地址报成静态端点。之后与手机的原生 IPv6 直连，往返 76～290 毫秒，连续几轮稳定；一次 HTTP 请求约 80 毫秒（经中继时约 500 毫秒） |
| 状态里的端点 | 状态只带本机的端点，对端端点要从 WhoIs 的节点信息里取 |

## 结论与限制

- 官方登录与身份判定可以替代 Headscale 与 Kite 账号；首次登录会遇到上游的错误页，引导要专门设计。
- 蜂窝网络到家庭宽带在这组条件下仍走境外中继，往返约 0.4 秒，可用但有可感知的停顿；同步要按「可能一直走中继」设计。
- CloudKit 推送与执行权见证要先加入付费的 Apple Developer Program。
- 受管网络里，经路由器认证通道加全局 IPv6，可以和蜂窝网络下的手机直连；手机侧的 IPv4 是对称型 NAT，只靠 IPv4 打不通。
- 只测了一组网络条件和一个时段；协调服务与登录在中国大陆的长期可达性、其他网络下的直连比例、App Store 审核都没有验证。
