# Claude 会话重组实验（2026-10-09）

历史验证材料，保留当时的条件与结果，不代表上游格式永远不变。现行做法见 [会话后端](../kited.md#会话后端与宿主边界)，脚本见 [spikes/compaction](../../spikes/compaction/README.md)。

## 问题

harness 压缩过上下文后切换到 Claude，能否只追加、不改写 Claude 会话文件，就让 Claude 从压缩后的上下文接续；原有条目能否继续用于显示。

## 条件

Claude Agent SDK 0.3.280 自带的 Claude Code 2.1.280，kited 当时的 Claude 配置，本机假 Anthropic 端点，隔离配置目录。原生跑三轮（第一轮含 thinking 与并行工具调用），之后在文件末尾追加：压缩分界（`system/compact_boundary`，`parentUuid` 为空，`logicalParentUuid` 指向原叶子）、第一轮条目的拷贝、一条摘要消息、第三轮条目的拷贝，再恢复会话发第四轮。

## 结果

| 验证 | 结果 |
|---|---|
| 分界的 `type`、`subtype` 排在行内较后位置 | CLI 认不出分界，分界之前的条目仍被加载 |
| 分界字段按原生顺序排列（`parentUuid`、`logicalParentUuid`、`isSidechain`、`type`、`subtype` 在前） | CLI 丢弃分界之前的条目，只加载分界之后的链 |
| 拷贝的助手条目沿用原 `message.id` | 同 id 的原条目内容被合并进来，请求中内容重复 |
| 拷贝换用新的 `message.id` | 请求只含重组后的历史；第一轮与原生请求逐字节一致（含 thinking 签名），system 与工具声明不变 |
| 不追加新的 `last-prompt` | 恢复后的新输入接在原叶子之后，与重组的链混在一起 |
| 追加 `last-prompt` 指向重组后的叶子 | 新输入接在重组的链之后 |
| SDK `getSessionMessages` 读取重组后的会话 | 只返回分界之后的链，读不到分界之前的原条目 |
| 在原生会话上 `resume` + `forkSession` + `persistSession: false` 发摘要指令（`summary.ts`） | 正常完成；messages 前缀与 system 与正常续接相同，会话目录不多出文件，原会话文件不变。实验未挂 Kite 工具服务，工具声明因此不同，要命中同一缓存须挂上同样的工具 |

## mod 接管压缩

同样条件下，用 mod 的 `session.compact` hook 接管压缩（`spikes/compaction/mod.ts`）：去掉 `DISABLE_COMPACT`，打开 `autoCompactEnabled`，阈值设为 20 万窗口的 50%；第三轮的工具调用回复报出 18 万输入用量。

| 验证 | 结果 |
|---|---|
| 回合中途是否触发 | 工具结果之后、同一回合下一次请求之前触发，`trigger` 为 `auto` |
| hook 中调用 `$.model.fork` | 正常返回；分叉请求带同样的工具声明 |
| hook 交回带 `handle` 的消息与自建的摘要消息 | 本进程内下一次请求：保留的第一轮与原请求逐字节一致，第三轮的 thinking、工具调用与结果都在，摘要替换第二轮；system 与工具声明不变 |
| 会话文件 | 写入原生压缩分界（`compactMetadata` 含 trigger、preTokens、postTokens，无保留段），随后把交回的消息全部重写一份，带 `handle` 的拷贝沿用原 `message.id` |
| 之后恢复会话 | 第一轮与第三轮的助手内容重复：同 `message.id` 的分界前原条目被合并进来，与会话重组实验中观察到的现象相同 |
| SDK `getSessionMessages` | 同样出现重复的助手消息 |
| hook 只交回摘要与第三轮（摘要在前、只保留末尾一段） | 分界记下保留消息的 uuid 列表（`preservedMessages`），原条目接回、不再重写，恢复与显示都不重复；但引擎把摘要改写成自己的续接消息（英文开头、原始记录路径、要求直接继续），正文被换成保留助手消息里的一句，第三轮的用户消息也不见了 |
| 回合结束后追加一次重组：拷贝当前主链、助手消息换新 `message.id`、更新 last-prompt（`cleanup.ts`） | 恢复后不再重复，压缩后的上下文完整接续 |

### 重复运行与宿主通道

同一份 `mod.ts` 之后多次重跑，结果不稳定：有的运行压缩发生在工具结果写入之前（hook 收到 5 条消息），hook 分叉后引擎仍采用自己的「只保留末尾一段」压缩；有的运行 hook 没有被调用，压缩由引擎完成。未找到决定差异的条件，CLI 没有输出相关日志。

宿主通道（`channel.ts`）：进程内另挂的 MCP 服务在 `bypassPermissions` 下用 `disallowedTools` 去不掉，模型请求里仍能看到；SDK 流式输入模式下没有观察到 `turn.complete` hook 被调用；在 `session.compact` 中调用 `$.mcp.call` 的几次运行恰好都遇到上述 hook 不生效，未能确认通道是否可用。

## 结论与限制

- 只追加即可替换 Claude 的模型上下文：分界加完整的新历史，再更新 `last-prompt`。合成的助手消息须用新的 `message.id`，分界的字段顺序须与原生一致。
- 显示不能直接用 SDK 读到的链；读取时须去掉重组写入的条目，把之后的新条目接回重组前的叶子。
- 可以在不留痕迹的分叉上让 Claude 基于完整原生上下文生成摘要。
- mod 在部分运行中能在回合中途接管压缩并决定压缩后的内容，但重复运行时引擎是否采用 hook 的结果不稳定，原因未查明。另外 CLI 2.1.280 把保留的消息以相同 `message.id` 重写一份，此后任何一次恢复会话都会出现重复内容，恢复前用新 `message.id` 重组一次可以消除重复。只保留末尾一段时引擎改用原生接回、没有重复，但会改写摘要并丢掉保留段开头的用户消息，不能直接用。
- 实验只覆盖假端点上的请求形态，未用真实 API 验证；会话文件属于 CLI 内部格式，升级 SDK 须重跑。
