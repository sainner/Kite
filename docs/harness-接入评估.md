# 自研 harness 接入评估（历史）

本文保留 2026-09-26 初次评估的理由与取舍，不描述当前能力，也不再维护实施进度。运行与当前限制见 [工作机说明](kited.md)，执行契约见 [harness 主循环](harness-主循环.md)，前端支持范围见 [会话显示协议](会话显示协议.md)。

## 当时的问题

Claude Code 账号受阻后，用户决定提前自研 harness，首个模型入口使用 ChatGPT 订阅。原任务书“第一阶段只接 Claude Code”的安排被覆盖；2026-10-06 又决定按精简基线重新接入 Claude Code，最新方向见 [项目记忆](../.kite/memory/harness-direction.md)。

Kite 已有项目登记、工作树、快照、采纳和检查执行骨架。接入目标是复用工作台，增加由 Kite 管理的模型循环、工具执行、持久记录和真实对话链路，而非更换旧 Runner 的模型 URL。

## 依赖分析与复用取舍

| 当时的能力 | 评估结论 |
|---|---|
| 项目登记、工作树、快照与采纳 | 复用 Git 语义；将工具批次与回合结束接到快照边界 |
| 检查和子进程停止 | 复用执行、日志、超时与进程组处理；检查能力与 SDK 工具包装分开 |
| Claude SDK Runner | 它控制完整 agent，不是可换 URL 的模型客户端；保留为独立 runtime |
| 会话登记与记录 | SQLite 管理领域对象；自研记录必须保留模型续接所需原生字段 |
| HTTP 与 SSE | 需要统一 Kite 显示语义、历史读取和重连，不直接暴露 SDK 消息 |
| App 展示模型 | 不能把已有样本类型当成网络协议，必须明确身份、投递确认和控制状态 |
| 测试夹具 | Git 测试继续有用；新循环增加可控模型流，不依赖真实订阅运行自动测试 |

## 订阅与适配边界

当时参考 [Codex 认证文档](https://learn.chatgpt.com/docs/auth)、[App Server](https://learn.chatgpt.com/docs/app-server#auth-endpoints) 和 Codex `rust-v0.157.0` 源码评估认证与请求。订阅登录和按量 API key 是不同入口，不能替用户变更选型。

公开认证资料没有单独给出任意自研 harness 的完整订阅协议，因此协议适配还需结合源码与真实返回验证。模型循环由 Kite 执行；官方登录工具只用于每台工作机独立授权，不能把调用 Codex CLI 当作完成自研。

当前登录步骤、凭据处理与限制只在 [工作机终端说明](kited.md#终端试用) 维护。历史机器上的 CLI 安装故障和记忆迁移步骤已不作为接入前提。

## 保留下来的验收依据

原推进顺序是先验证订阅文本、工具与续接，再完成最小循环和记录，随后接工作区与 App。它是当时的建议，不是当前待办。

两个恢复场景仍决定实现边界：请求中断不能留下无法配对的工具调用；工具已造成副作用但尚未保存结果时，恢复不能自动重放。模型续接必须使用原生记录，包括 opaque 字段，不能只存可见文字。

输入先可靠保存再确认，显示历史与执行恢复分别投影。会话记录放在项目外，项目指引与长期知识留在项目内。skill、长上下文、后台任务等能力应按实际需求逐项接入，不以一次文本实验代表完整可日用验证。
