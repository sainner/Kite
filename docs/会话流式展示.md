# 会话流式展示设计

状态：已实施。字段与重连约定以《会话显示协议》为准；下文保留设计依据和验收范围。

目标：正文、思考摘要、工具参数和工具执行输出都能随内容到达而更新；同一条记录从开始到结束保持身份，前端支持持续渲染 Markdown 和工具行。

## 实施前的链路与缺口

| 内容 | 当前行为 | 本次需要补齐 |
| --- | --- | --- |
| 正文 | 上游文本 delta 经 SSE 到达；投影累积后发送整条 partial 记录 | 字段增量传输，App 保留生成状态，只更新受影响的消息 |
| 思考摘要 | 完整 model.item 到达后才显示 | 开始、摘要增量、结束；消息流只显示当前正在生成的思考行 |
| 工具参数 | 完整 model.item 落盘后出现工具调用 | 生成参数时就建立工具行，逐步更新，完整后进入调度 |
| 工具执行 | 已有 tool.started / tool.finished；显示投影没有使用 started | 区分等待执行和执行中，完成后显示真实结果 |
| shell 输出 | 管道持续读取并写日志，但只在结束时返回 ToolResult | 把执行中的输出转发到工具详情，完成时以最终结果收口 |

正文当前不是按整段缓冲，也不是按字拆分：适配器按上游文本 chunk 处理。工具调度已经可以在某个完整调用落盘后开始，不需要等待整次模型请求结束。保持这一行为。

## 两层协议与存储

模型适配器负责把上游转换成 Kite 的模型内容事件；显示投影再转换成 App 的会话事件。App 不认识 Responses 事件名。SSE、现有历史快照和 journal 继续使用，不新增传输通道。

模型侧增加三个语义：条目开始、字段追加、字段定稿。既有完整条目和请求结束事件继续承担最终校正与落盘。文本分段保留 part index，避免同一条目中多段正文或摘要相互覆盖。

上游接入点：

| Responses 事件 | Kite 用途 |
| --- | --- |
| output_item.added | 建立正文、思考或工具调用条目，保存条目顺序与身份 |
| output_text.delta / done | 更新正文内容分段；done 校正该分段 |
| reasoning_summary_part.added、reasoning_summary_text.delta / done | 更新摘要分段；摘要结束不等于整个请求结束 |
| function_call_arguments.delta / done | 更新工具参数原文；done 校正参数 |
| output_item.done | 以完整条目校正草稿，结束该条目的生成 |
| completed / failed / incomplete | 请求收口；未完成草稿不标为成功 |

以上事件由官方 [Responses 流式事件参考](https://developers.openai.com/api/reference/resources/responses/streaming-events) 和 [工具调用指南](https://developers.openai.com/api/docs/guides/function-calling) 定义。Kite 使用 ChatGPT 订阅入口，实施时仍需验证该入口实际发送的事件；不能把公开 API 文档当作该入口逐项支持的证明。只返回完整条目的情况继续支持，不虚构中间过程。

完整原生条目继续进入 journal 和后续模型上下文，包括恢复所需的 opaque 字段。显示增量不逐 chunk fsync，也不把不完整参数放进模型历史。shell 完整输出继续写原日志。

## App 显示事件

保留 `thread.record`，负责建立条目、阶段变化、完整内容校正。增加一个 `thread.record.delta`，只携带记录 id、目标字段/分段和新增文字。阶段变化不混在文字 delta 中。

| 事件 | 作用 |
| --- | --- |
| thread.history | 完整快照，含当前仍在生成的内容、工具执行阶段和受限输出 |
| thread.record | 同 id 原位建立或替换；用于开始、阶段变化和结束校正 |
| thread.record.delta | 追加到指定记录的正文、摘要、参数原文或执行输出 |
| thread.state | 沿用会话四个主状态和上一轮结果 |

同一连接按 SSE 顺序应用事件。重连先以历史快照替换副本，再接新事件；废弃旧连接尚未处理的事件。delta 找不到对应记录时重新同步，不猜测归属。继续使用现有 cursor，不增加事件重放服务。

条目身份从第一次出现起固定：正文、思考使用 requestId + itemId；工具行使用 callId，批次使用 requestId。上游 itemId 与 callId 的映射只由适配器/投影维护。字段定稿和完整条目都是替换校正，不能把全文再追加一次。

生成完成、工具执行完成、回合完成是三个不同边界。正文/思考记录需要显式的生成状态：生成中、已完成、未完成；工具调用需要下节中的执行阶段。现有 partial 布尔值不能继续作为全部含义。具体类型采用区分联合，避免无意义的字段组合。

服务仍在运行时，断线重连包含内存中的草稿。daemon 重启后，只恢复已持久化的完整条目和执行事实；未落盘的生成草稿可能消失，不把它们伪装成成功结果。进程是否仍在运行交给既有 recovery 机制判断。

## 工具行的阶段

正常路径：生成参数 → 等待执行 → 执行中 → 结果。等待可能很短，但必须与真正开始执行区分；同一模型回复中的调用仍按现有并发/排他规则调度。

| 阶段 | 工具行 | 展开内容 |
| --- | --- | --- |
| 生成参数 | 已知工具名；摘要在可提取时更新；末端显示生成中 | 不完整参数的原始文本 |
| 等待执行 | 完整参数摘要；末端显示等待中 | 完整原始参数 |
| 执行中 | 保留摘要；末端显示执行中/耗时 | 原始参数与已收到的输出 |
| 结果 | 沿用实际成功、错误、未执行或结果未知 | 最终原始参数与结果 |

参数未完成时不能用默认值构造可执行调用。参数完整、校验通过并落盘后才能执行；显示解析与执行校验分开。生成中取消的调用显示未执行；已经启动的调用等待执行器给出真实结果，未知结果沿用恢复流程。

参数流首先按原文保存。摘要只从确实收到的字段提取；缺字段时只显示工具名，不能依赖 JSON 字段顺序。使用 [@streamparser/json](https://github.com/juanjoDiaz/streamparser-json) 的增量解析与字段路径选择，每个调用只输入新片段；不自行解析字符串、转义和嵌套结构。最终摘要以完整参数校正。

shell 输出是执行器产生的另一条流，不是模型文本。沿用 stdout/stderr 当前合并的到达顺序，不声称恢复两条管道的原始全局顺序。显示保留受限尾部及截断提示，限制沿用现有 outputLimit；快照和增量应用同一裁剪规则，完整日志另存。输出回调不改变进程停止、超时和结果未知的现有判断。

read、patch 没有自然的长输出流时直接返回最终结果，不人为拆字或制造进度。传输统一并不要求每个工具都一定产生增量。

## 前端渲染

正文以消息的稳定 id 保存源文本与生成状态。到达的 chunk 立即合并数据；同一渲染帧中的变化可合并刷新，先以约 30 次/秒为上限目标，开始、结束和阶段切换立即应用。不额外排队逐字播放。仅更新受影响的记录，不在每次 delta 重建整个 Transcript。

Markdown 继续先使用 Foundation 的解析能力，Mac 与 iPhone 共用解析结果，iPhone 保留原有选字能力。已完成且源文本没变的消息复用解析结果；当前消息先按刷新批次重解析，避免直接编写新的 Markdown 解析器。是否进一步增量解析，以长消息的实测开销决定。

未闭合代码块、行内标记、链接、表格和列表应容忍半成品，内容始终可见；结束后用完整原文重新解析。后续文字可能改变前面内容的 Markdown 解释，不能仅凭空行永久冻结前面的块。稳定记录身份，尽量复用未变化的渲染块；不保证语法补齐时绝不重排，但避免整条消息重建或无关内容闪动。

思考摘要独立于工具。只在明确的思考条目生成期间显示一行内容，无文字时显示“思考中”，结束或中断后隐藏；完整摘要数据仍保留。开始/结束以条目事件为准，不从会话 running 或最后一条历史记录猜测，也不增加 chip 子状态。

工具参数生成时即建立行，后续更新不改变 callId。详情展开状态和批次分组沿用原来的状态；思考行隐藏不能让已显示的工具组重新编号或丢失展开状态。批次仍按同一次模型回复划分，不按相邻工具或完成顺序猜测。

滚动继续沿用现有规则：用户在底部时跟随，往上翻后不抢回；思考行消失、Markdown 高度变化和工具详情增长交给同一套滚动布局处理。

## 实施顺序与验收

1. 模型适配器、执行器输出回调、显示投影：补齐事件并覆盖快照/结束/中断。工具调度语义保持不变。
2. App 接收层与 Transcript：保存稳定身份和生成/执行阶段，按 id 应用增量，补齐工具草稿与输出显示。
3. Markdown、思考行和工具行：批量刷新、渲染复用、展开状态与滚动衔接；增加可控的动态假数据供用户预览。

重点验证跨层行为：多条目交错与最终校正不重字；参数未完整时不执行；排他工具等待阶段；开始/结束/取消期间思考行收起；shell 中文跨 chunk、长输出截断；断线重连不丢字或重复；Markdown 从半成品到完整内容与直接解析完整文本一致。

实施时优先扩展现有 subscription、harness、transcript 测试，新增测试由 test-writer 按项目规则编写；Swift 协议契约测试覆盖解码和阶段更新。这不是纯样式修改，需要运行 `.kite/check`。最终编译并打开 Mac 和 iPhone 实机，由用户验证视觉和交互，不自行截图验收。


## 实验记录（2026-09-29）

- 真实 ChatGPT 订阅请求只让模型生成文本和一个无副作用的实验调用，没有执行工具。约 6.4 秒收到完整响应；观察到思考开始、思考摘要增量、正文增量、工具开始、参数增量和完整条目。计数为 thinking 字段事件 2、text 字段事件 14、arguments 字段事件 6（包含各字段的 done 校正），证明当前订阅入口确实提供这条链路；不把一次实验的速度当作性能承诺。
- 用 App 当前 Foundation 解析器读取未闭合粗体、代码块、链接、表格、列表，内容保持可显示。4200 字符样本在本机解释执行环境下，20 次解析平均约 9.5ms；因此合并短周期更新并缓存每条消息，不在本次另造 Markdown 解析器。
- 初版 partial-json 0.1.7 实验覆盖中文、转义引号、嵌套操作数组和半个指数；随后改用 @streamparser/json 0.0.26 的持久解析器，补验跨块 Unicode 代理、字段乱序与数组位置。字符串可提前显示，半个数字不补值，未配对 Unicode 代理不进入 Swift 概要，原始参数不变。
- 长 patch 参数实验：以 128 字符一块输入，约 3 万、6 万、12 万字符分别比较初版每块全量解析/校验与新解析器。初版耗时约 102.5、412.0、1096.8ms，新实现约 2.8、2.4、2.9ms；输入包含大量 diff 正文，概要只保留最后到达的 path/type。该结果仅测本机解析路径，不代表传输或 UI 总耗时。
- 动态样本「流式会话 · 动态预览」使用真实 WorkThread 事件合并入口，提供重播；依次展示思考行、正文、同批 read/shell、等待/执行与日志、代码块和表格定稿，不连接服务或执行工具。

- 验证结果：定向 9 个 small 用例与 Swift 协议契约通过；全仓 `.kite/check` 的 54 个测试、类型检查、lint 和 App 编译通过，全量 14.6 秒。发现原检查脚本的 Bun `--parallel` 并未按文件并行，已改为两个独立进程执行小测试文件，中测试继续串行；预算与测试数量不变。
