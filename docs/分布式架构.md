# 分布式架构

本文适用于 kited、kite-net 与 App，规定 Kite 不自营服务器，身份、组网、数据、执行权与推送分别由谁负责。身份与设备的现行约定见 [身份与设备](身份与设备.md)，工作区流转的现行做法见 [Line 与工作区流转](Line与工作区流转.md#工作区流转)。

**状态：方向已确认，设计待评审。已实施不依赖付费开发者账号的部分**：账号级数据与工作机目录在工作机之间同步，发现改用组网节点列表加 `/machine`（契约见 [工作机](kited.md#账号级数据)）；身份与组网改用 Tailscale 官方登录，账号服务、Headscale 与托管仓库已下线（见 [身份与设备](身份与设备.md)）；没有远程的项目各工作机的检出互为远程（见 [项目与远程仓库](项目与远程仓库.md)）；工作区执行数据以副本跟进，流转只递执行权，支持手动流转、强制接管，以及睡眠、登出、重启、关机前的自动换机，含项目声明的环境需求与优先不带电池的机器（见 [工作区流转](Line与工作区流转.md#工作区流转)）；工作机之间的自动更新与 App 的版本锁定（见 [版本](#版本)）。**尚未实施**：执行权租约的续约与过期（意外失联后的自动接手），用 Git ref 续约要频繁推送用户的远程，与 CloudKit 一起做；CloudKit 见证、推送与后备（等加入付费账号）。

## 原则

- Kite 不运营任何服务器。数据只存在用户自己的设备上，设备之间直接同步；用户的设备是其数据的唯一权威。
- 可以依赖第三方公共服务：Tailscale 提供组网与身份，苹果提供推送（经 CloudKit）与 App 分发，执行权的见证由 Git 平台或 CloudKit 担任，模型厂商与 Git 平台照旧。这些服务默认不保存 Kite 的业务数据，经过它们的只有组网握手、推送提醒、执行权租约，以及用户本来就交给 Git 平台的代码；项目打开后备时，工作区执行数据另存一份在用户自己的私有远程或 iCloud 里。
- 面向多个用户发行：每个用户的设备自成一张网，不同用户之间没有共享的 Kite 基础设施。
- 每个工作区同一时刻只有一台设备执行和写入，其他设备持有副本并按序跟进。

## 身份与设备

- 用户身份就是 Tailscale 用户：登录 Tailscale 即登录 Kite，没有单独的 Kite 账号与密码。
- Kite 设备是该用户名下加入 tailnet 的设备：工作机运行 kited 与 kite-net，控制端运行 App。共享 tailnet 里其他用户的设备、从别的 tailnet 分享进来的设备都不算。
- 请求来源以 WhoIs 判定，只接受同一 Tailscale 用户的设备，与现在 kite-net 的核验一致。撤销设备就是把它移出 tailnet。
- 信任边界：Tailscale 的协调服务有能力往 tailnet 里加节点。需要更强的保证时开启 Tailnet Lock，是否默认开启待评估。

## 组网与发现

- kite-net 与 App 内的 TailscaleKit 连 Tailscale 官方协调服务，打洞失败时走 Tailscale 的公共中继。不再部署 Headscale。
- 发现：从 tailnet 的节点列表里找同一用户的 Kite 设备，再读各自的 `/machine` 确认身份与能力。不再有托管目录。
- App 照旧直连各工作机读实时内容、执行操作。各工作机的目录摘要也在工作机之间互相同步，App 连上任意一台在线的工作机，就能看到其他工作机最近一次的摘要。
- 组网上一条连接遇上丢包后可能一直慢下去，新开的连接却往往很快（[实测](research/2026-10-22-组网传输速度.md)）。所以设备之间的文件、附件、新版本与工作区副本都按段传：切成小段几路同时传，一段卡住就换个连接重传；提供方的接口按字节范围给不会变的内容。Git 的包是现场生成的，切不了段，传得太慢时整次换连接重来，几次之后才按宽松的设定传到底。

## 数据的归属与同步

| 数据 | 权威在哪 | 怎么同步 |
|---|---|---|
| 工作区执行数据：线程记录、实例与插件状态、monitor 与收件箱、操作收据、通知、标题、窗口 | 该工作区当前执行的设备 | 执行设备写只追加的日志，每条带工作区 `epoch` 与序号；其他工作机按序跟进，断线后从断点续传 |
| 工作区文件 | 执行设备的工作树 | 快照照旧在每个工具批次后拍，经 Git 在工作机之间同步；分支照旧推项目远程 |
| 账号级数据：设备与偏好、资源库（角色、上下文模板、插件包、点阵签名）、项目登记与项目约束、凭据 | 所有工作机共有，任一台都能修改 | 按条目带版本同步；同一条目在两台设备上并发修改时以后写的为准，被覆盖的版本保留，可以找回 |
| 模型登录、被忽略的文件、太大没进快照的文件、运行中的进程、构建产物与缓存 | 各设备本地 | 不同步 |

- 凭据只在用户自己的设备之间传输，传输由 WireGuard 加密，落地加密保存。模型登录仍按每台工作机独立授权，不复制 refresh token。
- 控制端（iPhone、iPad、只做控制的 Mac）只保存导航缓存，不是任何数据的权威副本。
- 流转不再推恢复材料：工作区的执行数据与快照本来就在工作机之间同步。
- 后备：设备之间同步要两台同时在线，执行设备出事时其他设备可能都没在线、副本落后。项目可以打开后备，执行设备每个回合结束把执行数据与快照的增量存到一直在线的地方：有远程的项目推到项目远程的 ref，只限私有远程；没有远程的项目存进用户 iCloud 的私有数据库（CloudKit）。后备只是副本，权威仍是执行设备；与 CloudKit 见证方一起接入。
- 没有远程的项目，以各设备上的检出互为远程。主线只做快进同步；两边都有新提交时，与现在一样拒绝并提示集成。原来放在托管远程上的项目（包括 Line 的项目）迁到设备之间。
- 项目 ID 由建项目的设备生成，项目登记随账号级数据同步；同一远程在两台设备上各自登记成两个项目时，按归一化的远程地址合并。

## 执行权

- 每个工作区的执行权是一张租约 `{device, epoch}`，记在见证方。见证方可以替换，只要求带版本条件的写入：Git 远程上的 ref（带预期旧值推送），或用户 iCloud 私有数据库里的一条记录（CloudKit）。写入带版本条件，同一时刻只有一台设备能改成功，这样即使设备之间彼此连不上，也不会两台同时持有执行权。
- 持有者定期续约，续不上超过租约期就自己停下。续不上通常说明它连不上外网，这时它本来也调不了模型。只有持有者执行和写入；设备之间同步时，`epoch` 更低的写入一律丢弃。
- **交接**：源设备停下执行，确认目标已跟进到日志末尾，再在见证方把租约改给目标，`epoch` 加 1。数据平时一直在同步，交接只剩递执行权这一步。两台设备都在线才能交接。
- **自动换机的范围**：Line 总是自动换机。普通工作区默认不自动换机：被忽略的文件、机器特有的环境（工具链、连着的设备、签名证书、已登录的命令行工具、本机服务）和运行中的进程都带不走，换机还要 clone、跑 setup、冷构建；工作区目录也可能正被用户在本机打开着。项目可以在设置里打开自动换机，并声明它需要的环境，例如 Xcode、连着的 iPhone。打开了的项目里，只有正在工作的工作区会换机；空闲的不动，需要时再手动流转。
- **合适的目标**：在线；工作区所用的模型厂商已登录；满足项目声明的环境需求；磁盘够用。有多台时优先不带电池的机器。
- **有预告的离开**：设备将要睡眠、关机、重启或注销时，把属于自动换机范围的工作区交给合适的目标。源设备先停下这些工作区的线程，被打断的命令记为中断；到了目标机，被打断的回合自动继续。kited 的服务停止、重启与升级不算离开。
- **意外失联**：租约过期没有续，合适的目标在见证方抢占，`epoch` 加 1，从自己的副本继续，副本落后时先从后备补齐。属于自动换机范围的工作区自动这样做，其他工作区由用户决定是否接手，接手同样经过见证方。接手要等租约过期，不是即时的。副本里结果未知的调用按 [恢复约定](harness-主循环.md#恢复约定) 进入恢复阻塞，等用户确认。原设备回来看到更高的 `epoch` 就冻结，没来得及同步出去的部分保存下来，留给用户合并。
- **见证方不可用**：持有者到期后停下，其他设备也抢不到执行权。这时由用户声明源设备已丢失后强制接管；代价是可能分叉，按 `epoch` 与设备 ID 排序，较低的一方冻结。
- 有 Git 远程的项目用自己的远程做见证方，现在的 lease 就放在那里；没有远程的项目（例如 Line）用 CloudKit。CloudKit 要求付费的开发者账号，加入之前没有远程的项目没有见证方：两台设备都在线时直接交接，有预告的离开照常换机，意外失联不自动接手，由用户决定是否强制接管；没有 CloudKit 的工作机（例如 Linux）照旧用 Git ref。同一个工作区始终只用一个见证方。

## 版本

- 没有下载服务器：新版本只来自用户在自己某台设备上的安装。安装就是发布，发布记录是一条账号级数据，后写的为准；其他工作机从组网里正在运行这一版的工作机取运行文件，空闲时换上。做法见 [自动更新](macOS安装与打包.md#自动更新)。
- 工作机之间只与构建号相同的对端跟进工作区副本、流转与换机、拉取没有远程的项目。账号级数据的同步、`/machine` 与取新版本的接口跨版本保持兼容，新旧版本靠它们发现并取得新版。
- App 与工作机按协议号判断能否协作，不符的那台工作机在 App 里锁定为待更新，见 [App](App.md#版本)。

## 推送

- 后台或未运行的 iPhone、iPad 经 CloudKit 收通知：工作机把一条提醒写进用户 iCloud 的私有数据库，设备事先订阅了这类记录，由 iCloud 推送。Kite 不持有推送密钥，也不需要服务器。
- 写 CloudKit 需要 App 身份，kited 经 Mac App 或 App 内的辅助程序写入；没有 Mac 的工作机（例如 Linux）不发推送。
- 提醒只带标题、摘要与事项 ID，送达后删除；正文在用户点开后从工作机读取。

## 离线

- 设备离线时仍能读自己的副本。代理每一步都要调用模型，断网时本来就不能工作，因此不为离线执行设计。
- 账号级数据可以在离线设备上修改，联网后按上面的规则合并。

## 迁移

改造时没有在用的数据，不做迁移：旧的账号服务与 Headscale 已下线，各设备装新版后重新登录 Tailscale。

## 待验证

- 内嵌 TailscaleKit 的 App 能否通过上架审核。官方登录在 Mac（tsnet）与 iPhone（TailscaleKit）上已经走通，首次登录会遇到上游的错误页，引导要专门设计，见 [官方组网实测](research/2026-10-15-官方组网实测.md)。
- Tailscale 免费额度（设备数、用户数）对个人用户是否够用；商业发行的 App 内嵌 tsnet、让每个用户用自己的 Tailscale 账号，是否符合 Tailscale 的使用条款。组网层要保持可替换，以防条款或额度变化。
- CloudKit：前提是付费的 Apple Developer Program，现在的签名团队是个人团队，不能开 iCloud 与推送；准备上架时再加入。订阅推送在 App 未运行时能否送达、延迟；带版本条件的写入能否做租约的比较后更新；App 界面没有运行时，kited 能否经 App 内的辅助程序持续读写（推送与续约都依赖这一点）。
- GitHub 设备码授权能在客户端完成、不需要 client secret。
- 工作机之间日志复制与 Git 同步的带宽，以及 Line 记录的大小。
- 同步要按「可能一直走境外中继」设计：增量、可续传、不阻塞当前操作。2026-10-15 的一组实测见 [官方组网实测](research/2026-10-15-官方组网实测.md)：同一 Wi-Fi 直连约 8 毫秒；iPhone 蜂窝到 Mac 家宽打不了洞，经东京官方中继往返约 0.4 秒，一次 HTTP 请求约 0.5 秒。还要验证：其他网络下的直连比例，协调服务与登录在中国大陆的长期可达性。
- 受管网络：出网的组网 UDP 经路由器认证的 WireGuard 通道、只在这条路径上打洞，发往本机直连网段的直接走网卡（局域网直连待真机验证），在一台 Mac 上已经验证可以与蜂窝网络下的手机经 IPv6 直连（见 [官方组网实测](research/2026-10-15-官方组网实测.md)）。现已作为可选的「受管网络通道」进入 kite-net，默认不配，见 [工作机](kited.md)。
- 用户自己的常开设备做中继（Tailscale peer relays）：需要外面连得进来的 UDP 端口（公网 IPv6，或公网 IPv4 加端口转发），要在访问策略里授权，不能跑在 iOS 上；tsnet 能否充当中继、访问策略能否由 Kite 自动配置。
- 睡眠通知与系统给出的等待时间（文档称约 30 秒）。登出、重启、关机的预告用的是 loginwindow 的 notify 广播，不是公开接口：能否按时收到，预告到 SIGTERM 之间与之后各有多少时间（安装的 launchd 配置允许 SIGTERM 后 30 秒），要在真机上登出、重启实测。服务停止、重启与升级不带预告，以此与离开区分。
