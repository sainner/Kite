# Line 与工作区流转

本文适用于 kited、账号服务与 App，规定个人 agent Line、线程向用户的上报与交接链、monitor，以及工作区的稳定身份、远端创建与跨机流转。

**状态：方向与下列决定已确认，尚未实现，尚未批准编码。** 实施时按本文替换现行文档中的冲突陈述（见文末），并把本节状态改为已实现范围。对象归属见 [产品架构](产品架构.md)，执行与恢复语义沿用 [harness 执行约定](harness-主循环.md) 与 [会话状态机](会话状态机.md)，操作与授权沿用 [实例操作](实例操作.md)。

## 目标与原则

Line 是常驻的个人 agent，统一协调账号下各项目的工作区，减少用户巡视进度、搬运上下文、转发问答和记挂事项的负担。系统状态就是它的动态上下文：项目线程完成或需要输入时，Line 主动交接给用户；用户回复 Line，Line 核对后转给正确的线程，或按用户的决定结束线程、收尾工作区。

- 第一版就跨机器。Line 自己能换机器，不必带着它管理的项目一起迁。
- Line 复用普通项目、工作区、目录与 Git；「全局」只表示用途和获准范围，不是新的对象类型。
- 复用现有 agent 回合。monitor 只是一种输入来源，不另造模型循环。
- 跨机流转是通用工作区能力，Line 复用它。
- 流转材料走项目自己的 Git 远程，包括用户自有的平台远程；不建特殊的无 Git 体系，也不建托管 sidecar 仓库。
- 工作区可以从远端创建，选择执行机器并运行 setup；本地检出改为自动步骤，不再是用户可见的前置条件。

本文中「交接」指 Line 与用户之间的往来；线程向用户提出的结构化事项称「上报」，与 [线程通知投递](线程通知投递.md) 里输入纳入请求的「交接」无关。

## 对象与职责

| 角色 | 负责 | 不负责 |
|---|---|---|
| Line agent | 理解目标、协调任务、与用户交接 | 代码、研究、测试等具体工作 |
| Line 工作区 | Line 的会话、记忆文件、待办与插件配置 | 其他项目的实时状态 |
| Kite 管理插件 | 查询状态、传递回复、管理线程与工作区 | 自行扩权 |
| 普通项目 agent | 执行具体工作，向用户上报 | 跨项目协调 |
| kited | 执行、持久化、权限、工作区生命周期与流转 | 集中仲裁 |
| 账号服务 | 设备发现、项目登记、凭据 | 会话正文、转发执行、工作区执行权 |
| 项目远程 | 代码、流转材料、执行权 lease | 实时状态 |
| monitor | 观察变化、保存处理进度、投递有效输入 | 自己运行模型 |

实时任务状态从原工作区读取。Line 的记忆保存在它项目的 `.kite/memory/` 文件里，随 Git 流转；待办等插件实例状态随工作区的恢复材料流转。全局待办可以聚合，但引用原实例，不复制出第二份事实。

## 工作区的稳定身份与执行权

工作区 ID 在创建时生成，此后在任何机器上都不变。当前宿主机器、目录和检出是可变属性。同一 ID 在不同机器上的记录以 `epoch` 区分新旧，`epoch` 从 1 开始，每次接管加 1。

执行权记录在项目远程的 `refs/kite/lease/<工作区>`，内容为 `{machine, epoch, state}`，`state` 为 `active` 或 `handing_off`。更新一律用 Git 的比较后更新推送做 CAS，远程服务端保证原子。从未流转过的工作区没有 lease，本机即持有者。

- 工作机联网后核对自己持有的工作区：lease 的 `epoch` 更高且机器不是自己，就把本地记录标为 `transferred` 并冻结：拒绝 send、resume、setup、采纳和 monitor 推进，只读历史仍可用。
- 离线时查不到 lease，按仍持有继续。因此接管默认要求源机自己先进入 `handing_off`；用户显式声明源机丢失时才允许强制接管。被强制接管的源机回来后冻结，本地多出的改动保存为快照，留给人合并。
- 目录上报的工作区摘要带 `epoch` 与 `transferred` 状态。App 按工作区 ID 关联，同一 ID 取 `epoch` 最高的记录为当前宿主，其余显示为已流转。窗口集合随工作区走；布局与阅读位置仍按设备保存，键是工作区 ID 与窗口 ID，流转后不丢。

执行权只决定谁能推进工作区，不决定谁能读取远程里的材料；读取权限就是仓库权限。

## 远端创建工作区与受控 setup

创建工作区的入口接受项目和目标机器，不再要求先有检出。目标机没有该项目的检出时，自动 clone 到默认路径并登记，再创建工作区；检出对象保留，`KITE_MAIN_DIR` 仍指向它。用户指定了机器就在那台机器上建，不自动换机。

创建前检查目标环境，检查失败不创建：平台与系统版本、所选模型厂商在目标机的登录状态、项目声明的凭据引用能否领取、磁盘空间。项目自己的工具链以 setup 的结果为准，负载与缓存只作参考。

setup 的执行要求：

- 与 shell 共用操作系统沙箱：工作区可写，必要工具链可读，宿主凭据、数据库与会话记录受保护。网络在项目级网络授权落地前默认开放，之后按授权收紧（待定）。
- 显式传环境，只提供约定变量，不继承 kited 进程的完整环境。
- 完整输出只写日志文件；事件只带退出码和截断摘要。使用了凭据的 setup 与带 secrets 的 shell 一样丢弃全部输出。
- 失败时工作区为 `failed`，可以重跑，不自动重跑。

环境分层：代码、普通配置和模板随 Git；密钥、证书与敏感 `.env` 通过凭据服务按范围授权，setup 以引用领取，不上传忽略文件；依赖和构建产物在目标机重建或复用缓存；会话与插件状态进入恢复材料。setup 如何声明所需凭据引用尚未确定（待定）；在此之前 setup 不接触凭据。

## 工作区流转

流程：检查目标环境 → 源工作区进入可交接状态 → 保存恢复材料并推送 → 目标还原并运行 setup → 校验 → 转移执行权 → 恢复会话、插件与 monitor → App 按工作区 ID 重连。

**可交接状态。** 所有线程空闲，没有恢复阻塞，没有结果未知的操作；不满足就拒绝，不猜测。进入后 lease 置为 `handing_off`，源机拒绝新的执行，待处理输入原样进入材料。用户可以取消，取消把 lease 改回 `active`，只在目标尚未接管时成立。

**恢复材料**全部是项目远程 `refs/kite/transfer/<工作区>/` 下的 ref，源机推完即可下线：

| ref | 内容 |
|---|---|
| `branch` | 工作区分支头；根工作区没有 |
| `snapshots` | 快照链，只推最近一段 |
| `worktree` | 未提交改动打成的 commit，含未跟踪但未忽略的文件 |
| `records` | 工作区、实例、线程、标题、窗口、通知、操作收据、上报、monitor 状态的导出，以及各线程的 journal 与 Claude 原生记录 |

材料按「有仓库读权限的人都能看」来定：不含被忽略的文件、凭据和 kited 内部凭据；journal 中的命令输出照实保留，使用了 secrets 的命令本来没有输出；工具结果里的图片以说明文字替代，不进材料。PID、运行中的进程、模型登录不复制，目标机必须已完成所用厂商的登录。

**目标还原。** 目标机确认或自动建立检出，取 transfer ref，核对 lease 仍是源机的 `handing_off` 与预期 `epoch`，再从 `branch` 建工作树、把 `worktree` 还原为未提交改动、导入 `records`、改写 Claude 原生记录的目录与 cwd 字段、运行 setup、保存初始快照。全部成功后 CAS 把 lease 改为自己的 `active` 与 `epoch + 1`，工作区才为 `open`，并删除 transfer ref。CAS 之前任何一步失败都清掉本地半成品，lease 不变，源机可以取消交接继续工作。

根工作区的还原落到目标检出的根工作区：目标根工作区没有实例时沿用流转来的 ID 与内容，已有实例时拒绝。源机上的根工作区目录不动，只冻结实例与线程。

恢复的线程沿用 [恢复约定](harness-主循环.md#恢复约定)：排队输入保留，等待显式输入或继续；未完成的工具按原规则标记，不自动重放。

**公开仓库与平台。** 绑定了 GitHub 的项目按仓库可见性判断，公开仓库默认不推材料，项目上显式打开才推；拿不到可见性的平台首次推送前问用户一次。流转前先推一个极小的探测 ref，平台拒绝自定义 ref 就明确报错，不改走别的路径。

## 上报与交接链

线程通过 Kite 工具 `report` 向用户提出结构化事项，harness 与 Claude 共用，不靠答复里有没有问号判断。上报对象归线程所有，同一线程同时只能有一个 open 的上报。

| kind | 含义 | 结束方式 |
|---|---|---|
| `question` | 需要用户回答才能继续 | 用户答复 |
| `confirm` | 需要用户决定是或否 | 用户选择 `yes` / `no` |
| `done` | 线程认为任务完成，等待验收 | 用户接受或退回 |
| `blocked` | 线程无法继续，说明原因 | 用户答复或关闭 |

状态与收据分开记录，每一步各有凭据，缺一步不能宣称下一步：

```text
open → answered → delivered → incorporated → closed
                                         ↘ superseded / archived
```

- `answered`：用户的答复已可靠保存，可以保存在原线程所在机器，也可以保存在 Line 所在机器。
- `delivered`：答复作为输入保存到目标线程，用输入 ID 去重；目标离线时停在 `answered`，界面说明未送达，不说已继续。
- `incorporated`：输入已纳入一次模型请求，沿用现有纳入语义。
- `closed`：纳入后的回合结束，或用户关闭 `done` / `blocked`。
- `superseded`：线程在上报仍 open 时收到了别的用户输入，或线程自己已经解决；之后到达的答复拒绝，不再追问。
- `archived`：线程或工作区归档，open 的上报关闭并记原因；尚未纳入的输入退还给发起方，Line 发起的由 Line 向用户说明。

用户可以在原线程窗口直接答，也可以答给 Line，两边都必须引用上报 ID。答复落到线程时来源为人，并记录「经 Line 转达」；Line 不改写用户原文，Line 自己的补充说明作为另一条 Kite 来源的输入。同一上报的第二次答复拒绝，或作为追加由用户确认。退回 `done` 时的说明作为新输入开始下一回合。

状态分离：

| 状态 | 判据 | 自动触发什么 |
|---|---|---|
| 回合结束 | `idle` 且 `completed` | 无 |
| 会话空闲 | 没有排队输入、没有恢复阻塞 | 无 |
| 任务完成 | 线程发出 `done` | Line 交接给用户 |
| 用户验收 | 用户把 `done` 关闭为接受 | 无 |
| 集成、推送、归档 | 各自的显式操作 | 由用户或经确认的 Line 触发 |

一句「收到」不收尾任何东西。

## Line

**常驻工作区。** 首次启用时创建一个托管项目，在所选机器上 clone 并以根工作区承载 Line：一个 Line 代理实例，加记忆、待办等持久插件实例。Line 的根工作区由宿主在回合结束与进入可交接状态时提交并推送现场，这是对「根工作区不自动提交」的例外，只适用于 Line 的项目。Line 换机器走通用流转。

**管理插件。** Line 的工具对应现有 HTTP 操作：列出机器、项目、工作区与线程状态，读取和答复上报，send、resume、stop，归档线程或工作区，在指定机器创建工作区，发起流转。Line 所在的 kited 作为同账号设备直接调用目标 kited，请求带来源字段「代理 Line、实例 ID」；目标只把来源记入收据与历史，用于显示和 monitor 去重，不按来源做策略判断。目标侧不区分代理与用户的理由：来源只是调用方 kited 的声明，可信度等于设备，目标侧规则挡不住调用方自身的故障。

权限全部在 Line 所在机器：Line 实例的操作授权允许目标范围为账号目录里的全部工作区，普通代理仍限同工作区；白名单由用户在 Line 的操作授权页编辑。stop、归档、流转、创建这类动作须引用一条 Line 线程上已答复、决定为 `yes` 且未被使用过的 `confirm` 上报，由宿主核验后放行，模型只能引用，不能伪造。

**monitor。** 属于 Line 工作区的宿主机制，持久保存订阅、每个目标的已确认状态指纹和待投递项，随工作区流转。订阅来源是账号目录，默认覆盖账号下全部工作区，目前不提供开关。

- 不消费事件日志。远程 kited 的事件只提示重读目标状态；离线机器保留上次指纹，超过阈值后标为不可达。
- 指纹包含线程的执行阶段、上一回合结果、等待继续、恢复阻塞、open 上报及其状态，以及工作区状态与 `epoch`。由指纹派生待办集合；集合变化才生成一条 Kite 来源的输入投递给 Line 的线程，正文使用 `line.monitor` 模板。
- Line 空闲时该输入开始回合，运行中在下一次自然请求纳入。同一目标的多次变化合并为一条；Line 自己发起的操作引起的变化按来源字段跳过，不唤醒。合并窗口与 Line 的每回合请求预算共同限制唤醒成本。
- 无事时不运行模型。模型运行也不一定给用户发消息：Line 对用户的主动消息就是它线程上的上报。

## 接口草案

以下为契约级草案，字段与错误码在实现时按 [实例操作](实例操作.md) 的收据与错误语义定稿。

| 入口 | 约定 |
|---|---|
| `POST /workspaces` | 接受 `project` 代替 `checkout`；没有检出时自动 clone 并登记 |
| `GET /environment?project=` | 平台、模型登录状态、凭据引用可领取性、磁盘；只读 |
| `POST /workspaces/:id/handover` | 进入可交接状态并推送材料，返回 `epoch`；不满足条件时 409 |
| `POST /workspaces/:id/handover/cancel` | 目标未接管时撤回，lease 改回 `active` |
| `POST /workspaces/restore` | `{project, workspaceId, operationId}`；还原、setup、CAS 接管；失败清理本地 |
| `GET /threads/:id/reports` | 线程的上报及状态 |
| `POST /threads/:id/reports/:report/answer` | `{id, text?, decision?, note?}`，`id` 为输入 ID；已关闭或已答复返回 409 与当前状态 |
| `POST /threads/:id/reports/:report/close` | `{id, outcome}`，关闭 `done` / `blocked` |
| `GET /workspaces/:id/monitor` | Line 工作区的订阅、指纹与待投递项；只读 |
| 工具 `report` | `{kind, text, refs?}`，返回上报 ID；已有 open 上报时报错 |
| 目录摘要 | 工作区项增加 `epoch` 与 `transferred` |

## 验收

| 验收项 | 依据的机制 |
|---|---|
| 两机任务不串话 | 全局工作区 ID；上报绑定机器、项目、工作区与线程 |
| 回复重试不重复执行 | 答复用输入 ID 去重；非幂等操作用 operationId 收据 |
| 重启不丢问题 | 上报与 monitor 指纹持久化，随材料流转 |
| 原会话已解决后不再追问 | `superseded`；Line 投递前重读状态 |
| 归档不吞输入 | 归档退还未纳入输入并记关闭原因 |
| 流转后能续接 | 材料 ref 完整导入；排队输入与 monitor 恢复 |
| 旧宿主不能继续执行 | lease `epoch` 冻结 |
| 迁移失败可恢复 | CAS 之前源机保留并可取消交接 |

## 范围外与待验证

范围外：多个 Line、跨账号的协调与交接给谁、Linux 实机、资源配额、Line 的界面细节。

待验证：OpenAI 加密推理与 Claude 思考签名能否在另一个账号的登录下继续使用，不能时按跨厂商交接的方式丢弃推理；各平台对自定义 ref 的接受情况；Claude 原生记录改写 cwd 后能否正常恢复；材料大小与推送耗时。
