# Line 与工作区流转

本文适用于 kited 与 App，规定个人 agent Line、会话状态与关注设备决定的转发、monitor，以及工作区的稳定身份、远端创建与跨机流转。审批与提问见 [工具审批与提问](工具审批与提问.md)，同一工作区多线程并行见 [工作区并行](工作区并行.md)。

**状态：已批准编码，分期实施。** 已实现：按项目远端创建工作区（环境检查、自动 clone、沙箱内的 setup 与重跑），工作区 `epoch`、执行权的核对与冻结，工作区副本的跟进与跨机流转（交接、撤回、还原接管、强制接管），工作机睡眠、登出、重启或关机前的自动换机（含项目声明的环境需求），Line 的启用、跨机调用、必问动作的执行前审批；kited 侧的关注设备、收件箱（Line 的 [monitor](Monitor.md) 实例，含离开期间的时间线）、代处理与两种托管、`line_handle` 与 `line_relay`、monitor 的事件路由（含回来简报与每日唤醒预算），自约唤醒（通用 monitor 的定时来源），系统通知的事件，以用户为中心的记忆（提示词与项目说明）。App 侧已实现：点侧栏顶部的标志进 Line 的工作区（没有 Line 时选一台工作机启用），收件箱窗口（等你的事项与离开期间的时间线、直接回应、交给 Line、托管菜单），上报关注设备，Mac 系统通知（只带「交给 Line」），工作区的手动流转与强制接管；尚未经真机验收。尚未实施：手机推送、执行权租约的续约与过期（意外失联后的自动接手）。实施时按本文替换现行文档中的冲突陈述（见文末），并把本节状态改为已实现范围。对象归属见 [产品架构](产品架构.md)，执行与恢复语义沿用 [harness 执行约定](harness-主循环.md) 与 [会话状态机](会话状态机.md)，操作与授权沿用 [实例操作](实例操作.md)。

## 目标与原则

Line 是常驻的个人 agent，统一协调账号下各项目的工作区，减少用户巡视进度、搬运上下文、转发问答和记挂事项的负担。Line 首先是用户的收件箱：所有轮到用户的事（等你回应的审批和提问、用户离开期间结束的回合、失败）原样汇集到这里，用户直接处理；其次才是用户的代理人：用户点「代处理」或开启托管时，Line 带着对用户的了解替用户决定，拿不准的留给用户。Line 还能自己约时间醒来，替用户记挂事情。

- 第一版就跨机器。Line 自己能换机器，不必带着它管理的项目一起迁。
- Line 复用普通项目、工作区、目录与 Git；「全局」只表示用途和获准范围，不是新的对象类型。
- 复用现有 agent 回合。monitor 只是事件路由和一种输入来源，不另造模型循环；默认不唤醒 Line，只有用户交代了事或 Line 自己的事有了结果才跑模型。
- 跨机流转是通用工作区能力，Line 复用它。
- 工作区的执行数据平时就在工作机之间跟进，流转只递执行权；不经服务器，也不把会话记录推到项目远程。
- 工作区可以从远端创建，选择执行机器并运行 setup；本地检出改为自动步骤，不再是用户可见的前置条件。

本文中「交接」指 Line 与用户之间的往来，与 [线程通知投递](线程通知投递.md) 里输入纳入请求的「交接」无关。

## 对象与职责

| 角色 | 负责 | 不负责 |
|---|---|---|
| Line agent | 理解目标、协调任务、受托替用户处理收件箱、与用户交接 | 代码、研究、测试等具体工作；项目的专业经验 |
| Line 工作区 | Line 的会话、关于用户的记忆、收件箱（Line 的 monitor）、Line 自约的定时与插件配置 | 其他项目的实时状态 |
| Kite 管理插件 | 查询状态、传递回复、管理线程与工作区 | 自行扩权 |
| 普通项目 agent | 执行具体工作；越出授权时经审批层请求 | 跨项目协调，也不必声明自己在等用户 |
| kited | 执行、持久化、权限、工作区生命周期与流转 | 集中仲裁 |
| 账号级数据 | 工作机目录、项目登记、凭据，在工作机之间同步 | 会话正文、转发执行、工作区执行权 |
| 项目远程 | 代码；有远程的项目还记执行权 lease | 实时状态、会话记录 |
| Line 的 monitor | 把各处事件路由成进收件箱、发系统通知、唤醒 Line 三种动作，保存收件箱与处理进度；是通用 [monitor](Monitor.md) 的一个实例 | 自己运行模型 |

实时任务状态从原工作区读取。Line 的记忆保存在它项目的 `.kite/memory/` 文件里，随 Git 流转；待办等插件实例状态随工作区的副本流转。全局待办可以聚合，但引用原实例，不复制出第二份事实。

## 工作区的稳定身份与执行权

工作区 ID 在创建时生成，此后在任何机器上都不变。当前宿主机器、目录和检出是可变属性。同一 ID 在不同机器上的记录以 `epoch` 区分新旧，`epoch` 从 1 开始，每次接管加 1。

执行权的见证方按项目分，同一个工作区始终只用一个，见 [分布式架构](分布式架构.md#执行权)：

- 有远程的项目记在项目远程的 `refs/kite/lease/<工作区>`，指向一个提交，树里的 `lease.json` 为 `{machine, epoch, state}`，`state` 为 `active` 或 `handing_off`；新提交以旧提交为父，留下流转历史。更新一律带预期旧值推送（`--force-with-lease`）做 CAS，远程服务端按旧值比较后更新，保证原子。从未流转过的工作区没有 lease，本机即持有者。
- 没有远程的项目暂时没有见证方（CloudKit 要等加入付费开发者账号）：两台都在线时由目标通知源机交出；其他工作机从目录摘要里看谁持有、`epoch` 多少。

- 工作机联网后核对自己持有的工作区（启动与每 5 分钟，随项目同步）：有远程的看 lease，没有远程的看其他工作机的目录摘要；`epoch` 更高且机器不是自己，就把本地记录标为 `transferred` 并冻结：停下线程与插件，拒绝 send、resume、setup、采纳和 monitor 推进，只读历史仍可用。
- 离线时查不到，按仍持有继续。因此接管默认要求源机自己先进入 `handing_off`；用户显式声明源机丢失时才强制接管。被强制接管的源机回来后冻结，本地多出的改动保存为快照，留给人合并。
- 工作机目录摘要里的工作区带 `epoch` 与 `transferred` 状态。App 按工作区 ID 关联，同一 ID 取未冻结且 `epoch` 最高的记录为当前宿主，其余显示为已流转（App 目前只隐去冻结记录）。窗口集合随工作区走；布局与阅读位置仍按设备保存，键是工作区 ID 与窗口 ID，流转后不丢。

## 远端创建工作区与受控 setup

创建工作区的入口接受项目和目标机器，不再要求先有检出。目标机没有该项目的检出时，自动 clone 到数据目录并登记，再创建工作区；检出保留。用户指定了机器就在那台机器上建，不自动换机。

创建前检查目标环境，检查失败不创建：平台与系统版本、所选模型厂商在目标机的登录状态、磁盘空间。项目自己的工具链以 setup 的结果为准，负载与缓存只作参考。当前实现拒绝的条件是所选角色默认模型的厂商未登录、工作树或检出所在卷剩余不足 1 GB；平台只报告。

setup 的执行要求：

- 与 shell 共用操作系统沙箱：工作区可写，必要工具链可读，检出与其他 Git 元数据只读，宿主凭据、数据库与会话记录受保护。网络在项目级网络授权落地前默认开放，之后按授权收紧（待定）；开放时上游沙箱的回环与本机地址检查仍然生效。
- 显式传环境，只提供约定变量，不继承 kited 进程的完整环境。
- 完整输出只写日志文件；事件只带退出码和截断摘要。
- 不领取凭据；设了路径的项目密钥由宿主在 setup 之前写进工作树。
- 失败时工作区为 `failed`，可以重跑，不自动重跑。

环境分层：代码、普通配置和模板随 Git；密钥、证书与敏感 `.env` 存成凭据（账号级数据），需要落成文件的设好工作区里的路径，由宿主在建工作树时写入，不上传忽略文件；依赖和构建产物在目标机由 setup 重建或复用缓存；会话与插件状态在工作区副本里。

## 工作区流转

流程：工作区副本平时跟进 → 源工作区进入可交接状态 → 目标把副本补到末尾，还原并运行 setup → 校验 → 转移执行权 → 源机冻结 → 恢复会话、插件与 monitor → App 按工作区 ID 重连。

**工作区副本。** 其他工作机持续跟进执行设备上的工作区：执行设备列出它持有的工作区和各自的摘要，跟进方摘要对不上就按文件增量拉取。副本包含工作区、实例（含插件状态）、线程、标题、窗口与窗口请求、尚未交接的通知、操作收据、monitor 状态的数据库行，各线程的 journal、控制状态与命令日志，历史差异，以及 Claude 原生记录；只长不改的文件（journal、命令日志）从原来的末尾续传。本机有这个项目检出的跟进方，还从执行设备的检出取快照链与工作区分支。同一工作区出现在几台上时跟 `epoch` 最高的那台；执行设备在线却不再列出（归档或流转走）时副本删掉。副本是用户自己工作机之间的拷贝，经组网的 WireGuard 传输，图片与命令输出照原样保留；PID、运行中的进程、模型登录不复制，目标机必须已完成所用厂商的登录。

通知序号在每台工作机上各自自增，线程以序号为交接游标。副本的清单带上各线程的游标，目标机只导入游标之后的通知，并在本机重新编号到游标之后；已交接的通知正文已在记录里。

**可交接状态。** 所有线程空闲，没有恢复阻塞，没有结果未知的操作；不满足就拒绝，不猜测。用户在 App 里手动流转时先连带确认待恢复的线程，自动换机不确认。进入后本地工作区状态为 `handing_off`，有远程的项目同时把 lease 置为 `handing_off`；源机拒绝新的执行，停下执行进程，保存最后一个快照，待处理输入原样留在记录里。中途失败停在这个状态，可以重试交接或撤回。用户可以取消，取消把状态与 lease 改回 `active`，只在目标尚未接管时成立；已被接管时返回 409 并冻结本地记录。

**目标还原。** 目标机确认或自动建立检出，把副本补到源机的末尾（源机须在线），核对源机仍在 `handing_off` 与预期 `epoch`（有远程的项目同时核对 lease），再从副本里的分支建工作树、用最后一个快照还原未提交的改动、导入记录、改写 Claude 原生记录的目录与 cwd 字段、写入设了路径的项目密钥、运行 setup、保存初始快照。全部成功后才转移执行权：有远程的项目 CAS 把 lease 改为自己的 `active` 与 `epoch + 1`；没有远程的项目通知源机交出，源机冻结本地记录并记下目标，同一次交接只交给先到的那台，别的目标再来通知时拒绝；回应丢失时目标再通知一次。转移之前任何一步失败都清掉本地半成品，执行权不变，源机可以取消交接继续工作。

目标机已有同一 ID 的冻结或已归档记录（工作区流转回来）时，以副本替换它；还留着旧工作树时先归档本机的旧记录。替换之前先留下旧记录的数据库行、会话文件与快照引用，接管失败时原样还原，接管成功后才删。还原检查目标机对副本里各线程所用厂商的登录，未登录时拒绝。已归档线程的会话文件同样在副本里。

恢复的线程沿用 [恢复约定](harness-主循环.md#恢复约定)：排队输入保留，等待显式输入或继续；未完成的工具按原规则标记，不自动重放。有预告的离开是例外，见下。

**手动流转。** 用户在 App 里或经 Line 发起：源机交出，通知目标还原，目标接过执行权后源机立即核对并冻结；目标没接成时源机撤回交接，工作区重新开放。

**子工作区。** 子工作区随父工作区一起流转，不能单独流转：手动流转与有预告的离开都以父工作区为单位，连同它下面的全部子工作区交给同一个目标，可交接状态要求整组都满足，有一个交不出就整组撤回；自动换机按整组判断，组里有正在工作的就整组换。目标从父工作区起逐个接过，父工作区接过之后某个子工作区没接成时，它和后面的撤回、留在源机，这时它们的父工作区已不在源机，可以单独再流转。强制接管同样整组接管。子工作区见 [项目与远程仓库](项目与远程仓库.md#子工作区)。

**强制接管。** 源机丢失（用户确认）时，目标不联系源机，用本机手上的副本接管：副本落后的部分丢失，有远程的项目照样在 lease 上 CAS 到更高的 `epoch`。源机回来后看到更高的 `epoch` 就冻结，本地多出的改动存成快照，留给人合并。

**有预告的离开。** 工作机将要睡眠（macOS 的系统睡眠预告）、登出、重启或关机（loginwindow 的预告）时，在时限里把属于自动换机范围的工作区交给合适的目标：Line 的总是换；项目在设置里打开了自动换机的，只换正在工作的工作区，空闲的不动。合适的目标在线、工作区所用的模型厂商已登录、满足项目声明的环境（Xcode、连着的 iPhone 或 iPad）、磁盘够用；几台都合适时优先不带电池的，再优先已有这个项目检出的。正在工作的线程先打断，收回排队的输入；到了目标机先补一条说明让它接着做被打断的回合，再把排队的输入按原来的正文与来源重发。睡眠由系统等交接收尾；登出、重启、关机拦不住，kited 收到 SIGTERM 后先等交接收尾再停。时限里交不出去的撤回，留在本机接着做；醒来或登出被取消时还停在可交接状态的同样撤回。kited 的服务停止、重启与升级不带预告，不算离开。

## 会话状态与关注设备

**会话状态。** 从用户的角度，线程只有四种状态：工作中、等你回应、回合结束、归档。等你回应是回合中途卡在一个审批上，或者代理停下来等它发出的提问、密钥请求，见 [工具审批与提问](工具审批与提问.md)；回合结束就是轮到用户，无论代理是在汇报、说做完了还是把问题写在回复里，用户都要看一眼，所以不另设由代理声明的「完成」或「在等你」，也不靠回复里有没有问号判断。失败、恢复阻塞与工作区准备失败沿用 [会话状态机](会话状态机.md)。

**关注设备。** Line 所在的工作机保存 `focusedDevices`：此刻正在关注 Kite 的设备，可以同时有多台。用户是否在用 Kite 以它为准；不用会话「已读」判断（窗口停着、自动滚到底会被误判），也不用键鼠空闲判断（人在电脑前不一定在用 Kite）。

- Mac：Kite 窗口获得焦点时加入，失去焦点时移出。
- 手机：Kite 在前台且连着工作机时加入，切到后台或断连时移出。
- App 与工作机的事件流断开，就视为这台设备移出；连不上 Line 所在工作机的设备不算在关注，宁可多通知，不漏。
- `focusedDevices` 变空的时刻记为离开时刻，不设宽限；之后的判定都从这一刻追溯。

## Line 的收件箱、代处理与托管

**收件箱。** 所有轮到用户的事汇集在 Line 的界面里，默认不唤醒 Line：

| | 审批、提问 | 回合结束 | 失败、恢复阻塞、准备失败 |
|---|---|---|---|
| 是什么 | 原线程等待的那个对象本身，在哪里回应都写回它 | 线程的最新一回合 | 线程或工作区的状态 |
| 何时进 | 一出现就进，不论用户在不在用 Kite | 只收离开期间发生的，用户在用 Kite 时停靠栏和标题栏已经足够 | 一出现就进 |
| 系统通知 | 没人关注时立即单条推送 | 不逐条推：离开后攒 10 分钟发第一条摘要，之后有新的再每 10 分钟最多一条 | 没人关注时立即推送 |
| 何时移出 | 被回应、被代处理或作废 | 用户给那个线程发了消息、在收件箱里点开或点「知道了」、Line 代处理清掉、线程开始新一轮或被归档 | 状态解除 |

**离开期间的时间线。** 收件箱分两段：一段是此刻等你的事项，不论你在不在都进；另一段是从离开那一刻起的时间线，记离开期间结束的回合、Line 替你做了什么和理由、在别处回应或自己解除的事项。你回来后它作为简报留着，下次离开时换成新的一段，不长期保存；没点「知道了」的回合结束留在等你的那一段。

Line 发起的工作不进用户的收件箱，结果交给 Line，由它决定要不要告诉用户。「Line 发起的工作」指最近一条输入是 Line 自己说明的线程；用户再发消息（含经 Line 转达的原话）就归回用户。Line 自己线程上的请求（它的必问动作）也进收件箱，只能由用户处理。未启用 Line 时没有收件箱，审批与提问只在原线程窗口出现。

**系统通知。** Line 找用户的通道不依赖焦点。第一版在 Mac 上由后台运行的 App 发本地通知，点开就是收件箱里那一项：Line 所在的工作机在目录事件流上推 `line.notification`，App 收到就发。手机在后台或被系统关闭时的推送经 CloudKit，单列后做，见 [分布式架构](分布式架构.md#推送)。App 没有运行时，事项留在收件箱里。

**代处理。** 收件箱的每一项都可以点「代处理」交给 Line，这时才唤醒 Line：

- 审批：批准这一次或拒绝；不替用户「允许并记住」。
- 提问：选择选项或写「其他」。
- 回合结束：读最后的回复，做完了就给用户一句总结，代理在回复里提了问题就按用户的习惯回答，只是进度汇报就清掉。
- 失败：读原因，能按用户的习惯处理的处理（例如继续），否则留给用户。

Line 不能处理它自己发起的请求（例如它要停止、流转别人的工作区），否则「必问」形同虚设。恢复阻塞、准备失败与连不上的工作机 Line 没有对应的处理手段，不能交给它；密钥请求只能由用户填写，同样不能交给它。拿不准的留给用户；交给 Line 之后它的回合结束了还没了结的，也交回用户。交回用户的事项不再自动交给 Line。代处理的结果写明由 Line 代为处理和理由，用户在收件箱里能看到它做了什么。

**托管。** 两种托管可以同时开启，都只覆盖 Line 能代处理的事项：

- 按时段托管：例如「接下来 2 小时由 Line 处理」，时段内新进收件箱的事项都交给 Line，到点自动结束。
- 超时托管：审批与提问先等用户，超过设定时间（例如 15 分钟）用户还没处理，再交给 Line。

**用户经 Line 答复。** 用户可以直接在收件箱里回应，也可以在 Line 的线程里说。后者由 Line 指定用户的那条消息，宿主照原文转达：转给等待中的提问时作为「其他」的回答，转给线程时作为一条来源为人、经 Line 转达的输入。Line 不改写用户原文，它自己的补充说明另发一条代理来源、发信方为 Line 的输入（见 [输入来源](harness-主循环.md#输入来源)）。

一句「收到」不收尾任何东西：集成、推送、归档仍是各自的显式操作，由用户或经批准的 Line 触发。

## Line

**常驻工作区。** 首次启用时在所选机器上建一个没有远程的项目和一个工作区来承载 Line：一个 Line 代理实例，加记忆、待办等持久插件实例。Line 的工作区是普通工作区，记忆等文件的改动随快照和工作区分支进入副本，换机器走通用流转，宿主不另外提交；工作机睡眠前总是换到别的在线工作机。Line 所在的工作区不能归档，项目不能删除。

当前实现：在所选工作机上 `POST /line`，建一个没有远程的项目「Line」（检出的初始版本写入说明与空的记忆索引）和一个工作区，承载一个内置角色「Line」（`kite.line`）的代理实例与它的收件箱，代理带上账号范围的 `line` 授权；本机已有 Line 时返回它所在的工作区，其他工作机的目录摘要标着 Line 时拒绝，要换机器走流转。摘要同步有延迟，几乎同时在两台启用仍可能各建一个，要等有见证方才能挡住。待办插件实例尚未随启用创建。Line 由角色识别，不是新的对象类型。

**记忆以用户为中心。** Line 的记忆是离用户最近的那份：用户的偏好、做决定的习惯、各项目的轻重缓急、以前怎么处理过类似的事项（例如「这类域名一般允许」）。各项目的专业经验留在项目自己的记忆里，Line 不收集。每次代处理的决定与理由也记下来，让 Line 越来越接近用户的判断。Line 角色的提示词与 Line 项目的说明按此修订。

**管理插件。** Line 的工具对应现有 HTTP 操作：列出机器、项目、工作区与线程状态，读取线程最后一回合的回复，转达用户答复，send、resume、stop，归档线程或工作区，在指定机器创建工作区，发起流转。Line 所在的 kited 作为同一用户的设备直接调用目标 kited，请求带来源字段「代理 Line、实例 ID」；目标只把来源记入收据与历史，用于显示和 monitor 去重，不按来源做策略判断。目标侧不区分代理与用户的理由：来源只是调用方 kited 的声明，可信度等于设备，目标侧规则挡不住调用方自身的故障。

权限全部在 Line 所在机器：Line 实例的操作授权允许目标范围为工作机目录里的全部工作区，普通代理仍限同工作区；白名单由用户在 Line 的协作授权里编辑。stop、归档、流转、创建这类动作在 [工具审批与提问](工具审批与提问.md) 里标为「必问」：Line 调用时宿主拦下，等用户批准才执行；Line 不能处理它自己发起的这类请求，代处理与托管也不例外。

工具（属于代理工具全集，只声明给 Line 角色的实例；内置「工作」角色排除它们）：

| 工具 | 动作 | 约定 |
|---|---|---|
| `line_status` | `status` | `{machine?, threadId?}`：读各工作机的 `GET /summary` 与收件箱，含未归档的工作区、线程执行状态、等你回应的对象与最近一次回合结束的时间；带 `threadId` 时返回那个线程最后一回合的回复。离线或连不上的标明原因 |
| `line_handle` | `reply` | `{item, decision?, answers?, reason}`：处理收件箱里交给 Line 的一项（代处理或托管中）。宿主核对这一项确实已委托给 Line、不是 Line 自己发起的请求；审批只能批准这一次或拒绝 |
| `line_relay` | `reply` | `{machine, threadId, from}`：`from` 是用户在 Line 线程里那条消息的输入 ID，宿主照原文转达给等待中的提问或线程，输入 ID 由两者决定，重试只去重 |
| `line_control` | `send`、`resume`、`stop`、`archive` | send 是 Line 自己的说明，来源为代理、发信方为 Line；stop 与 archive 必问 |
| `line_workspace` | `create`、`transfer` | create 用目标机的按项目创建；transfer 依次调用源机交接、目标机还原、源机核对执行权；都必问 |

授权的白名单是协作授权里的 `{operation: "line", actions}`，启用 Line 时全部打开。跨机调用经账号目录（工作机凭据可读）找到组网地址，经 kite-net 的本机 HTTP 代理入口过去，请求头 `X-Kite-Source` 声明 `{kind: "line", machine, instance}`；目标把它记在输入上（转达的用户原话记为 `via`，Line 自己的说明记为发信方），用于显示与防循环，不参与授权。必问动作执行前在 Line 的线程上等用户批准。Line 约时刻醒来（包括用户设定的每日巡视）用通用的 `monitor_start` 定时来源，到点直接唤醒 Line，不经收件箱。模型看不到输入 ID，`line_relay` 的 `from` 省略时取用户在 Line 线程里最近的一条消息；`line_status` 带 `threadId` 时读目标机的 `GET /threads/:id/reply`。

## monitor 的事件路由

Line 的 monitor 是 Line 工作区里由宿主建的那个 [monitor](Monitor.md) 实例，来源是账号下各工作机的会话状态与关注设备：把各处的事件路由成三种动作——进收件箱、发系统通知、唤醒 Line。它的视图就是收件箱；代理自己开的 monitor 不发系统通知、不进收件箱。

| 事件来源 | 事件 | 进收件箱 | 系统通知 | 唤醒 Line |
|---|---|---|---|---|
| 会话状态 | 出现审批或提问 | 是 | 没人关注时立即 | 按时段托管中（攒十几秒）；超时托管起计时 |
| | 审批或提问被回应、作废 | 移出 | — | — |
| | 别人发起的线程结束回合 | 离开期间才进 | 摘要 | 按时段托管中（按分钟合并） |
| | Line 发起的工作有了结果（线程结束回合、创建或流转完成、失败） | 否 | — | 是 |
| | 失败、恢复阻塞、准备失败 | 是 | 没人关注时立即 | 按时段托管中 |
| 关注设备 | 变空（离开） | — | — | 否，只记下离开时刻 |
| | 变非空（回来），离开够久且收件箱有东西 | — | — | 是，给用户一段简报：离开期间发生了什么、哪几件需要用户、建议先处理哪个 |
| | 超时托管到点 | — | — | 是，只交这一项 |
| | 摘要窗口到点 | — | 发一条摘要，不调模型 | — |
| 工作机 | 连不上超过阈值 | 是 | 没人关注时 | 否 |
| 用户 | 点「代处理」 | — | — | 是，只交这一项 |

去重与防循环：

- 同一线程只看最新状态，同一事项只进一次收件箱。
- Line 自己的线程、已流转走的冻结副本不产生事件。
- Line 操作别人的线程所引起的变化按来源跳过，不反过来唤醒它；但那些线程跑完的结果属于「Line 发起的工作有了结果」，照常交给它。
- 唤醒合并成一条 Kite 来源的输入，正文使用 `line.monitor` 模板；Line 空闲时开始回合，运行中在下一次自然请求纳入。没有新事项不跑模型；每天有唤醒预算，超了只进收件箱、不再唤醒。

收件箱、离开期间的时间线、托管设置与待投递项都持久化在 Line 的 monitor 实例上，随工作区流转。远程工作机的事件只提示重读目标状态，不消费事件日志；离线机器保留上次的状态，超过阈值后记为连不上。

当前实现：每 60 秒读一轮各工作机的汇总，本机状态变化后 2 秒补读，托管攒批、超时、自约时刻、摘要与托管结束按到点时间另约一次；远程工作机靠定时读取，没有订阅各机的事件流。回合结束以各工作机实时看到的收尾时间判断，工作机重启前结束的回合不补；「Line 发起的工作」只记在内存，重启后按用户的工作对待。按时段托管时审批、提问与失败攒 15 秒，回合结束攒 1 分钟；连不上 30 分钟进收件箱；离开 30 分钟以上回来才写简报。自动唤醒每天 40 次，用户点的代处理不计上限；超了托管的事项交回用户，Line 的工作结果改进收件箱。待投递的输入先存进 monitor 实例的状态再送，送不到（如 Line 正在交接）下一轮用同一 ID 补送。

## 接口草案

以下为契约级草案，字段与错误码在实现时按 [实例操作](实例操作.md) 的收据与错误语义定稿。

| 入口 | 约定 |
|---|---|
| `POST /workspaces` | 接受 `project` 代替 `checkout`；先检查环境，没有检出时自动 clone 并登记（已实现） |
| `GET /environment?project=` | 平台与系统版本、两家订阅的登录、工作树与检出所在卷的剩余空间、已有检出；只读（已实现） |
| `POST /workspaces/:id/setup` | 准备失败的工作区重跑准备（已实现） |
| `POST /workspaces/:id/handover` | 进入可交接状态：停下线程、保存最后的快照，返回 `epoch`；不满足条件时 409（已实现） |
| `POST /workspaces/:id/handover/cancel` | 目标未接管时撤回，状态与 lease 改回 `active`，返回工作区聚合（已实现） |
| `POST /workspaces/:id/handover/complete` | 没有远程的项目，目标装好后通知源机交出 `{epoch, machine}`；同一次交接只认一台；只接受工作机（已实现） |
| `GET /replica`、`POST /replica/:id` | 工作区副本：执行设备持有的工作区与摘要，按跟进方手上的文件给一页增量；只接受工作机（已实现） |
| `POST /workspaces/:id/lease/check` | 立即核对执行权，已被接管就冻结，返回工作区聚合；目标接管后可在源机调用，不必等定期核对（已实现） |
| `POST /workspaces/restore` | `{project?, workspaceId, operationId, from?, force?, continue?}`（没给 `project` 时从本机副本里取）；把副本补到 `from` 的末尾，还原、setup、转移执行权，返回工作区聚合；`force` 用本机副本强制接管，`continue` 接着做睡眠前被打断的回合；失败清理本地；同一 `operationId` 重试返回原结果（已实现） |
| 收件箱 | Line 的 monitor 实例上的操作，经 `POST /workspaces/:id/operations/:operation`：`monitor.read` 读 `{items, period, records, delegation}`，`monitor.delegate` 交给 Line 代处理，`monitor.dismiss` 移出回合结束，`monitor.hosting` 设置两种托管 `{until?, timeoutMinutes?}`；回应审批与提问时直接调原线程所在工作机的接口（已实现） |
| 关注设备 | App 在焦点、前后台与连接变化时告诉 Line 所在的工作机：`PUT /attention {device, focused}`，同时连着带 `device` 的事件流才生效；事件流断开即视为移出。`GET /attention` 读当前的 `focusedDevices` 与离开时刻（kited 侧已实现） |
| `POST /line` | 在这台工作机启用 Line，返回 Line 所在的工作区聚合；其他工作机已有 Line 时 409（已实现） |
| `GET /summary` | 这台工作机的状态汇总：未归档工作区、线程执行状态、等你回应的对象、最近一次回合结束的时间与是否 Line 发起的工作；Line 与 monitor 读取（已实现） |
| 目录摘要 | 工作区项增加 `epoch` 与 `transferred`；`line` 标出本机承载 Line 的工作区，App 据此认出没连上的工作机上的 Line（已实现） |

## 验收

| 验收项 | 依据的机制 |
|---|---|
| 两机任务不串话 | 全局工作区 ID；收件箱与转达都绑定机器、工作区与线程 |
| 转达重试不重复执行 | 转达的输入 ID 由来源消息与目标决定；非幂等操作用 operationId 收据 |
| 用户在 Kite 前时不打扰 | 有设备关注时不推系统通知，回合结束不进收件箱 |
| 离开后不漏事 | 从离开时刻起追溯；收件箱、时间线与待投递项持久化，随副本流转 |
| 默认不花钱 | 收件箱不唤醒 Line；只有代处理、托管、自约唤醒、回来简报与 Line 自己的事会跑模型，且有每日预算 |
| 越权动作须经用户 | 工具审批的必问；Line 不能处理自己发起的请求 |
| 流转后能续接 | 副本补到末尾后完整导入；排队输入与 monitor 恢复 |
| 旧宿主不能继续执行 | lease `epoch` 冻结 |
| 迁移失败可恢复 | 转移执行权之前源机保留并可取消交接 |

## 范围外与待验证

范围外：多个 Line、跨账号的协调与交接给谁、Linux 实机、资源配额、Line 的界面细节、手机推送（单列后做）、托管中按用户习惯自动推进下一步（例如测试过了就采纳，用一阵再定）。

待验证：OpenAI 加密推理与 Claude 思考签名能否在另一个账号的登录下继续使用，不能时按跨厂商交接的方式丢弃推理；各平台（GitHub、GitLab 等）对自定义 ref（lease）的接受情况，本地裸仓库已接受；副本的大小与经中继时的跟进耗时；系统睡眠预告留的时间够不够交接，关机、重启与注销的预告怎么接收。

已验证（2026-10-14，锁定版本 CLI 与测试用假端点，同一账号）：Claude 原生记录改写 cwd、放到新目录对应的位置后，删掉源目录的原文件，目标机的 CLI 仍能按会话 ID 恢复，后续请求带着流转前的对话。
