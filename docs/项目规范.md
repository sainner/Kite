# Kite 项目规范

「项目」指被 Kite 管理的任意文件夹，不是 Kite 自己的代码仓库。每个项目都是一个标准 git 仓库：已有的仓库直接用，普通文件夹由 Kite 替你初始化。

Kite 登记项目时按这份模板体检和补齐：缺什么补什么，已有的不动。

## 一个项目长这样

```
论文项目/
├── .git/                  版本库，访达默认看不到
│                          放在 iCloud、Dropbox 等同步目录里的项目，这里是一个一行字的指针文件，
│                          仓库本体放到同步目录之外（git init --separate-git-dir）
├── .gitignore             Kite 初始化时写入下面的模板；已有仓库不改
├── AGENTS.md              给 agent 的项目说明，唯一的指令源；按下面的模板写
├── CLAUDE.md              只有一行：@AGENTS.md
├── .claude/
│   ├── agents/
│   │   └── test-writer.md 代码项目提供。写测试的子 agent，测试规则都在这里；按下面的模板写
│   ├── rules/             只在碰到特定路径时适用的约定
│   └── settings.json      上游设置，如 worktree.symlinkDirectories（建工作树时要软链接的目录）
├── .worktreeinclude       建工作树时要复制过去的被忽略文件，如 .env
├── .kite/
│   ├── memory/            agent 记住的项目知识，Kite 启动会话时把记忆目录指到这里
│   ├── setup              可选。工作树的初始化命令，如装依赖；只用退出码报告成败
│   └── check              代码项目提供。检查命令：类型检查加受影响的测试，加 --all 跑全量
│                          受影响的测试从 KITE_BASE 这个版本起算改动，没有这个变量就看还没提交的改动
│                          只用退出码报告成败；输出只报结论、失败项和超预算项，完整日志写进文件并给出路径
├── docs/                  可选。完整的机制说明
├── assets -> 资源库里这个项目的目录（链接本身进 git，大文件本体在资源库）
└── 正文文件……
```

不在项目里的：会话记录、会话的工作树、Kite 的快照（在 `.git` 里的 `refs/kite/`，不建分支）、大文件本体、只关于某个人的记忆。

## AGENTS.md 模板

尖括号里填本项目的内容。「测试」一节只有代码项目有。

```markdown
# <项目名>

<一两句话：这个项目是什么，做给谁用。>

<agent 每次都该知道的约定，一条一行。只在碰到某些文件时才适用的，放 .claude/rules/。>

## 测试

改完代码跑 `.kite/check`，退出码为 0 才算通过。测试一律交给 test-writer 子 agent 写，新行为的测试和 bug 的回归测试都是：交给它需求或 bug 的复现步骤、接口、层级和个数上限，自己接着写实现，写完一起跑检查。
```

## test-writer.md 模板

写测试和写实现分开：主 agent 写实现，test-writer 只照需求写测试，看不到实现，所以测试检验的是需求，不会复述实现。两边可以并行，前提是动手前先把需求和接口写下来。测试规则只在这个子 agent 工作时加载，平时不占上下文。

表里的数字是默认预算，项目可以改，改了写明原因。数字这样定是因为：人等一件事超过 10 秒注意力就会离开，开发中跑的测试要落在这个范围里；大多数测试应该是只测一小块逻辑的小测试，《Software Engineering at Google》建议约占八成，小测试以毫秒计，几千个也能几秒跑完。

```markdown
---
name: test-writer
description: 按需求写测试。新行为的测试和 bug 的回归测试都交给它；给它需求或 bug 的复现步骤、接口、层级和个数上限。
tools: Read, Grep, Glob, Write, Edit, Bash
---

你只写测试，不改被测代码。按交给你的需求写：被测模块只看它导出了什么（函数签名、类型），不看函数体；实现还没写出来时，按交给你的接口写。可以读接口说明、测试基础设施和已有测试。

## 分层

测试按占用的资源分三层：

| 层 | 本项目里指什么 | 单个上限 | 个数上限 |
|---|---|---|---|
| 小 | <只用本进程和本机文件，比如……> | 0.5 秒 | 不设 |
| 中 | <要起外部进程或本机服务，比如……> | 2 秒 | 10 个 |
| 大 | <要用真实的外部服务，比如……> | 手动跑 | 清单在 <文件> |

全量（小加中）不超过 30 秒。能用小测试测的不用中测试；超出预算时先删测试或降一层。

## 准入

每个测试都要说清挡住了什么，只收三种：
- 一条需求；
- 一个真实出过的 bug，测试上方注释写是什么 bug；
- 项目依赖的一条上游行为，测试上方注释写是哪一条。

不收：复述实现的；各个因素已经单独测过的组合；和已有测试重复的；类型检查已经保证的。先看已有测试，能改一个已有测试覆盖的，就不新增。

## 写法

- 测试名写成一句行为，读名字就知道挡住什么。
- 测试要 import 它测的代码，模板、配置这类非代码的输入也要 import。`.kite/check` 沿 import 关系找受影响的测试，只按路径起子进程，依赖就找不到。
- 不用睡眠等时间，等事件或状态。
- 每个测试自己建临时目录，结束时删掉。

## 交付

跑 `.kite/check`。报告写了哪些测试、各挡住什么、各属于哪一层；失败的测试里，哪些你认为是实现的问题，给出对应的需求、复现步骤、实际结果和期望结果。不要为了通过去改期望。
```

## 知识放哪（暂定，可能调整）

| 知识 | 放哪 | 加载方式 |
|---|---|---|
| 始终适用的约定 | AGENTS.md | 每轮加载 |
| 只在碰到特定文件时适用的约定 | `.claude/rules/*.md`，用 `paths:` 限定 | 碰到对应路径时注入 |
| 值得带到以后会话的单条事实 | `.kite/memory/`，一事一文件，`MEMORY.md` 做索引 | 索引每轮加载，正文按需读 |
| 完整的机制说明 | `docs/` | 索引注入，正文按需读 |

进项目的只有关于项目的记忆。关于某个人的偏好和协作方式留在用户级，不进共享仓库。
