## 1. 背景：为什么不在 Pigeon 上继续

Pigeon 是用户自己开发的 agent 编排平台：hub 在东京 s58700，node 在执行机上，前端是 Web。讨论的起点是新加的"隔离执行底座"引出的三个故障：

| 会话 | 现象 | 根因 |
|---|---|---|
| #2323 | 看起来是 websearch 不能用 | 实际上 WebSearch 是好的（它在 Anthropic 服务端执行）。坏的是 WebFetch：它在本机出网，而底座是 `--unshare-net` 完全断网；`network` 授权项只能开"固定主机+端口"的转发，给不了访问任意网站的能力 |
| #2322 | on-create hook 的 `bun install` 每轮都在重试 | 底座里 `GIT_DIR` 指向私有 Git 视图，于是 `git-dir == common-dir`，hook 把 worktree 误判成主检出，直接 `exit 0`，不写状态文件，平台就每轮重跑。即使跑到了，也会因为断网、HOME 是临时目录没有缓存而失败 |
| #2325 | 开启"以宿主身份执行"后，环境准备完就进 idle | 宿主模式下 CLI 使用 `HOME=/root`，加载了自带插件 `agents-md` 和 `telemetry`；执行环境对账（`reconcile.ts`）把它们当成"计划外插件"直接中止 |

这三个都没修（Pigeon 已冻结，#2325 可能值得修一下）。追下去发现，问题在更底层：

**底层前提错了：**
- **把对话当作业。** 72% 的主轨回合（2589/3615）是用户发消息触发的，每条消息却要按一次完整作业处理：hub 排队、认领、组装订单、node 准备现场、重启 CLI 进程、resume 几十万 token 的上下文。从消息发出到 CLI 启动：同机中位数 2.5 秒；境内 mac mini 中位数 7 秒，90 分位 66 秒。这些时间全部花在 CLI 启动之前，也就是派单和现场准备上：1b 实测重启 CLI 并 resume 约 1 MB 历史只要约 200 ms（§6）。Pigeon 的进程模型本身没有问题：回合进行中进程一直活着，排队消息可以折入正在跑的回合，回合结束且后台任务清空才关进程。
- **自研沙箱**，造出一个和宿主不一样的环境（断网、没缓存、临时 HOME），工具在里面到处出问题。
- **平台替代了上游能力**，例如关掉 Codex 原生的 goals 功能（`features.goals = false`），换成自研的检查轨。

**生长方式有问题：** 每遇到一个问题就加一个机制，代码多由 agent 快速写成。不到三个月（2026-07-03 起），产品代码 14.3 万行、测试 20.8 万行、Web 11.4 万行、文档 1.6 万行，1494 个提交；runner.md 一篇就有 1228 行。

**实际用法和设计不符（近 30 天数据）：**
- 只有 1 个用户；87% 的会话（739/853）在开发 Pigeon 本身。
- 最初的核心需求（微信收集需求）从未在生产上运行：相关六张表都是 0 行，2026-09-14 被删除（提交 `91d42323b`）。
- 目标判定轮 42% 失败；853 条会话里有 537 条本来就选了由人判定。
- hub 从没做过出网中转，node 一直直连 `api.anthropic.com`。
- 81% 的会话（693 条）跑在 s58700 上。

结论（**已决定**）：**冻结 Pigeon，在另一个文件夹里新开项目。** Pigeon 在新产品覆盖日常使用之前继续使用，只修阻塞问题。

## 2. 用户是谁、要什么

- 设计出身，对界面有自己的想法；**做界面是成就感的重要来源**。
- 以前不熟悉 PR 流程，一直是本地分支合并后推到 origin。
- 同时用 Claude Code 和 Codex，**因为单个订阅的额度不够**：Claude 额度用完就换 Codex 接着干，但两边的环境（skill 等）不一样，也不想为 Codex 重新熟悉一遍。
- 项目目录散落在多台机器上，自己也记不清在哪，每次都要手动 cd。
- agent 经常停下来问些没必要的问题，**大多是"要不要我继续做下一步"**。
- 想借这个项目学习 agent 的底层原理。
- 团队方向是真实的，成员基本都用苹果设备。

| 9 | 微信需求 → issue → agent → PR | 以后 |

### 可以请来试用的人

- 用户本人是第一用户，**自己用是主线**。用户的长期设想是做一个通用的 agent 工作平台，兼容各种人使用 agent 的需求。
- 可以请来试用的人：公司同事（运营、产品经理），以及做科研的同学。科研同学已经在用 Claude Code 写 LaTeX、写脚本分析实验数据。
- 约束：没有时间做旁观访谈，科研数据往往保密。皮振曾因数据保密拒绝试用 Pigeon，用户也拿不到他的 SSH 密钥去代部署。由此得到两条推论（**建议**）：「数据不出你的电脑」是卖点；安装必须由用户自己完成，不能依赖别人上门部署。

### 产品目的（**建议**，用户尚未确认）

上面的需求清单更像 Pigeon 的痛点修复单，不是产品目的。用 §17 的检验标准筛一遍：需求 1 到 6 都在上游的射程里，Claude 桌面 App 已有会话列表、Remote Control、iOS 端、diff 视图和回退；7 到 9 上游不会做。

网上调研的痛点强度（原文在 [research/](research/)；Reddit 全站抓不到，知乎小红书多数 403，科研人员的第一人称证据偏少，主力是 GitHub issue 和 HN）：

| 痛点 | 强度 | 代表证据 |
|---|---|---|
| agent 把文件弄坏了回不去 | 最强 | 整理医学 PDF 被 rm -rf 掉 7 GB（claude-code#46058）；Cowork 删 11 GB；工作树自动清理吞掉十天工作（#46444）；rewind 默认选项本身是破坏性的（#64615）。丢数据几乎都来自 Bash 的 rm/mv，而上游 rewind 不覆盖 Bash。写给科研人员的 Claude Code 指南第一条都是「先学 git 分支」 |
| 数据不能出机 | 强 | Yale 教授：「不能放 Dropbox 的就别给 Claude 看」；Stanford 集群文档警告 agent 会把数据发往云端 |
| agent 记不住规范 | 强 | 用户不是抱怨而是装模板：一套学术模板 2900+ fork，国内 academic-research-skills 1.2 万星 |
| 离开电脑用手机看进度 | 开发者很强，科研人员无一手证据 | 上游已免费内置 |

竞品调研的结论：最硬的空白是**文件夹级、不绑单一 agent、非程序员看得懂的版本历史和一键回退**。Cowork 没有任何回退，官方建议用户自己备份；Codex 的 Undo 有已知 bug；Claude Code 的 rewind 绑会话、不覆盖 Bash、30 天过期；Entire 和 GitButler 都要求 git 仓库、面向开发者。手机远程已被 Anthropic 和 OpenAI 免费内置，第三方远程工具里 Terragon、Vibe Kanban 已关闭，Omnara 已转型，不能当卖点。科研方向只有 Claude Science，偏生命科学、没有手机端。

- **目的：让不懂 git 的人也敢把文件夹交给 agent。** 三个支柱：随时回到任何一刻；数据不出电脑；agent 记住的东西看得见。这也是用户本人的需求，Pigeon 自研按工具调用打快照，就是因为被 Bash 改动咬过。
- **电梯宣言草案**：「把任何文件夹交给 Claude 改，改坏了随时回到任何一刻，数据不出你的电脑。」等第一位别人用过再修。
- **和「通用平台」的关系**：通用是终点的形态，不是起点的目的。和厂商比通用比不过，还会重演「每人一个需求就加一个机制」。通用靠 §10 的「不为每种人做特殊界面」，而不是为每种人加功能。第一阶段的筛选规则：**只做用户本人和科研同学都需要的东西**。项目总览、远程控制、回退、看文件和 diff、记忆可见，两边都要；PR 和 CI、跨厂商切换、自研 harness 只有用户本人要，往后放；微信入口、团队协作现在谁都不要。
- **风险**：Anthropic 给 Cowork 加版本历史的成本很低，已有用户在 issue 里要（claude-code#36542）。可守的位置：版本单位是文件夹而不是会话；底层是 git，可导出可审计；不绑单一 agent；数据不出机。这几点第一版就要成立。
- **反向指标**：Pigeon 有 87% 的会话在开发 Pigeon 本身。Kite 要盯「不是关于 Kite 的会话占比」，第一个月低于一半就是又掉进去了。

## 3. 已经做出的决定

1. **名称：Kite（风筝）**（用户命名）。寓意：人在地上握着线（手机、笔记本），风筝在远处飞（家里 mac mini 上的 agent）；线在手里，飞多远都不会丢，大部分时间它自己在飞。kite 也是一种鸟（鸢），延续了 Pigeon 的鸟类家族。曾考虑过 Dialog，放弃的原因：在界面设计术语里 dialog 指模态弹窗；命令行 `dialog` 也已被 Unix 的 dialog 工具和 swiftDialog 占用。命名建议（**建议**）：后台服务 `kited`（守护进程惯例；已停运的 Kite AI 补全工具的引擎也叫 kited，那个产品 2022 年已关闭，冲突风险低）；Bundle ID `com.<标识>.kite`；git 快照引用 `refs/kite/…`。**定位**：个人 agent 工作台。在 Mac 和 iPhone 上看到所有项目，用 agent 在上面工作。
2. **界面只做原生 App**：macOS 和 iOS 都用 SwiftUI，**不做 Web**（团队都用苹果设备）。
3. **三个组成部分**：App（Swift）、daemon（跑在工作机上，TypeScript/Bun）、服务器（跑在 edge 节点上）。daemon 用 TS，是因为 Claude Agent SDK 只有 TS 和 Python 版本；App 和 daemon 之间用从 schema 生成的契约连接（沿用 Pigeon 的做法）。
4. **机器分工**：mac mini（国内）是唯一的工作机；MacBook、iPhone 是客户端；edge 节点（境外，国内可以直连，延迟比 s58700 低，本来就是用户个人的 V2Ray VLESS 代理）承载全部基础设施；s58700 等新产品替代 Pigeon 后退掉。
5. **分阶段：第一阶段只接 Claude Code**；自研 harness 和 GPT 等 Claude Code 稳定之后再做。
6. **统一会话格式是"源语"**：界面和跨 runtime 切换都只经过自己定义的格式（见 §5）。
7. **服务器只记录和转发**：目录、会话存档、推送、账号、兜底中转。它不调度、不做判断，也不在实时对话的路径上。
8. **消息直达执行机，不再按轮派单**。App 的消息直接交给会话所在机器上的 kited；进程在跑就写进它的输入流，已关闭就本地 resume。现场只在建会话时准备一次。（原表述是「对话由常驻进程承载」，1b 之后看，重心在不派单，不在常驻，见 §6。）
9. **不限于代码**：项目是任意文件夹，Git 在底下隐形工作（见 §9）；会话记录不进项目文件夹（见 §11）；知识由 agent 边做边写进项目（见 §12）。
10. **每个会话一个工作树，完成后自动合并回主线**（2026-09-23）。流程形状和 Pigeon 一样，机械部分轻得多，见 §21。曾建议「默认在主文件夹直接改、工作树只作为可选草稿」，用户否决，理由是自己一定会并行多个改动。
11. **项目文件夹里尽量不放大文件**（2026-09-23）。图片、PDF、视频这类文件默认不进项目快照，将来放进资源库。用户的设想：mac mini 外接一块 1 TB 常驻硬盘做 NAS；一个项目关联一个资源库；内置一个 MCP 工具，让 agent 按需把资源库里的文件临时取到本地；资源库自己做二进制对象的去重和版本管理。见 §8。
12. **每个项目都是一个标准 git 仓库**（2026-09-23）。已有的仓库直接用；普通文件夹由 Kite 执行 `git init`，提交由 Kite 代做；放在 iCloud、Dropbox 等同步目录里的，仓库本体放到同步目录之外，文件夹里只留 `.git` 指针文件（`git init --separate-git-dir`）。只有一种模式，不再给普通文件夹建隐藏仓库。理由：会话工作树、合并、多机推送都需要带分支的正常仓库；历史留在项目里才不锁定；访达默认就不显示 `.git`。项目该长什么样见 项目规范（kite-onboard skill）。

## 4. 产品形态

```
 Mac / iPhone App（SwiftUI）
    │ 实时对话：组网直连          │ 总览、历史、通知
    ▼                            ▼
 kited（mac mini）   ─────────►  服务器（edge 节点）
  · 驱动 runtime                 · 目录：项目 / 机器 / 检出 / 会话
  · 检出管理、仓库发现            · 会话存档（原生 + 统一格式）
  · 原生记录 → 统一格式           · APNs 推送、账号
  · 事件流、git 快照、文件接口    · 兜底中转
```

**App**
- 只认统一格式，不解析任何 runtime 的原生格式。
- 可以用上的系统能力：实时活动 / 灵动岛（显示 agent 进度）、可直接回复的通知、分享扩展（从微信收需求）、Spotlight（搜项目）、Mac 菜单栏常驻、Handoff。
- 通过 TestFlight 分发，需要 Apple 开发者账号（每年 99 美元；推送和 TestFlight 都要求付费账号）。
- 团队账号可以考虑用"通过 Apple 登录"（**建议**）。

**daemon（第一阶段只需要支持 macOS，由 launchd 托管）**
- 通过 Agent SDK 驱动 Claude Code：回合和后台任务期间进程常驻，结束即关，下一条消息到来时 resume（§6）。
- 检出放在统一路径 `~/code/<域名>/<owner>/<repo>`（ghq 约定，**建议**）；扫描家目录发现散落的仓库，可以一键登记或迁移。
- 把原生记录转换成统一格式，翻译器放在 daemon 里：上游改格式时只改 daemon，不用重新发 App。
- 环境同步：一份源（AGENTS.md、skills/、MCP 清单）分发到各 runtime 的原生位置。
- 负责 git 快照和只读文件接口（见 §7、§8）。

**网络**
- 主路：headscale 组网，国内点对点直连（国内家宽和手机网络大多有 IPv6，直连成功率较高）。用户手机平时不开代理 App。
- 兜底：经服务器中转。手机开着代理 App 时会用到，因为 iOS 同时只能有一个 VPN。
- headscale、DERP 中继、服务器都放在 edge 节点上。
- mac mini 的 V2Ray 规则：`100.64.0.0/10` 和 edge 节点地址走 DIRECT。
- mac mini 设置：关闭自动睡眠、打开"断电后自动启动"。

## 5. 核心设计：统一会话格式（源语）

**用户已认可**：以自己的格式作为源语。设计要点：

1. 会话由若干"**段**"组成，每一段由一个 runtime 执行；切换 runtime 就是开始新的一段。
2. **原生记录原样存档**（Claude jsonl，以后还有 Codex rollout），作为该段的原始事实；统一格式由翻译器从原生记录生成，翻译器改进后可以重新生成。自研 harness 的段，统一格式本身就是原始记录。（这一点是在起草时补充的，**用户还没明确确认**。）
3. **只追加、不修改**：内容块（text、tool_use、tool_result、thinking……）按顺序追加。这样能保住提示缓存，同步增量也简单。
4. **用 parent 指针串成树**，支持回退和分叉。
5. **系统提示和工具列表不存进会话**，发请求时由 runtime 现场生成。
6. **界面可以直接渲染**，自研 harness 也可以直接拿它续跑。
7. 正在进行中那一轮的逐字输出走实时事件流；内容块完成后以记录为准。
8. 第一阶段只需要"jsonl → 统一格式"这一个方向，但**格式本身要按多 runtime 来设计**。

**为什么不另存一份归一化事件**：Pigeon 在数据库里存了一份自己归一化的事件（`run_events`），它不能用来续跑，于是换窗和切换 runtime 时只能编译成 16 KB 以内的文本塞给新会话。正确的做法是"存原始事实、派生视图"。

**跨 runtime 切换（第二阶段）**：原生记录 → 统一格式 → 目标 runtime 的输入。推理内容（thinking 签名、加密 reasoning）和提示缓存无法跨厂商迁移，这是已知的损失。

**普查：翻译器要覆盖什么（1c，2026-09-23）**

样本是本机 `~/.claude/projects`：88 个有内容的主会话（另有 364 个空文件，是桌面端远程会话留下的空壳）、49 个子 agent 记录、3 个老格式子 agent 记录，共 3.7 万条、86 MB，版本 2.1.222 到 2.1.280。本机没有的压缩、分叉、后台任务、打断，用 1b 的假端点在 2.1.280 上制造出来补齐。完整报告在 [research/2026-09-23-transcript-census.md](research/2026-09-23-transcript-census.md)，脚本是 `spikes/transcripts/census.ts` 和 `spikes/sdk/synth.ts`。s58700 上的会话（占 81%）没有普查。

一个会话在磁盘上是这些东西：

| 东西 | 位置 | 翻译时怎么处理 |
|---|---|---|
| 主记录 | `<会话 id>.jsonl` | 翻译的主体 |
| 子 agent 记录 | `<会话 id>/subagents/agent-<id>.jsonl`，另有同名 json 元数据（agent 类型、描述、发起它的 tool_use id、嵌套深度） | 挂到主记录里发起它的那次工具调用下面 |
| 外置的大工具输出 | `<会话 id>/tool-results/*.txt` | 工具结果的正文可能在这里，不在 jsonl 里 |
| 老格式子 agent 记录 | 项目目录下的 `agent-<id>.jsonl` | 同子 agent 记录 |

主记录里的记录分两类。**链上记录**带 `uuid` 和 `parentUuid`，构成对话本身：

- **assistant**：一条 API 回复按内容块拆成多条记录，14707 条记录对应 6515 个 `message.id`，同一个 id 最多 23 条。翻译时按 `message.id` 合并。块类型有 text、thinking、tool_use；thinking 带签名，占主记录 16 MB，只有同一模型能用。另有 `isApiErrorMessage` 标记的错误消息。
- **user**：大多数是工具结果，5497 条。工具结果在 `message.content` 里有一份，在 `toolUseResult` 里还有一份结构化输出，两者重复，分别占 10 MB 和 12 MB。其余是人发的消息，以及系统塞进来的消息：后台任务通知、钩子注入的 `<system-reminder>` 文本、本地命令输出、中断标记、`isMeta` 消息、压缩摘要。**分辨人发的还是系统塞的，没有单一可靠的字段**：`origin` 能标出 `human` 和 `task-notification`，但有 132 条人发的消息 `origin` 为空，SDK 发的消息也为空。要组合 `origin`、`promptSource`、`turnOrigin`、`isMeta`、`isCompactSummary` 和正文开头的标签来判断。Kite 自己驱动的会话不用猜：kited 投递人发的消息时带上 `origin: {kind: 'human'}`，第 2 步实测会原样写进记录；Kite 自己发的（如合并冲突的说明）不带。
- **attachment**：27 种，大多是请求时才渲染成上下文的注入：环境、日期、模型身份、技能和 agent 和工具清单、剩余 token 提醒、回合中插话（`queued_command`）、钩子上下文、编辑过的文件、指令文件、系统提示快照等。对话视图只关心插话；其余是能力视图（§13）的数据来源。
- **system**：`stop_hook_summary`（Stop 钩子运行结果）、`compact_boundary`（压缩）。

**链外记录**不带 `uuid`，是界面和进程状态：标题（`custom-title`、`ai-title`）、`agent-name`、`last-prompt`（带 `leafUuid`，指向当前叶子）、`mode`、`queue-operation`（插话队列的入队、出队、被回合吸收）、`cost-state`、`bridge-session`、`atis-latch`，以及 Claude Code 自己的文件检查点（`file-history-snapshot`、`file-history-delta`）。统一格式不需要它们，标题可以取来用。

链的形状：
- **每个文件只有一个根。** 压缩是例外：压缩后从一个新根开始，新根是 `compact_boundary`，用 `logicalParentUuid` 接回压缩前的最后一条，后面跟一条 `isCompactSummary` 的摘要消息。
- **分叉点很多，但几乎都不是回退。** 462 个分叉点里，373 个是并行工具调用（第二个 tool_use 和第一个工具结果挂在同一个父节点下），86 个是钩子上下文与工具结果并列，真正的对话分叉只有 3 个。所以「当前对话」不能靠找唯一的子链，要从叶子往回走；`last-prompt` 的 `leafUuid` 可能就是 Claude Code 用的叶子，没有核实。
- **分叉出的新会话不记来源。** `forkSession` 会把分叉点之前的历史整段复制进新文件，全部换成新的会话 id，没有任何字段指回原会话。会话之间的血缘只能由 Kite 自己记在统一格式里（「段」的 parent）。

几种运行时事件在记录里的样子：
- **后台任务**完成时，一条正文为 `<task-notification>…` 的用户消息经队列进入，开启新的一轮。记录类型和人发的消息相同，只能靠 `origin` 或正文开头区分。
- **打断**（`interrupt()`）50 ms 内结束回合，result 为 `error_during_execution`。正在跑的工具记成被用户拒绝的 tool_result，后面补一段「[Request interrupted by user for tool use]」，和下一条人发的消息并在同一条用户消息里。
- **SDK 消息流**里出现过：assistant、user、result、`system` 的 init、status、compact_boundary、task_started、task_updated、task_notification、background_tasks_changed。`session_state_changed` 一次都没出现，可能需要额外开启。

## 6. 对话模型

- **进程生命周期（建议）**：沿用 Pigeon 的收口判据。回合进行中进程一直活着，新消息写进它的输入流，插话靠这个。回合结束后看 Stop hook 输入里的两份清单：在途后台任务（`background_tasks`）和稍后会唤醒本会话的定时任务（`session_crons`），两份都空才关闭输入流，让进程退出；清单读不到不当空处理。依据是官方 hooks 文档「Stop input」一节：两份清单用来区分「会话结束」和「会话暂停、等后台工作唤醒」，任务注册表可达时才出现，没有在途或已排程的工作时为空数组。Pigeon `docs/runner.md` 就是按这一节实现的。kited 用 SDK 的进程内 hook 回调读这两份清单，不需要钩子脚本文件。另有两个信号不能单独当收口判据：`background_tasks_changed` 消息（官方 TypeScript 参考，Claude Code 2.1.203 起）每次后台任务集合变化推一份完整清单，但不含定时任务，只适合做界面上的后台活动提示；`session_state_changed` 消息的 idle 状态只写在 SDK 类型定义里，网页文档没有，是否考虑定时任务也没说明。关闭后下一条消息到来时本地 resume。进程崩溃或机器重启等同于关闭。不另设空闲超时：resume 只要约 200 ms，多留进程换来的好处很小。
- **三个层级**：一次模型调用（一个请求、一个回复）→ 一个**回合**（从用户发消息让 agent 开工，到它停下来）→ 一个会话。
- **回合进行中的插话（已实测）**：不会开启新回合，而是先进入队列，等工具执行完、下一次调用模型之前，作为 system 消息插在 tool_result 后面，内容是：`The user sent a new message while you were working:\n<原文>\n\nThis is how Claude Code surfaces messages the user sends mid-turn...`。在 jsonl 里它是一条 `queued_command` 附件（带 uuid，在链上），另有队列操作记录（`enqueue`，以及原因为 `absorbed_mid_turn` 的 `remove`）。如果送达时回合已经结束，它就单独开启新回合。
- **"要不要继续"类停顿**：在 AGENTS.md 里写一行"目标没完成之前不要询问是否继续"，再加一个 Stop hook 兜底。**不做**检查轨或目标判定轨。

**实测（1b，2026-09-23）**

方法同 §16：本机假端点驱动 Agent SDK 0.3.280 自带的 Claude Code 2.1.280，隔离了用户设置（`settingSources: []`、临时 `CLAUDE_CONFIG_DIR` 和 HOME）。脚本在 `spikes/sdk/`：`fake-api.ts` 是假端点，`run.ts` 是七个实验。为模拟长对话，假端点每次回复附带 2 万个字符，50 轮后请求体约 1 MB。

| 实验 | 测量 | 结果 |
|---|---|---|
| 常驻多轮 | 50 轮后仍是同一个进程 | 是 |
| 常驻多轮 | 投递延迟（消息进入输入流到请求发出），前 10 轮 / 后 10 轮中位数 | 5 ms / 6 ms，最大 24 ms |
| 常驻多轮 | 请求体 第 1 轮 → 第 50 轮 | 54 KB → 1021 KB |
| 常驻多轮 | 进程内存 第 1 轮 → 第 50 轮 | 218 MB → 339 MB |
| 冷启动 | 新会话：创建到第一次请求 | 228 ms 和 799 ms（两次运行，波动大） |
| 休眠唤醒 | 关闭输入流后进程退出 | 11 ms，退出码 0 |
| 休眠唤醒 | resume 约 1 MB 历史，到第一次请求（3 次中位数） | 183 ms |
| 休眠唤醒 | 唤醒后 system、tools、历史前缀与休眠前一致 | 一致 |
| 空闲被杀 | SIGKILL 后 SDK 的表现 | 迭代器抛错「Claude Code process terminated by signal SIGKILL」 |
| 空闲被杀 | 再 resume，历史前缀一致 | 一致 |
| 回合中被杀 | 工具执行到一半 SIGKILL，再 resume | 能接上 |
| 回合中插话 | 默认优先级：何时送达 | 等当前工具跑完才送达，插话后约 2 秒，1 个 result |
| 回合中插话 | `priority: 'now'`：何时送达 | 同样等工具跑完，不会打断 |
| 工作树 | 会话记录目录 | 按工作树路径命名 |
| 工作树 | 删掉工作树后，从主文件夹 resume | 能恢复，历史完整 |

结论：
- **常驻进程模型成立。** 一个进程能承载多轮，投递延迟几毫秒，历史长到 1 MB 也不变。
- **resume 不破坏缓存。** 唤醒和被杀后重建的请求，与常驻进程下一轮会发的请求一致：system 和 tools 逐字节相同，历史前缀内容相同。唯一的字面差异是上一轮最后一条剩余 token 提醒：带缓存标记时写成文本块数组，标记挪走后退回字符串。这在正常运行的相邻两轮之间同样存在，不是恢复特有的。
- **进程模型和 Pigeon 没有本质区别。** Pigeon 回合进行中同样保持进程，也能把排队消息折入正在跑的回合：Claude 经 SDK 输入流，Codex 经 `turn/steer`；它的探针测到推入后 9 到 14 ms 被接收，与本次的 5 到 6 ms 同一量级。Kite 的区别在消息到达进程之前：没有派单流水线，现场不每轮准备。
- **不需要空闲常驻。** 唤醒约 200 ms，全新会话的冷启动在 0.2 到 0.8 秒之间，相比模型本身的秒级延迟可以忽略；每个进程却要占 200 到 350 MB，mac mini 有 16 GB。所以回合和后台任务结束就关。注意这里测的是不加载任何设置、插件、MCP 的最小启动，真实配置下的唤醒时间没测。
- **被杀等同休眠。** kited 看到迭代器抛错，就把会话标成休眠，下一条消息到来时 resume。
- **回合中被杀，Claude Code 会自己补一段中断记录。** resume 后的请求末尾依次是：一个报错的 tool_result「[Request interrupted by user for tool use]」加一句「Continue from where you left off.」，一条合成的助手消息「No response requested.」，然后才是新消息。被杀那条命令已经造成的文件改动还在，由快照兜底。
- **插话不会打断正在跑的工具。** 默认优先级下，插话包装成 system 消息「The user sent a new message while you were working」，放在 tool_result 后面，和上面已记录的行为一致。`priority: 'now'` 也不打断，只是不再包装，直接作为文本块并进 tool_result 所在的那条用户消息。真要打断得调 `interrupt()`，1c 测过：50 ms 内结束回合，见 §5。
- **会话记录不随工作树消失。** 删掉工作树后，从主文件夹用会话 id 照样能 resume。但历史里留着「这是一个 git 工作树，不要 cd 到原仓库根目录」这句环境说明，换目录恢复后它就过时了。
- **版本锁定是免费的。** SDK 包自带对应版本的 Claude Code 原生程序，kited 锁定 SDK 版本就锁定了 Claude Code 版本，也就锁定了会话记录格式。这正是 §20 里「翻译器要锁定版本」需要的。

## 7. Checkpoint 与回退

**上游现状（Claude Code 2.1.280 / Agent SDK 0.3.280，查过官方文档）：**
- 代码回退：`enableFileCheckpointing: true` 加 `query.rewindFiles(用户消息uuid, {dryRun})`。需要 `extraArgs: {'replay-user-messages': null}` 才能在流里拿到用户消息的 uuid。每次用户发消息开启回合时打一个 checkpoint。
- 对话回退：`resume` 加 `resumeSessionAt: <任意链上记录的 uuid>`，保留到这条记录为止（含这条）；加 `forkSession: true` 就分叉出新会话，原会话不动。
- **限制**：Bash 的修改不追踪（`rm`、`mv`、`sed -i`、格式化、代码生成、安装依赖都回退不了），只追踪 Write、Edit、NotebookEdit；subagent 的修改基本不追踪；新建、移动、删除目录不撤销；软链接和硬链接会跳过；快照约 30 天后清理；每个会话最多保留 100 个 checkpoint；回合中插进来的消息没有 checkpoint；**只对 Claude Code 有效**。
- 正是因为不追踪 Bash，Pigeon 当初才自研了一套：每次工具调用后把整个工作树固化成 git 树，外加改动统计和链外 blob 存储。它能覆盖 Bash，但太重。

**实测：用 `resumeSessionAt` 回退到插话前后**
- 指向插话前的 tool_result：插话和它之后 agent 的回复都干净地消失，新消息直接接在 tool_result 后面。**可以精确撤回插话。**
- 指向插话记录（`queued_command`）本身：插话保留，之后的回复被去掉；但有一个怪癖，重建时插话被放到新消息**后面**，而且仍然带着"工作时用户发来的新消息"这层包装。
- Claude Code 的 `/rewind` 界面只列出开启回合的消息，做不到这一点。这是 SDK 能做、界面没开放的能力。

**参照物（2026-09-23 查证）：**
- **VS Code 时间轴**是两个数据源叠在一起：Git 提交历史，加上与 Git 无关的「本地历史」。本地历史在每次经编辑器保存时把整个文件复制一份，存在项目外的 `~/Library/Application Support/Code/User/History/<路径哈希>/`，另有索引记录时间和来源标签（重命名、撤销、全局替换等）。用户本机有 371 个文件、2501 条、36 MB，好几个文件已顶到每文件 50 条的默认上限，更早的版本已丢。它的边界：只记经编辑器保存的改动（按官方文档，终端、脚本、agent 的 Bash 都不进时间轴，未实测）；单位是单个文件，没法整体回到某一刻；全量复制，所以必须设上限。JetBrains 的本地历史思路相同，并且会记录外部改动。
- **Pigeon 的实现**已经是 git 对象库方案，见 `src/dbfree/siteCheckpoint.ts` 和 `src/dbfree/git.ts` 里的工作树状态追踪器。核心几条命令：用临时索引（`GIT_INDEX_FILE`）→ `read-tree HEAD` → `add -u` → 添加未被忽略的未跟踪文件 → `write-tree` → `commit-tree`，父节点是上一枚快照，HEAD 前移时另挂 HEAD → 带比较并交换的 `update-ref refs/pigeon/site/<会话>`。回退是 `read-tree -u --reset`、`clean -fdq`、`reset --mixed` 三条。合并进行中（有 MERGE_HEAD）时不打新快照。重量都在外围：打包归档 168 行、按版本读 154 行、回收流程 960 行，外加数据库账本。根源是快照住在远程执行机的临时工作树里，中心又不持有仓库。Kite 全在本机，没有这个问题，快照部分预计一两百行。

**设计（建议）：**
- 由 daemon 打 git 快照，挂在 `refs/kite/snapshots/<会话>`（第 2 步从 `refs/kite/<会话>` 改过来：会话分支叫 `kite/<会话>`，git 解析短名时 `refs/<名字>` 排在分支前面，按分支名操作会拿到快照）。捕获流程和 Pigeon 相同，只有一处不同：**每个会话保留一个私有索引，不每次新建临时索引**。私有索引记着文件的修改时间，下次只需逐个检查，不必重读所有文件算哈希；实测快 4 到 30 倍（见下方实测）。捕获就是私有索引上的 `add -A` 加 `write-tree`，树没变就复用上一枚，不产生新提交。Bash 的修改和未跟踪的新文件都能记录（遵守 `.gitignore`），不碰用户自己的暂存区和分支，而且**和 runtime 无关**，第二阶段照样能用。
- 内容相同的文件只存一份，不需要 VS Code 那种条数上限。但引用会让对象永不回收，需要保留期限。
- 快照永远存进项目自己的仓库（§3 第 12 条）。普通文件夹先由 Kite 初始化成标准仓库，不另建隐藏仓库。
- **每批工具调用完成时打快照**（PostToolBatch 钩子；第 2 步从 PostToolUse 改过来：PostToolUse 在并行调用时会并发触发，几次捕获抢同一个私有索引，PostToolBatch 在一批调用全部结束、下一次调用模型之前只触发一次）。回合结束再打一次，收进后台任务在工具之外写的文件。会话开始时先打一枚「会话开始」，回退到「agent 动手之前」才有落点。实测一次捕获在一两百毫秒以内，工具调用本身通常要几秒，成本不是障碍。工具完成时工作树是稳定的；收到消息的那一刻命令可能还在执行，快照不一致，所以不在收到消息时打。没有写文件的工具调用不会产生新提交。回合是界面上的默认粒度，工具级快照用于回退到回合中间。以后可以加文件系统监听，记下 agent 之外的改动（JetBrains 的做法）；实测对五万文件的目录 fsmonitor 没有带来提速，暂不需要。
- **首次登记大文件夹**要读全部文件：五万个小文件用了 18.6 秒。放到后台做并显示进度，做完立刻打包（`git repack`），否则每个小文件一个松散对象，对象库会膨胀到 200 MB。
- 回退代码：把工作树恢复成快照那棵树（包括删掉之后新建的文件），**只动文件，不动用户的 HEAD 和分支**（Pigeon 回退会把 HEAD 拨回去，对代码仓库的用户是意外副作用）；也支持只恢复单个文件。回退对话：用 `resumeSessionAt` 加 `forkSession`。App 里提供和上游一样的三个选项：代码和对话一起回退、只回退对话、只回退代码。
- 每个版本带一句人话标签，就是触发这一回合的用户消息。比「文件已保存」有用得多。
- checkpoint 作为统一格式里的一条记录，指向快照 commit。
- 每个会话的快照链在它自己的工作树里（§21），回退一个会话不会撤掉另一个会话的改动。
- 已知边界：被 ignore 的文件（`node_modules`、`.env`）不在快照里。
- **大文件类型默认不进快照**（§3 第 11 条）。图片、PDF 这类已压缩的文件 git 压不动，收进来快照就约等于再存一份：185 MB 的科研式文件夹，首次快照后对象库 155 MB，之后每改一张 3 MB 的图多 3.4 MB。Kite 初始化的仓库，`.gitignore` 默认排除位图、PDF、视频、音频、压缩包和镜像、设计源文件、二进制数据格式；矢量图（svg）和 Office 文档照常进快照，它们是正文的一部分。模板见 项目规范（kite-onboard skill），只写小写扩展名，靠 macOS 上 git 默认的 `core.ignorecase=true` 挡住大写（已实测）。排除之后同一个文件夹：首次快照 0.9 秒，对象库 19.5 MB，gc 后 10.8 MB；一个回合增长 0.4 MB。代码仓库按它自己的 `.gitignore`，Kite 不改；已跟踪的二进制文件本来就在仓库里，不额外占空间。
- **代价是被排除的文件不受快照保护**，而调研里被引用最多的事故正是 agent 删掉了 7 GB 的 PDF。保护由资源库补上（§8）。另一个后果：被忽略的文件不会出现在会话的工作树里，散落在项目各处的图片和 PDF，agent 在会话里看不到，LaTeX 也编译不了。所以大文件必须集中到资源库，项目里只放一个指向它的链接。

**实测（1a，2026-09-23，mac mini M4，文件缓存是热的）**

原型在 `spikes/snapshot/`（普通文件夹场景是按当时的隐藏仓库方案测的，机制相同，数字同样适用于 Kite 初始化的标准仓库）：`snap.ts` 是捕获和回退，`verify.ts` 是回退语义的 25 项检查，`bench.ts` 是性能测试。

| 场景 | 规模 | 首次快照 | 无改动，私有索引 | 无改动，每次新建索引 | 一个回合后快照 | 整体回退 |
|---|---|---|---|---|---|---|
| Pigeon 仓库 | 2913 个跟踪文件，装了 node_modules | 218 ms | 59 ms | 219 ms | 118 ms，26 个文件变化 | 190 ms |
| 科研式普通文件夹（排除大文件之前，排除后见上） | 2320 个文件，185 MB，含默认忽略的 .venv | 3.3 s | 40 ms | 412 ms | 144 ms，19 个文件变化 | 373 ms |
| 五万个小文件的普通文件夹 | 50000 个文件 | 18.6 s | 112 ms | 3.3 s | 207 ms，109 个文件变化 | 478 ms |

参照：Pigeon 仓库上 `git status` 是 24 ms。

回退语义全部通过：Bash 的 `rm -rf` 和 `mv` 都能撤回；之后新建的文件和空目录会被删掉；被忽略的文件不动；用户的 HEAD、分支、暂存区逐条不变；快照里的父节点会挂上 agent 自己做的提交；单文件恢复可用，快照里没有的文件会被删掉；回退前自动存一枚，所以回退本身可以撤销；`.DS_Store` 默认忽略，中文带空格的文件名和二进制文件都正常。

整体回退的做法：先捕获当前状态，此时私有索引就等于「现在」；再在私有索引上执行 `read-tree --reset -u <目标>`。现在有而目标没有的文件被删，被忽略的文件因为不在索引里所以不碰。这比 Pigeon 的 `read-tree` 加 `clean -fdq` 加 `reset --mixed` 少两步，而且不动 HEAD。

没测到的：冷缓存（开机后第一次）、捕获过程中 agent 同时在写、合并进行中的仓库、子模块、大小写改名（APFS 默认不区分大小写）、单个 GB 级文件。

## 8. 文件管理（建议）

- **随手翻 mac mini 上的文件**：用系统功能，不开发。mac mini 打开"文件共享"（SMB）；iPhone 在"文件" App 里选"连接服务器"，输入 `smb://<组网设备名>`；MacBook 在访达里挂载。需要整个桌面时用"屏幕共享"。都走组网。
- **在会话里看文件**：daemon 提供**只读**文件接口，范围限定在已登记的项目里：列目录、读文件、和某个 checkpoint 做 diff。App 负责呈现：项目文件树、agent 改过的文件、diff、Markdown 和图片预览。编辑先不做。

### 资源库（NAS）

**已决定方向**（§3 第 11 条）：大文件放资源库，不放项目文件夹。资源库、MCP 工具、去重和版本管理是用户设想的未来形态，下面是**建议**。

- **物理形态**：mac mini 外接 1 TB 常驻硬盘，格式化为 APFS，用系统的「文件共享」（SMB）经组网给 iPhone、MacBook 浏览，不开发。
- **存储不用 git，用按原字节存放的内容寻址库。** 结构是 `blobs/<SHA-256>` 加版本清单（路径到哈希的映射）。资源库里用户看到的文件，是库里对象的 APFS 克隆，和对象共用磁盘块。2026-09-23 实测：256 MB 的文件克隆进库，可用空间减少 0 MB；再从库里克隆出一个副本，还是 0 MB；算一遍 SHA-256 用 525 ms。所以当前版本不额外占空间，只有旧版本占空间，内容相同的文件天然只存一份。克隆只在同一个 APFS 卷内有效。
- **为什么不用 git**：同一套快照原型当资源库用也能工作（`bench.ts` 的资源库场景，1 GB 媒体文件）：首次入库 6.8 秒；复制一个 128 MB 视频、整个目录改名都不增长；换一张 3 MB 照片增长 3.0 MB；删掉的视频能整体回退找回。但 git 对象带头部和封装，和原文件不是逐字节相同，不能克隆共享，每份内容都要存两遍，1 TB 的盘只能装约 500 GB 资源。
- **先查上游**：git-annex 的 thin 模式用硬链接做类似的事（未核实）。硬链接在原地修改文件时会连带改坏历史版本，克隆没有这个问题。
- **保护**：资源库只追加。agent 删除一个文件只是把它从当前清单里去掉，历史版本还在。这补上了大文件不进项目快照留下的缺口。
- **访问**：mac mini 本机直接按路径读，不需要 MCP。项目里放一个指向资源库对应目录的链接，链接本身进 git，每个会话的工作树自动带上。Claude Code 的沙箱默认只允许在工作目录里写，所以 agent 经链接只能读、删不掉（**待验证**）。MCP 工具在别的机器或同事要取文件时才需要：按需下载到本地临时缓存，写回时新增一个版本。
- **未定**：资源盘自身的备份，盘坏了会全部丢失，需要第二份副本；旧版本的保留期限；排除清单的边界，比如 Keynote 文件可能很大、几 GB 的 CSV 按类型挡不住，是否再加一个大小阈值。

## 9. 项目的概念：任意文件夹，Git 隐形（**已决定**方向）

用户的想法：Kite 不只服务写代码。比如运营同事开一个项目，里面一行代码都不写，只放自己的零碎脚本、相关资产和资料，以及 agent 的记忆。**Git 虽然出自编程，但在这种项目管理场景里正好可以普及，只是使用者根本不需要知道 Git 在帮他做什么。** Git 也是多机协作、远程仓库的基础。

**为什么是现在**：过去普通人用不了 Git，主要卡在两点：心智模型太难（commit、branch、merge），冲突太难处理。现在 agent 可以替他提交、写说明、用大白话解释历史，也能可靠地解决冲突。

**参照物**：Figma 的版本历史和分支。设计师每天都在用"自动保存、命名版本、分支、合并"，却不需要懂背后的原理。

| 用户看到的 | 背后的 Git |
|---|---|
| 自动保存点，可以回到任意一刻 | 每个回合一个快照（§7） |
| 给这个版本起个名字 | tag |
| 一次对话在"草稿"上改，满意了再"采纳" | 会话分支 / worktree，合并 |
| 换一台机器接着用；团队共享 | push / pull，远程仓库 |
| 请同事看一下 | PR |
| 冲突 | agent 自动解决；解决不了时让用户在两个版本中选一个 |

**要提前想好的坑（建议）**：
- 大文件（设计稿、视频）Git 处理得很差。已定为放在项目之外的资源库，仓库里只存链接，不用 Git LFS（§8）。
- Word、Excel、图片这类文件没法逐行合并，冲突时只能二选一或两个都留，界面要为此专门设计。
- 非技术用户的脚本里很可能直接写着密钥：同步前要自动扫描，常见的敏感文件默认忽略。
- 托管位置：GitHub 从国内访问不稳定，可以在 edge 节点上自建 Forgejo 或 Gitea（国内可直连），或者用国内平台。**未定**。

**同类产品对照**（2026-09 调研）：

| | 做什么 | 面向谁 |
|---|---|---|
| Entire（GitHub 前 CEO Thomas Dohmke 2026 年 2 月创办，种子轮 6000 万美元） | 开源 CLI Checkpoints：每次提交时把 agent 的完整会话（对话记录、提示、改动文件、工具调用、token 用量）直接存进 Git，再用界面展示；目标是 agent 与人协作的开发者平台 | 开发者 |
| 腾讯 CNB | 代码托管 + 云端开发环境 + AI 代码助手和评审 | 开发者 |
| AtomGit | 代码、模型、数据集、智能体的一站式平台 | 开发者、AI 从业者 |
| **Kite** | Git 隐形化，任何文件夹都是项目；跑在自己的机器上；手机跨境控制；设计师做的原生界面；以后支持跨 runtime 切换 | 不一定懂技术的个人和小团队 |

## 10. 界面不分 Chat / Cowork / Code 模式（建议）

- Claude 桌面 App 目前分三个 tab。**Chat**：云端对话，你每轮掌舵，碰不到本地文件。**Cowork**：把多步骤任务交出去，在本机沙箱虚拟机里操作指定的文件夹，有连接器、浏览器、电脑操作、定时任务。**Code**：就是 Claude Code，面向代码仓库、终端、git，有 diff 视图。
- 本质区别：**模型相同，harness 不同**，也就是系统提示、工具、运行环境、界面侧重点不同。
- 2026-09-20 前后，Claude 下载页出现横幅"Claude Cowork is now just Claude"，正向 Pro 和 Max 推送：Chat 和 Cowork 的界线正在消失。
- 对 Kite 的启示：**只有一种对话界面，按项目的性质显示不同的能力。** 任何文件夹都能开会话；如果是 git 仓库（Kite 的项目默认都是），代码相关的部分（diff、checkpoint、PR）在需要时出现。

## 11. 会话记录不进项目文件夹（**已决定**）

用户的原则：项目文件夹里只放**持久化的知识**（代码、代码注释、文档、agent 的 memory）；会话过程只是为了得到产物的瞬时过程，本身价值不大。

**数据支持**（拆了一条 4.2 MB 的真实会话记录）：JSON 结构和元数据 55%，思考（基本是只有同一模型能读的加密签名）16.7%，工具结果 11.5%（大多是仓库已有内容的副本或一次性输出），附件 9.7%，助手文字 3.3%，工具调用参数 3.1%，**用户说的话 0.6%**。有长期价值的"为什么"只占不到 4%。

**放进项目的坏处**：噪音（非技术用户看到一堆看不懂的东西）、体积（每个协作者 clone 都要带上）、泄密（工具结果里常混进密钥和个人内容，进了 Git 历史很难删）、误导（旧会话描述的代码状态早已不存在，agent 读了会被带偏）、格式不稳定。

**三层（已决定）**：

| 层 | 内容 | 放在哪里 |
|---|---|---|
| 项目知识 | 代码、文档、AGENTS.md、memory、决策记录 | 项目文件夹（Git），长期保存 |
| 会话记录 | 完整原生记录和统一格式 | Kite 服务器，默认只有本人可见，设保留期限；续跑、切换、回退、界面历史都靠它 |
| 提炼 | 从会话中抽出有长期价值的部分，写进项目知识 | 见 §12，由 agent 边做边写 |

追溯（**建议**）：提交里加一行 `Kite-Session: <id>`。会话还在保留期内时可以一键跳回去看过程；过期之后，提炼出来的东西依然在项目里。这样能以很小的代价得到 Entire 那种追溯能力。

## 12. 知识架构：边做边写（**已决定**做法，细节为**建议**）

**用户现有的做法**：提炼不是会话结束后的一道工序，而是写进系统提示词，要求 agent 在执行过程中边做边写，写进每个项目统一的分层知识架构。Pigeon 的分层：

| 知识类型 | 归宿 | 加载方式 |
|---|---|---|
| 值得带到以后会话的单条事实 | `memory/`，一事一文件，加一个索引 | 索引每轮加载，正文按需读 |
| 始终适用的项目约定 | instructions（在 Kite 里就是 AGENTS.md） | 每轮加载 |
| 只在碰到特定文件时才适用的约定 | rules，用 `paths:` 限定路径 | 碰到对应路径时注入 |
| 完整的机制说明（推导、边界情况、证据） | `docs/` | 每轮注入索引，正文按需读 |

核心原则（Pigeon 系统提示词原文的意思）：**每类知识只有一个归宿；写下的内容是无状态的**，只写系统现在如何运作、为什么，从不写"工作做到哪了"；仓库已有的（代码结构、修过的 bug、git 历史）不重复记；一条知识所依据的证据（在哪个版本上测的、为什么放弃别的方案）属于知识本身；发现过时就立刻更新或删除，不留近似重复。

**上游已经有原生对应（2026-09 查官方文档）**：
- instructions 对应 AGENTS.md / CLAUDE.md（读取条件见 §13）。
- rules 对应 `.claude/rules/*.md`，同样用 `paths:` 限定路径。
- memory 对应 **auto memory**：一事一文件，`MEMORY.md` 做索引，每轮加载前 200 行或 25 KB，按类型分类（user、feedback、project、reference）。**但默认只存在本机**（`~/.claude/projects/<项目>/memory/`），不跨机器。
- docs 索引注入：上游没有，需要自己补。

**Kite 的做法（建议）**：
- 知识架构不做成子系统，而是一些约定加几行配置。
- 把 `autoMemoryDirectory` 设到项目文件夹里（例如 `.kite/memory/`），memory 就跟着 Git 走，换机器、团队共享都能用。这是补上上游唯一缺口的关键设置。
- 在系统提示词后面追加一小段（SDK preset 加 append），写明上面的原则，再加上 docs 索引（或者用会话启动时运行的 hook 注入）。
- **团队场景要区分个人记忆和项目记忆**：user、feedback 两类是关于某一个人的（偏好、协作方式），不该进共享仓库；project、reference 两类才进项目。上游的 `autoMemoryDirectory` 只能指向一个目录，这个拆分要在追加的提示词里交代。
- **面向非技术用户要更简单，也要看得见**：运营同事的项目大概率只需要 AGENTS.md 加 memory。界面上做一个"**Kite 记住了什么**"：每条记忆用大白话列出，可以查看、修改、删除（Claude Code 只弹一句"Saved 2 memories"）。让用户看见 agent 学到了什么，是建立信任的关键，也是设计的发挥空间。

## 13. 环境统一（建议）

- 指令：**AGENTS.md** 作为唯一的源（用户指出，除了 Claude Code 用 CLAUDE.md，其他 agent 都已经统一成 AGENTS.md）。Claude Code 从 v2.1.277 起，在没有 CLAUDE.md 时会直接读取 AGENTS.md；但官方文档写明，在关闭遥测等情况下读不到。daemon 如果设置了 `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` 就可能踩中，所以稳妥的做法是：放一个 CLAUDE.md，里面写一行 `@AGENTS.md`。
- Skill：SKILL.md 格式，两边通用；Codex 的目录位置**待验证**。
- MCP：一份清单，生成两种配置格式（JSON 和 TOML）。
- Hook：两边的事件模型不同，尽量少用。
- 用一个小的同步脚本分发到各自的原生位置，这样不管从哪里用（产品里、终端里），环境都一样。
- Pigeon 的 AEC（五层解析、合并代数、启动时对账）不要照搬。#2325 就是 AEC 对账引起的。

**能力视图：替代 AEC 的「看见」（建议，2026-09-23）**
- AEC 的初衷是「看见」：上游的 skill、rule、memory、工作树、preview 这些能力会在项目文件夹里长成什么样，没有一个统一的地方看。AEC 用「统一」去解决它：自己的格式、五层解析、合并、启动时对账。结果变成又一套要学的东西，用户后来也没真正看过项目配置，对账还和上游对不齐。配置是预测，用户关心的是实际发生了什么。
- Kite 不拥有配置，只读配置。分两个视图：
  - **项目里长了什么**：扫描上游原生位置，用大白话列出指令文件、规则、技能、记忆、设置里的钩子和权限、工作树的复制和软链接配置、MCP 清单。每项写清楚做什么、何时生效、是人写的还是 agent 写的。要改就打开原文件或让 agent 改，Kite 不发明格式。
  - **这次会话实际加载了什么**：从会话记录读，不推算。用户本机 455 条 jsonl 的附件类型里有 `instructions`（加载的指令文件和类型，如 User、AutoMem）、`skill_listing`、`agent_listing_delta`、`deferred_tools_delta`、`mcp_instructions_delta`、`hook_additional_context`、`environment`（含是否在工作树里）、`edited_text_file`（包括 agent 写进记忆目录的文件）。这是「存原始事实、派生视图」的又一次应用。
- 呈现在用户会看的地方，不做设置页：会话开头一行「加载了 2 条指令、14 条记忆、6 个技能」，点开是明细；agent 写了新记忆或规则，在时间线上显示成一个事件。和 §12 的「Kite 记住了什么」是同一个东西，范围扩大到所有上游能力。
- 「统一」那一半，也就是上面的同步脚本，留到第二阶段：只复制，不解析、不合并、不对账。
- **数据够不够（1c 已查清）**：够，前提是 Claude Code 不低于 2.1.280。`instructions` 附件是 2.1.280 才有的：这个版本的每个会话开头都记一次，内容是加载的指令文件路径、类型（User、AutoMem 等）和全文，文件变化时再记一次（`reason: session_start`、`changed: true`）；2.1.258 的 53 个会话一条都没有。`prompt_snapshot` 从 2.1.266 起出现，会话开头记两次，第二次带完整工具列表，内容是完整的系统提示分段。技能、agent、工具清单（含 MCP 服务器的待连接、需授权、连接失败状态）每个会话开头都有。kited 锁定 SDK 版本，就锁定了这些数据。

## 14. 交付（建议）

- 用 PR 代替 Pigeon 自研的交付流水线。对应关系：交付候选对应 PR；review 轨对应 PR 评审；验证门对应 CI 必过检查；集成队列对应合并队列加 squash；人工审批对应分支保护。
- 多机时怎么集成见 §21：不需要集成队列，git 推送自带比较并交换。
- Pigeon 检查轨里真正有价值的三样东西：独立的上下文、不同的模型、交付前的自动关卡。它们应该分别变成：agent 可以调用的能力（subagent、审查 skill）、用另一个模型审 PR、CI。不再是会话状态机里的阶段。

## 16. 从实验里学到的 Claude Code 内部机制

方法：在本机起一个假的 `/v1/messages` 端点，把 `ANTHROPIC_BASE_URL` 指过去，用预设的回复驱动真实的 Claude Code，不调用模型、不消耗额度（脚本附后）。

- **API 没有状态**：每次请求都把 system、tools 和全部 messages 重发一遍。不只是续跑时，同一会话里每一轮都是如此。
- **请求结构**（Claude Code 2.1.280，`claude -p`）：`model`、`max_tokens: 64000`、`stream: true`、`thinking: {type: adaptive, display: omitted}`、`output_config: {effort: high}`、`context_management`（clear_thinking）、`metadata`、`system`（3 块，约 9,300 字符，后两块带 `cache_control`）、`tools`（20 个，JSON 共 46,709 字符，约一万多 token，比系统提示还大；最大的几个是 SendMessage、Workflow、ScheduleWakeup、Cron 系列）、`messages`。另有 9 个 beta 功能头。
- **环境信息**以对话中间的 system 消息形式出现（`# Environment ...`），剩余 token 数这类动态信息总是放在末尾，以保住缓存前缀。
- **回复**：SSE 流式事件；`stop_reason` 为 `tool_use` 时，harness 执行工具，然后把 `tool_result` 以 user 身份送回。
- **第二轮请求**：system 和 tools 和第一轮逐字节相同，messages 只在末尾追加。
- **jsonl 会话记录**：每行一条事件，有 `uuid` 和 `parentUuid` 构成的树；附件（环境、模型身份、skill 列表、日期、token 提醒）在请求时才渲染成 system 消息；`prompt_snapshot` 只做记录，不发给模型；此外还有费用统计、队列操作等记录。
- **resume**：读取 jsonl，沿链重建 messages；system 和 tools 现场生成；重建出的前缀和上一次请求**逐字节相同**，所以续跑时能命中缓存。
- **Agent SDK 不指定 `systemPrompt` 时，只发一段 135 字符的极简系统提示**，没有 Claude Code 的行为说明、git 状态、自动记忆段落；要 `systemPrompt: {type: 'preset', preset: 'claude_code'}` 才和裸跑 Claude Code 一样（第 2 步用真实订阅实测：不加预设时会话里没有记忆，加了之后记忆段落出现，且指向 `autoMemoryDirectory` 设的目录）。1b 的实验用的是 SDK 默认提示，结论只涉及进程和缓存，不受影响。
- **修正一个早先的判断**：原生 Claude Code 的工具定义确实很重（约一万多 token），用户"Claude Code 太重"的感觉有道理。Pigeon 数据里的 3.5k，是因为 Pigeon 已经裁掉了一部分工具。但这部分每轮都不变，能命中缓存，按缓存价（约十分之一）计费。

## 17. 讨论中形成的设计原则

- **上游优先，只做薄层**：工具、沙箱、压缩、subagent、goal、审查、checkpoint，上游能做的就用上游的。检验标准：上游发布了同样的功能时，我们是删代码，而不是跟它竞争。
- **数据用原生格式，不锁定**：AGENTS.md、SKILL.md、git 仓库。不用这个产品，一切照样能用。
- **存原始事实，派生视图**。
- **后端要小，界面要自由**：后端的复杂度不应该渗透到界面上。
- **加机制之前先问三个问题**：上游有没有？一个约定能不能解决？几行指令能不能解决？
- **看见靠读记录，不靠拥有配置**（§13）。
- **通用靠不做特殊界面，不靠为每种人加功能**（§2）。

## 21. 会话工作树与集成

**已决定**：每个会话跑在自己的 git 工作树上，完成后自动合并回主线。这就是普通的 git 工作流。Kite 的价值在于流程里没有一步需要人动手：自动执行，agent 解决冲突，每回合快照（git 之上唯一新加的机制），说人话（草稿、采纳、回到下午三点），加上不丢东西的规则。

**生命周期（建议）**
- **位置**：放在项目文件夹外，由 Kite 管理。用户在访达里看到的永远是主文件夹；会话中的改动在 App 里看，采纳后才出现在主文件夹，也就是 Figma 分支的语义。普通文件夹由 Kite 初始化成标准仓库后，走同一套流程。
- **起点**：有远程时先拉取，从最新的主线建工作树。起点越新，冲突越少。
- **带过去被忽略的文件**：复用 Claude Code 的原生格式（在 2.1.217 的程序里核实存在）。`.worktreeinclude` 列出要复制的文件，如 `.env`；设置里的 `worktree.symlinkDirectories` 列出要从主仓库软链接的目录；另有 `worktree.sparsePaths` 做稀疏检出。项目配一次，在 Kite 里和裸跑 Claude Code 效果一样。上游还有 `WorktreeCreate` 钩子，但它是**接管创建**：脚本自己建目录并打印路径，不打印就报错。它不是建后初始化。
- **初始化脚本**：上游没有建后初始化的钩子，所以保留一个项目脚本约定，相当于 Pigeon 的 on-create.sh。吸取 #2322 的教训：Kite 用环境变量告诉脚本主仓库在哪，脚本不自己判断身份；Kite 自己记录初始化是否成功，脚本只用退出码报结果，不写状态文件；不做沙箱，脚本在有网络、有全局缓存的真实环境里跑。只在建工作树时跑一次，agent 开工前跑完。
- **依赖目录不需要机制**。2026-09-23 在 mac mini 上实测（bun 1.3.14，Pigeon 仓库，跳过 postinstall）：

  | 工作树 | 安装用时 | du 显示的 node_modules | 可用空间实际减少 |
  |---|---|---|---|
  | 第一棵 | 1 秒 | 926 MB | 约 12 MB |
  | 第二棵 | 1 秒 | 926 MB | 约 0 |

  bun 在 macOS 上默认用 APFS 写时复制克隆，数据块共用一份。所以每个工作树直接装，不软链接 `node_modules`：省不了空间，还会让依赖不同的分支互相改坏。软链接只留给数据集、缓存这类只读的大目录。未测：postinstall 编译出的原生模块（真实写入）、npm 和 pip（整份复制）、uv 和 pnpm（应当也是克隆或硬链接）、构建和测试产物。
  另：Pigeon 并没有解决依赖目录重复的问题。on-create 至今每个工作树跑一次 `bun install`；2026-09-03 s58700 磁盘满之后，加的是低水位抢占、备份保留和回收纪律；8 月那次「按 git 树共享」共享的是类型检查缓存和测试耗时。s58700 上每棵 1.3 GB 是否真占盘没有核实，bun 在 Linux 上默认硬链接。
- **采纳（合并）**：本机按项目加一把锁，多个会话依次合。主文件夹可能被人直接改过却没提交，非技术用户会直接在主文件夹改 Word，所以合并前先把主文件夹存成一个版本。冲突交给这个会话的 agent；Word、图片这类没法逐行合并的，让用户在两个版本里选一个。
- **在哪里合并**（第 2 步定下）：先在会话工作树里提交全部改动，再把主线合进会话分支，最后主文件夹快进。冲突因此只出现在会话工作树里，交给 agent 解决，它这一轮结束后 Kite 自动重试；主文件夹永远不会处于冲突状态。
- **采纳之后会话照常可用**（第 2 步定下）：采纳后会话分支等于主线，可以接着改、再采纳，不必每次开新会话。所以采纳不删工作树，删目录挪到归档。
- **删除（归档）**：没合并的永不自动删，手动归档也要显式确认；删之前先打快照；删目录和会话分支，但保留快照引用，会话过程可以找回。Claude Code 工作树自动清理吞掉十天工作（#46444）这类事故，在 Kite 里不会发生。

**检查与排队（建议，2026-09-23）**
- 代码项目提供 `.kite/check`（见项目规范，kite-onboard skill）：类型检查加受影响的测试，加 `--all` 跑全量；只用退出码报告成败，输出只报结论、失败项和超预算项，完整日志写文件。受影响的测试从 `KITE_BASE` 起算改动，没有就看还没提交的改动。合回主线前跑全量；是否由 Kite 在采纳时自动跑，未定。
- 做成 Kite 给会话的工具 `check`（2026-09-23 改定；原先不做，理由是 Pigeon 做成工具是为了躲开自研沙箱的内存上限，Kite 没有这个上限）。现在的理由：在 Bash 里跑只看还没提交的改动，agent 自己提交过的改动会漏测，工具由 Kite 给 `KITE_BASE`（会话分支和主线的分叉点）；结果发成事件，App 能直接显示；以后按内存放行也加在这一层。调的还是 `.kite/check`，契约不变。实现是 SDK 的进程内工具，用 Pigeon 用过的 `CLAUDE_AGENT_SDK_MCP_NO_PREFIX=1` 去掉 `mcp__` 前缀。什么时候该用写在工具说明里，AGENTS.md 不再提。
- 测试怎么写放在项目的 test-writer 子 agent 定义里（`.claude/agents/test-writer.md`），项目规范（kite-onboard skill）里附模板；AGENTS.md 只写「改完跑检查、测试交给 test-writer」两句。主 agent 写实现，test-writer 照需求并行写测试，看不到实现，写完一起跑检查；规则只在写测试时加载。不放平台系统提示：系统提示每个会话都带，改了已开的会话收不到，项目文件里看不见，离开 Kite 就没了。
- 排队：Pigeon 的 Check 串行跑检查，一个长测试会堵住后面零点几秒就能跑完的检查（队头阻塞）。Kite 的做法是轻的不排队，类型检查和小测试随到随跑；重的一层按座位排队，座位数按机器内存定，mac mini 16 GB 先定 2 到 3 个，一个长测试只占一个座位。座位用锁文件实现，放在检查命令自己身上，这样 Kite 发起的和 agent 在 Bash 里自己跑的走同一套座位。以后还堵，就按每个检查上次实测的峰值内存放行。不做插队和抢占：插队解决不了前面那个正在跑，抢占会白费已经跑的时间。一个检查要跑几分钟是测试规范要管的事，不靠调度解决。

**多机集成（建议）**
- 远程仓库本身就是集成点。git 推送自带比较并交换：远程只接受基于它当前版本的推送。两台机器同时推，后到的被拒，不会互相覆盖。
- 每台机器的流程：开会话前拉取 → 会话完成后在本机合进本机主线（本机锁）→ 推送 → 被拒就拉下来重合再推。冲突由刚做完的那个会话的 agent 解决，因为只有它知道自己改了什么、为什么改。
- Pigeon 需要集成队列，真正的原因是合并前要跑几分钟的验收，期间主线可能前移，队列保证「验过的就是合进去的」。Kite 以后要在合并前强制跑 CI，就用托管平台自带的合并队列。
- 前提是有共享远程，机器之间不直接互推。代码仓库用它原来的远程；普通文件夹由 Kite 在 edge 节点上建远程，也就是 §9 未定的托管问题，多机场景让它成了前提。
- 第一阶段只有 mac mini 一台工作机，只用得到本机锁。

**不带过来的 Pigeon 机制**：集成队列、验收门、审查轨、中心归档、回收栅栏。

## 附：实验脚本

- `capture.ts`：假的 `/v1/messages` 端点。第一轮回复一个调用 Read 的 tool_use，第二轮回复结束，同时记录每条请求。
- `capture-delay.ts`：同上，但第一轮延迟 5 秒，用来测回合中的插话。
- `resume-at.ts`：用 SDK 的 `resumeSessionAt` 加 `forkSession`，从会话中间某个点分叉续跑。

运行方式：先 `bun capture.ts <输出目录> <目标文件>` 拿到端口，然后用最小环境运行 claude。注意：root 用户不能用 bypassPermissions，改用 `--allowedTools Read`。

```bash
env -i HOME=<临时目录> PATH=/usr/bin:/bin:$HOME/.local/bin CLAUDE_CONFIG_DIR=<临时目录> ANTHROPIC_BASE_URL=http://127.0.0.1:<端口> ANTHROPIC_API_KEY=sk-fake CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1 claude -p "<提示>" --allowedTools Read
```
