# Kite 产品架构（当前整理）

更新时间：2026-09-28

这份文档整理当前已经对齐的产品形态和下一阶段架构方向。它描述产品概念，不等同于当前代码已经全部实现；实现进度以代码、`kited/README.md` 和 [会话显示协议](会话显示协议.md) 为准。

## 1. 当前进度

Kite 已经完成第一轮可用闭环：

- 自研 harness 位于 `kited/src/harness/`，首个模型入口使用 ChatGPT 订阅；
- 新建会话默认使用 harness，支持工具调用、会话记录、恢复、打断和继续；
- kited 已接通工作树、快照、回退、采纳和归档；

- 工作机身份随数据库持久保存，检出通过 `machineId` 归属机器；App 保存连接地址与选中机器，请求携带目标 ID；
- 登记目录可新建项目，也可显式关联已有项目；同一项目在本机或不同工作机上可拥有多个检出；

- agent 已纳入插件实例，窗口统一引用 instanceId + viewId；添加和关闭跨端同步，两端分别保存布局；
- 当前 App 与 kited 主要仍是本机连接，文件窗口、终端窗口、版本时间线和完整工作区操作尚未完成。

下一阶段从“单个会话可用”转向“完整工作区可用”。

## 2. 目标产品形态

Kite 是一个个人 agent 工作台。用户在 Mac 或 iPhone 上看到工作机上的项目，打开一个工作区，在里面同时查看工作线程、文件、终端、diff、快照和插件窗口。

核心流程是：

1. 选择项目、检出和工作区；
2. 在工作区创建 agent 插件实例，或打开已有实例的会话窗口；
3. agent 在工作树中工作，Kite 持续保存快照；
4. 用户查看对话、工具调用、文件变化和检查结果；
5. 用户回退、继续、采纳或归档工作区。

**暂定核心承诺：** 让 agent 自己推进，把真正重要的决定留给你；每个决定都有证据，每一步都能回看。

## 3. 对象层级

命名统一：插件定义 `PluginDefinition` 创建工作区内的 `PluginInstance`，agent 也是一种插件。每个 agent 实例拥有一个持久会话 `Thread`，由 `ThreadRunner` 驱动；关闭 Runner 后仍可恢复同一会话。`AgentDefinition` 是 agent 插件的专有配置，不另建 Agent 持久表。上游 SDK 的 session 字段保留上游原名，自有产品模型使用 Thread。

```text
项目
└── 检出（machineId + 根目录）
    └── 工作区（cwd / 工作树）
        ├── 插件实例
        │   ├── agent 实例 → Thread / journal / Runner
        │   ├── agent 实例 → Thread / journal / Runner
        │   └── 终端、待办等实例 → 各自的业务数据与资源
        └── 共享窗口集合 → instanceId + viewId
            ├── Mac 布局与焦点
            └── iPhone 布局与焦点
```

### 工作机

`Machine` 表示拥有项目检出和执行现场的 kited 服务，保存稳定 UUID、名称和创建时间。身份属于 `KITE_HOME` 内的数据库：重启和地址变化不影响身份，新数据目录产生新身份。网络地址是 App 的连接记录，可以变化；每个检出通过 `machineId` 引用机器。当前 App 可保存并切换多台机器，一次连接一台。远程认证、组网和服务端存档尚未接通。

### 项目

逻辑上的项目，可以是 Git 仓库，也可以是普通文件夹。ID 使用独立 UUID；不同目录同名不会自动合并为一个项目。登记检出时可提供完整项目身份 `{id, name, createdAt}`，让本机或另一台工作机使用同一个项目 ID；已有身份的元数据冲突会被拒绝。

App 在连接记录中缓存各机器返回的项目身份，供登记时选择；每台 kited 独立保存本机检出和工作区。关联只建立项目身份关系，文件、Git 仓库和执行记录仍在各自工作机上。

### 检出

某台机器上的具体目录，包含机器、根路径和根仓库状态。项目只有一个检出时，界面可以隐藏这一层；隐藏只是显示规则，数据模型仍保留。

点击检出时，可以直接进入根工作区。

### 工作区

工作区是长期存在的工作容器：

- 一个 cwd；
- 一个工作树和分支；
- 一组窗口；
- 多个同级插件实例，包括拥有 Thread 的 agent 实例；
- 工作区级线程调度、事件广播和状态快照。

根检出本身可以作为根工作区。普通工作区通常对应 Kite 管理的独立工作树。

工作区和插件实例解耦：删除或归档一个 agent 实例及其会话，不自动删除工作区；删除工作区才会删除其工作树和分支；删除根工作区属于删除这台机器上的检出，需要单独的高风险操作。

工作区可以让多个线程共享同一个 cwd，也可以为线程提供隔离工作树。共享工作区适合探索、审查和小范围协作；需要独立回退、长时间修改或任意 shell 操作时，线程可以使用隔离工作区。

## 4. 插件实例、工作线程和窗口

PluginInstance 统一保存实例身份、工作区归属、定义引用、标题、配置与持久生命周期。Thread 是 agent 专有数据，不重复保存这些共有字段。

同一个 agent 定义可以创建多个实例，每个实例对应一个 Thread，保留自己的 journal、历史、执行与恢复状态。终端实例持有 PTY，待办实例持有任务数据，各自使用相应的业务状态。系统插件和自定义插件共用定义、实例、操作及窗口契约。

所有窗口统一引用 `instanceId + viewId`。agent 默认提供一个 conversation 视图，对应 0 或 1 个独立会话窗口；内嵌和后台 agent 可以不占用窗口。其他插件按定义提供 0 到多个视图，例如同一个待办实例提供 board 和 list。打开已有视图默认聚焦原窗口，创建新实例是另一个动作。窗口关闭后仍保留实例、Thread 和业务数据。

一个工作区允许多个线程同时运行。只读工具和可以安全合并的 `patch` 可以并行；补丁匹配失败时，工具把冲突交回发起线程重新读取和生成。删除是按调用时的路径执行，创建要求目标不存在。工作区事件在修改完成后广播，供其他线程更新状态和上下文，不负责替代工具本身的匹配或合并语义。

### Agent、线程和窗口

Agent 是具有会话和模型执行能力的插件实例。父线程创建 agent 时记录来源实例、来源回合和任务因果关系，因果关系不作为侧边栏的父子层级。外部操作使用 instanceId 定位 agent，不额外维护 agentId；Thread 的原生运行时 ID 保留在专有数据中。

Agent 的默认呈现或展示请求通过 `presentation` 声明，设备上的具体布局单独保存：

```text
presentation: window | inline | background
```

- `window`：显示为工作区中的独立窗口；
- `inline`：折叠显示在发起它的 agent 窗口内；
- `background`：不占独立窗口，在父线程、工作区活动栏和通知中显示状态。

隐藏只影响呈现，不改变工具权限。agent 需要用户输入时，要把状态送回父线程或提升为可见窗口。一次任务结束后释放执行资源，默认保留实例、配置和 Thread，后续继续对话。归档和删除由显式操作管理；执行阶段、上一回合结果、恢复阻塞和 Runner 生命周期沿用 [会话状态机](会话状态机.md)，不能只看 idle 判断能否恢复。

协作工具是插件操作的模型入口。以下是目标接口示意，具体参数以实施时的 schema 为准：

```text
agent.start   { definitionId, task, presentation, workspaceMode, operationId }
agent.list    { workspaceId, status, capability }
agent.send    { instanceId, input }
agent.resume  { instanceId }
agent.stop    { instanceId, operationId }
```

`agent.start` 适配实例创建，建立 agent 实例与其 Thread，记录来源与启动上下文。`agent.list` 从实例目录筛选 agent，返回实例 ID、定义、状态、能力和任务摘要。新任务通过 send 投递；resume 显式推进等待继续的会话；recovery 的确认仍是独立操作。服务端检查能力并避免同一 Thread 重复启动。

UI 停止按钮和其他 agent 的 `agent.stop` 调用，均经过宿主校验与授权，映射到现有 Thread 服务的 interrupt。停止操作 ID 沿用原停止收据，尚未纳入请求的输入按现有规则退回草稿。模型不会因为某操作存在就自动获得调用权限。

## 5. Agent 插件定义

agent 插件通过稳定的 PluginDefinition 引用登记，AgentDefinition 保存其中的专有配置，包括：

- 一个或多个上下文编排定义；
- 可用工具；
- 模型和推理设置；
- 输出和回合结束约定；
- 执行预算；
- 默认的窗口呈现和工作区模式。

上下文部分直接复用现有的 `ContextDefinition`、`ContextBinding` 和场景契约。核心场景可以扩展为 `agent.start`、`agent.resume` 和 `agent.event`，由宿主提供 `agent.*`、`workspace.*` 和受限的 `plugin.*` 变量。上下文组装器只负责校验、展开和保存快照，不负责创建 agent、调度线程或监听事件。

定义可以抽象成：

```text
PluginDefinition
└── AgentDefinition
    ├── ContextDefinition[]
    ├── tool capabilities
    ├── model settings
    ├── output and turn completion
    ├── presentation defaults
    └── workspace mode
```

例如 `explorer` 可以声明只读工具和 `inline` 呈现；测试员可以声明 `background` 呈现，由工作区变化事件触发新建或恢复会话。两者任务结束后都保留会话，供后续继续。

初步类型包括：

- `coding`：修改文件、执行命令、完成用户任务；
- `review`：读取当前变化并审查问题；
- `test`：运行检查并汇报结果；
- `research`：整理项目资料和外部材料。

待办面板属于普通插件；若需要模型整理待办，再创建调用待办操作的 agent 实例。

用户和其他 agent 通过同一个定义创建实例，共享上下文、工具和回合结束约定；subagent 只表示创建来源。实例保存生效配置，journal 的请求快照记录当次定义和值；历史快照不成为另一份可变配置源。触发器单独声明事件与动作，不进入上下文组装器。

## 6. 触发器和并行运行

触发器负责判断什么时候创建或恢复哪个 agent 会话；上下文组装器只负责准备该线程运行时的材料。工作区不再持有一个把所有线程排成单列的执行槽。

触发器由事件、条件和动作组成：

```text
事件：coding 回合完成
条件：工作区稳定、存在 diff、没有排队输入
动作：启动 `review` agent
```

条件读取工作区的结构化状态，不执行任意 JavaScript。每次触发记录条件判断时的状态快照、来源、时间和目标线程，避免重复触发或形成循环。

并行执行的边界由工具和工作区操作定义：

- `read`、搜索和只读分析可以并行；
- `patch` 在当前内容上匹配和应用，互不冲突的修改可以并存，匹配失败就是工具失败；
- `create_file`、`delete_file` 按调用时的目标执行；同一目标的先后顺序由实际操作顺序决定；
- 任意 `shell`、回退、采纳、合并和归档等无法由 patch 语义约束的操作，由工作区服务单独排队或放入隔离工作树；
- 快照和状态事件在操作完成后记录并广播，事件用于通知和重新组装上下文，不作为文件合并机制。

多个线程可以通过 `agent.list` 查询已有 agent 实例及其会话状态。对同一实例并发调用 `agent.resume` 时，由宿主检查运行状态并保证只启动一次执行。

“工作区干净”需要拆成几个状态，避免和 Git 的 clean 混淆：

- `executionIdle`：没有线程正在运行；
- `runningThreads`：正在运行的线程及其状态；
- `pendingAgents`：等待启动、输入或资源的 agent；
- `workspaceStable`：工具、快照和收尾已完成；
- `diffExists`：存在待审查改动；
- `gitClean`：没有未提交改动。

例如 review 通常依赖 `workspaceStable && diffExists`，不应把 `gitClean` 当成审查条件。

## 7. 工作区公共上下文

工作区状态可以成为上下文编排契约中的只读公共变量。它们不是操作系统的 `process.env`，而是宿主在请求或触发器判断前生成的结构化快照。

候选变量包括：

```text
workspace.id
workspace.cwd
workspace.branch
workspace.base
workspace.execution
workspace.diff.exists
workspace.diff.files
workspace.diff.summary
workspace.check.status
workspace.latestSnapshot
workspace.pendingInputs
```

规则如下：

1. 宿主负责读取 Git、文件和检查状态；
2. 组装器负责校验变量、选择分支和展开文本；
3. 每次模型请求固定一份变量快照；
4. 定义、绑定值和来源一起写入 journal；
5. 历史查看使用旧快照，不重新读取当前工作区；
6. 文件清单、摘要等小材料可以直接注入上下文；
7. 完整 diff 等大材料优先通过工具按需读取；
8. agent 启动、恢复和事件请求使用对应场景，插件启动状态通过受限的 `plugin.*` 绑定提供。

这条方向延续现有 `ContextBinding` 和 `contextScenes`，新增 `agent.*`、`workspace.*` 和按 manifest 声明的 `plugin.*` 命名空间即可，不另造一套变量系统。上下文编排器不监听文件变化，也不负责启动线程；这些仍由工作区宿主、事件广播和触发器负责。

## 8. 插件

插件是工作区中的统一产品概念，agent、文件、终端、待办均使用它。插件定义可以声明：

- 零到多个视图，由宿主打开为窗口；
- 有输入、输出 schema 的实例操作，分别声明是否供 UI、模型或内部逻辑调用；
- stdio 或远程 MCP 服务；
- 工作区配置和状态；
- 可选的 AgentDefinition；
- 上下文提供者、状态订阅或触发器。

插件实例属于工作区；定义引用、配置和持久业务数据保存在工作机。窗口集合由 kited 保存，各设备保存自己的布局。项目级配置可以放在 `.kite/<pluginName>/`，公共配置和实例运行状态分开保存。

### 系统插件

内置 agent、终端和文件系统登记到同一插件目录。内置身份由宿主认定，实现可直接适配核心服务；自定义 manifest 不能通过声明系统身份获得额外权限。

```text
工作区核心服务
├── FileSystemService
├── TerminalService
├── Git / SnapshotService
├── Thread 服务 / Runner
└── WorkspaceStateService

内置插件
├── AgentPlugin
├── FilesPlugin
└── TerminalPlugin
```

文件系统需要统一提供文件查看、编辑、diff、版本变化和预览；终端需要统一提供 PTY、输入输出、窗口尺寸、信号、进程组和后台任务。

agent 的 `read`、`patch`、`shell` 与文件窗口、终端窗口共用这些底层服务，不能各自实现一套文件或进程语义。

### 公开插件

自定义插件首批需要能写界面和业务逻辑，并调用已授权的工作区能力，包括修改状态或调用其他 agent。定义、实例、操作、视图和权限契约与内置插件相同；原生内置视图与自定义 UI 可以采用不同实现。

宿主校验调用方、目标实例、工作区和操作权限。插件声明需要的变量与能力，不默认获得任意路径、shell、环境变量或模型认证信息。agent.stop 等语义明确的操作可以同时供 UI 与模型调用，界面专用操作不必出现在模型工具列表里。

状态订阅先读取快照，再接后续事件。Agent 的执行阶段、回合结果、恢复阻塞和操作能力直接投影现有 Thread 事实；不再预设 agent.ready、waiting_input 等另一套状态。终端与待办保留各自的有类型状态。

自定义 Web 界面优先评估 MCP Apps，工作机代码的执行隔离方式仍待验证。完整对象、操作、权限与运行位置契约见 [Agent 与插件契约](Agent与插件契约.md)。

## 9. 界面布局

左侧按项目—检出—工作区组织。检出只有一个时省略该层。进入工作区后：

- 中央区域显示展开的窗口；
- agent 与其他插件的视图可以并列存在；
- 内嵌 agent 以可折叠块显示在发起线程内；
- 后台 agent 在工作区活动栏显示运行、完成、失败和需要输入；
- agent 可以从内嵌或后台状态提升为独立窗口；
- 窗口可以拖到右侧停靠栏；
- 拖动过程中显示跟随鼠标的圆形预览；
- 停靠栏保存窗口顺序、位置、展开状态和焦点。

Mac 右侧停靠栏收纳当前工作区缩小成圆的窗口，可拖回内容区或点击恢复。iPhone 对应底部折叠窗口栏：始终只有一个窗口展开，切换时原窗口折叠回栏中。

会话窗口 header 固定显示“代理”，工作区标题和项目关系在导航层表达。

工作区在各端拥有同一组窗口，窗口集合、稳定 ID 和目标引用由 kited 保存，添加与关闭跨端同步。分栏、尺寸、停靠顺序、当前展开项和焦点由各设备分别管理；iPhone 切换窗口不改变 Mac 的布局。关闭窗口保留绑定的插件实例及 Thread 等专有数据，停止执行与删除业务对象使用各自操作。共享窗口集合与 instanceId + viewId 目标引用已经接通；宿主校验实例归属与定义声明的视图。

## 10. 当前实现到目标架构的映射

| 目标概念 | 当前实现 | 后续工作 |
|---|---|---|
| 工作机 | 稳定 `Machine` 身份、`/machine`、App 连接记录与目标检查 | 远程认证、组网、多机目录汇总 |
| 项目 / 检出 | `projects.ts`、`store.ts`、`/checkouts`，支持显式关联同一项目的多个检出 | App 中补齐检出状态和操作 |
| 工作区 | `model.ts`、`store.ts`、`/workspaces`，登记检出建立 root 工作区，独立创建 worktree 工作区 | App 补齐回退、采纳和归档操作 |
| 插件实例 | PluginInstance 统一持有 agent 与其他插件的共有字段，Thread 仅保存专有字段 | 实例操作、授权与自定义插件加载 |
| 工作线程 | `/threads/:id` 和 ThreadRunner，同一工作区可建立多个独立 coding Thread | 作为 agent 实例的专有数据；接入工具层并行调度，当前同 cwd 执行互斥 |
| PluginDefinition / AgentDefinition | 内置定义目录与视图声明已接通，agent 配置目前仅选择默认 runtime | 上下文、工具与模型配置接入定义和请求快照 |
| Agent 协作工具 | 尚未实现 | 创建、列出、恢复会话、提升窗口和停止执行 |
| 窗口组 | kited 保存 WorkspaceWindow，统一实例与视图引用；App 本机持久化布局 | 接入实际插件内容与内嵌呈现 |
| 上下文变量 | `contextScenes`、`ContextBinding` | 增加 `agent.*`、`workspace.*` 和受限 `plugin.*` |
| 快照 / diff | `snapshots.ts`、Git 工作树 | App 版本时间线和文件变化视图 |
| 文件系统 | harness 文件工具 | 系统 FilesPlugin 和共享服务 |
| 终端 | harness `shell` 工具 | 系统 TerminalPlugin、PTY 和后台进程 |
| 触发器 | 尚未实现 | 工作区事件、条件和 agent 生命周期 |
| 公开插件 | 尚未实现 | 按统一定义、实例和操作契约接通界面、逻辑与工作区能力 |

## 11. 当前不提前做的事

- 不把所有插件强行压成同一个底层协议；
- 不把上下文组装器变成事件监听器或调度器；
- 不让事件广播替代 patch 匹配、工具错误和工作区操作边界；
- 不让任意 shell 绕过工作区服务直接获得并行修改保证；
- 不先做任意脚本化触发器；
- 不在没有实际插件需求前建立复杂的通用插件市场或远程加载系统。

## 12. 下一阶段建议

1. 在已统一的 PluginInstance 和窗口目标上完善实例操作及授权；
2. 完善内置 coding 定义配置，让 AgentDefinition 接入现有上下文编排；
3. 以实例操作适配现有 Thread 服务，接通 agent 创建、列出、发送、停止和继续；
4. 做 FilesPlugin 或 TerminalPlugin 的真实业务闭环，让 UI 与 agent 经过同一工作区服务；
5. 用待办插件验证自定义界面、工作机逻辑、持久状态与 agent 工具调用；
6. 继续补齐跨线程并行、内嵌与后台呈现、diff 和快照操作，再按实际需求增加触发器。

具体接口与验证顺序以 [Agent 与插件契约](Agent与插件契约.md) 为准。在研期间直接调整协议和存储，不为当前未部署模型增加兼容层。
