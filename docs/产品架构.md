# Kite 产品架构（当前整理）

更新时间：2026-09-27

这份文档整理当前已经对齐的产品形态和下一阶段架构方向。它描述产品概念，不等同于当前代码已经全部实现；实现进度以代码、`kited/README.md` 和 [会话显示协议](会话显示协议.md) 为准。

下一阶段从“单个会话可用”转向“完整工作区可用”。

## 2. 目标产品形态

Kite 是一个个人 agent 工作台。用户在 Mac 或 iPhone 上看到工作机上的项目，打开一个工作区，在里面同时查看工作线程、文件、终端、diff、快照和插件窗口。

核心流程是：

1. 选择项目、检出和工作区；
2. 在工作区添加或打开一个工作线程；
3. agent 在工作树中工作，Kite 持续保存快照；
4. 用户查看对话、工具调用、文件变化和检查结果；
5. 用户回退、继续、采纳或归档工作区。

产品的核心承诺是：用户可以把文件夹交给 agent，同时随时知道发生了什么，并能回到之前的状态。

## 3. 对象层级

```text
项目
└── 检出（机器 + 根目录）
    └── 工作区（cwd / 工作树）
        ├── 工作线程
        ├── 工作线程
        └── 插件窗口
```

### 项目

逻辑上的项目，可以是 Git 仓库，也可以是普通文件夹。

### 检出

某台机器上的具体目录，包含机器、根路径和根仓库状态。项目只有一个检出时，界面可以隐藏这一层；隐藏只是显示规则，数据模型仍保留。

点击检出时，可以直接进入根工作区。

### 工作区

工作区是长期存在的工作容器：

- 一个 cwd；
- 一个工作树和分支；
- 一组窗口；
- 多个同级工作线程；
- 工作区级执行队列和状态快照。

根检出本身可以作为根工作区。普通工作区通常对应 Kite 管理的独立工作树。

工作区和线程解耦：删除或归档一个线程，不自动删除工作区；删除工作区才会删除其工作树和分支；删除根工作区属于删除这台机器上的检出，需要单独的高风险操作。

## 4. 工作线程和窗口

所有工作线程同级，没有主线程和协作线程之分。线程有自己的：

- 类型；
- journal 和历史；
- 上下文编排策略；
- 工具能力；
- 运行状态；
- 窗口。

线程与窗口是不同概念：线程是持久化的工作过程，窗口是它在工作区中的界面呈现。插件也可以提供窗口，但不一定创建 agent 线程。

一个工作区允许多个线程存在，但同一时间只运行一个线程。工作区持有唯一的执行槽：当前线程完成、暂停或被打断后，队列中的线程才可以获得执行权。这样可以保证同一 cwd 的模型和工具修改有明确顺序，快照和 diff 也有唯一的执行归属。

未来的 subagent 可以沿用同一个线程模型：

- 被其他线程调用时，记录调用来源和因果关系；
- 在 App 中默认作为调用线程内部的页签或子面板显示；
- 如果用户需要直接操作，再提升为工作区中的同级线程。

因果关系可以持久化，但不作为侧边栏的父子层级。

## 5. 工作线程类型

线程类型是一个可复用的 agent profile，而不是一段单独的 prompt。一个类型可以定义：

- 上下文定义和动态材料；
- 可用工具；
- 模型和推理设置；
- 输出或结束约定；
- 可以响应的触发器。

初步类型包括：

- `coding`：修改文件、执行命令、完成用户任务；
- `review`：读取当前变化并审查问题；
- `test`：运行检查并汇报结果；
- `research`：整理项目资料和外部材料；
- `todo`：提供任务面板和任务操作。

同一个 profile 既可以被主循环内部调用，也可以被用户从工作区打开。两种使用方式共享上下文和工具定义，不再另外维护一套“预制 subagent”系统。

## 6. 触发器和串行运行

触发器负责判断什么时候排队启动哪个线程；上下文组装器只负责准备该线程运行时的材料。

触发器由事件、条件和动作组成：

```text
事件：coding 回合完成
条件：工作区稳定、存在 diff、没有排队输入
动作：排队启动 review 线程
```

条件读取工作区的结构化状态，不执行任意 JavaScript。每次触发记录条件判断时的状态快照、来源、时间和目标线程，避免重复触发或形成循环。

“工作区干净”需要拆成几个状态，避免和 Git 的 clean 混淆：

- `executionIdle`：没有线程正在运行；
- `workspaceStable`：工具、快照和收尾已完成；
- `diffExists`：存在待审查改动；
- `gitClean`：没有未提交改动。

例如 review 通常依赖 `workspaceStable && diffExists`，不应把 `gitClean` 当成审查条件。

## 7. 工作区公共上下文

工作区状态可以成为上下文编排契约中的只读公共变量。它们不是操作系统的 `process.env`，而是宿主在请求或触发器判断前生成的结构化快照。

候选变量包括：

```text
workspace.id
workspace.cwd
workspace.branch
workspace.base
workspace.execution
workspace.diff.exists
workspace.diff.files
workspace.diff.summary
workspace.check.status
workspace.latestSnapshot
workspace.pendingInputs
```

规则如下：

1. 宿主负责读取 Git、文件和检查状态；
2. 组装器负责校验变量、选择分支和展开文本；
3. 每次模型请求固定一份变量快照；
4. 定义、绑定值和来源一起写入 journal；
5. 历史查看使用旧快照，不重新读取当前工作区；
6. 文件清单、摘要等小材料可以直接注入上下文；
7. 完整 diff 等大材料优先通过工具按需读取。

这条方向延续现有 `ContextBinding` 和 `contextScenes`，新增 `workspace.*` 命名空间即可，不另造一套变量系统。上下文编排器不监听文件变化，也不负责启动线程；这些仍由工作区宿主和触发器负责。

## 8. 插件

插件是工作区中的统一产品概念。插件可以提供：

- 一个或多个窗口；
- agent 工具；
- stdio 或远程 MCP 服务；
- 工作区配置和状态；
- 线程类型或触发器。

插件实例属于工作区，窗口布局和必要状态随工作区保存。项目级配置可以放在 `.kite/<pluginName>/`，公共配置和工作区状态分开保存。

### 系统插件

终端和文件系统以插件形式出现在界面中，但拥有系统插件权限，因为它们需要直接接入工作区核心服务。

```text
工作区核心服务
├── FileSystemService
├── TerminalService
├── Git / SnapshotService
└── WorkspaceStateService

系统插件窗口
├── FilesPlugin
└── TerminalPlugin
```

文件系统需要统一提供文件查看、编辑、diff、版本变化和预览；终端需要统一提供 PTY、输入输出、窗口尺寸、信号、进程组和后台任务。

agent 的 `read`、`patch`、`shell` 与文件窗口、终端窗口共用这些底层服务，不能各自实现一套文件或进程语义。

### 公开插件

普通插件只通过受限能力接口读取工作区。插件声明需要的变量和能力，宿主按权限提供，不默认开放任意路径、shell、环境变量或认证信息。

“窗口插件”“agent 工具插件”“MCP/stdio/远程服务”是插件的不同能力，不强行统一成同一种运行通道。

## 9. 界面布局

左侧按项目—检出—工作区组织。检出只有一个时省略该层。进入工作区后：

- 中央区域显示当前聚焦窗口；
- 工作线程和插件窗口可以并列存在；
- 窗口可以拖到右侧停靠栏；
- 拖动过程中显示跟随鼠标的圆形预览；
- 停靠栏保存窗口顺序、位置、展开状态和焦点。

右侧停靠栏是当前工作区的窗口容器，不是另一套会话列表。

## 11. 当前不提前做的事

- 不把所有插件强行压成同一个底层协议；
- 不允许多个线程默认同时写同一个 cwd；
- 不把上下文组装器变成事件监听器或调度器；
- 不先做任意脚本化触发器；
- 不在没有实际插件需求前建立复杂的通用插件市场或远程加载系统。

## 12. 下一阶段建议

1. 先把 App 的数据模型从 `Session` 中心调整成 `Project → Checkout → Workspace → Thread / Plugin Window`；
2. 在工作区内实现多个同级线程和单一执行槽；
3. 接入 `workspace.*` 公共上下文变量；
4. 做 FilesPlugin 和 TerminalPlugin 的核心窗口；
5. 补 diff、快照时间线、回退和采纳的工作区操作；
6. 再设计触发器和普通插件公开契约。
