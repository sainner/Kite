# 项目与远程仓库

本文适用于 kited 与 App，规定项目身份、检出、没有远程的项目和工作区集成的职责。对象关系见 [产品架构](产品架构.md#对象与归属)，项目登记表与凭据的接口见 [工作机](kited.md#账号级数据)，工作区操作与错误语义见 [工作机](kited.md#工作区与线程的生命周期)。

**状态：已实现，尚未经真机验收。** 没有根工作区，所有工作都在工作区里做；检出是 Kite 数据目录里的裸仓库，用户自己的文件夹 Kite 不碰。添加远程项目只登记、不选工作机，可以一起导入环境变量文件；项目有集成方式（直接合入或提交 PR），工作区可以同步主线；项目专用的文件密钥可以设工作区里的路径，改动经 [密钥请求](工具审批与提问.md#密钥请求) 由用户在卡片里填写。

## 项目身份

项目登记表是账号级数据，在工作机之间同步。项目 ID 由先登记它的工作机生成，此后不变。

- 有远程的项目以远程为身份：远程地址按 `域名/owner/repo` 归一化，SSH 与 HTTPS 写法指向同一项目；登记本机文件夹时以它的 origin 为准，同一远程归入同一项目。两台工作机没同步上时各自登记了同一远程，同步后按登记先后合并，保留最早的，另一台的检出改挂过去；并入的项目设过约束时，保留的项目取两份里更严的组合，它的项目专用密钥归到保留的项目。
- 没有远程的文件夹登记为没有远程的项目，以 ID 为身份，各工作机上的检出互为远程，不需要另外准备 Git 平台账号也能多机协作。之后可以给它设远程，项目 ID 不变。
- 远程是用户自有平台（GitHub、GitLab 等）上的仓库；Kite 不托管仓库。

## 检出

检出是某台工作机上项目的 Kite 仓库：数据目录下 `repos/<项目 ID>.git` 的一个裸仓库，只有 Git 历史，没有可以直接编辑的文件，用户不需要打开它。这台机器上的工作区都从它开出工作树；没有远程的项目，各工作机的检出互为远程。

检出在需要时才有：在一台还没有检出的工作机上建工作区时自动 clone，有远程的从远程 clone，没有远程的从在线、有它检出的工作机 clone；导入本机文件夹时在那台工作机上建。一个项目可以在哪台工作机上都还没有检出。

用户自己的文件夹 Kite 不碰：登记时只读它的 origin 或导入它的内容，之后不在里面运行 agent、不提交、不快进。要看 agent 的成果，打开工作区目录，或从远程拉到自己的文件夹。

## 添加项目

添加项目只是登记，不建工作区。

| 来源 | 行为 |
|---|---|
| 远程仓库 | 填写地址或从已绑定账号的仓库中选择，不选工作机、不 clone；先在一台在线的工作机上确认能访问，再写进项目登记表 |
| 本机文件夹，已有远程 | 选文件夹所在的工作机与路径，读它的 origin，按远程登记，之后与远程仓库一样 |
| 本机文件夹，没有 Git 仓库或没有远程 | 在那台工作机上导入成没有远程的项目：已有仓库的取全部分支，工作目录里未提交的改动另作一个提交放在主线上；不是仓库的按默认的忽略规则把文件提交进检出。原文件夹不动 |

- 有远程的项目，确认能访问之后按仓库情况给出集成方式的默认值，见 [工作区与集成](#工作区与集成)，用户确认后才登记。
- 环境变量文件可以在添加时一起存成项目密钥，设好在工作区里的路径（见 [凭据](#凭据)）。本机文件夹由那台工作机找出被忽略的 `.env`、`.env.*` 这类文件，默认都选上，路径照它们在文件夹里的位置，文件内容直接存进凭据，不经过 App；也可以从操作的设备或工作机上任意位置选文件，默认放在 `.env`，工作机上的文件同样由那台工作机读。
- 登记项目与保存这些密钥一起完成，中途取消什么都不留。同一远程已经登记过时用原项目，不改它的设置，带上的环境变量文件存进它的项目密钥。

之后可以在任何一台工作机上为项目建工作区，见 [工作区与集成](#工作区与集成)。

## 删除项目

删除项目是把它从 Kite 里去掉：项目登记、约束与项目专用的密钥从账号级数据删除；各工作机看到删除后停下这个项目的线程，删除工作区、会话和 Kite 的检出。离线的工作机上线同步后再移除。用户自己的文件夹不受影响。

工作区里没集成的改动随检出一起删除；没有远程的项目，各工作机的检出就是它的全部副本，删除后只剩导入时的原文件夹。所以删除前列出还没归档的工作区（其中没集成的改动会丢），没有远程的另外说明这一点，用户确认后才删。之后再添加同一远程或文件夹是一个新项目。Line 所在的项目不能删除。

## 没有远程的项目

各工作机上的检出互为远程：kited 在组网上只读地提供本机检出的 Git 智能 HTTP，只接受同一用户的工作机，不接受推送。

- 主线只做快进：项目同步时从有它检出的其他工作机拉取全部分支，本机主线落后就快进；两边都有新提交时不合并，提示用户在工作区里集成，与有远程时远程领先且分叉的处理一致。
- 集成方式只有直接合入，只合进本机检出的主线，其他工作机同步时快进过来。
- 设远程：在一台有检出的工作机上把全部分支和标签推到用户给的远程，加上 origin，写进登记表；其他工作机的检出随项目同步加上 origin，此后与有远程的项目一样。远程须是空的或与本机同一段历史，推送被拒时不改登记表。

## 工作区与集成

工作区由一个工作树和一个本地分支组成，建在指定的工作机上，从这台机器的检出开出，没有检出时先 clone。建之前先拉取主线（有远程的从远程拉，没有远程的从其他工作机拉），从最新的主线开出。

集成由用户触发，做什么由项目设置里的集成方式决定：

| 集成方式 | 集成时做什么 | 适合 |
|---|---|---|
| 直接合入 | 把工作区分支合进主线，再推送到远程 | 只有自己用的仓库 |
| 提交 PR | 把工作区分支推到远程并开一个 PR（Pull Request），在平台网页上审查、合并 | 多人共用或主线受保护的仓库 |

- 两种方式都先把远程主线合进工作区分支。冲突留在工作区，交给其中的 agent 解决。
- 直接合入：推送被拒时拉取远程主线、重新合并后再推送；因主线受保护被拒时，报错提示改用提交 PR。
- 提交 PR：远程分支名按工作区标题生成，远程或本机别的工作区已占用时加序号。PR 的标题和说明由辅助生成起草，没有启用辅助生成时用工作区名称，提交后可以在网页上改。再次集成把新的改动推到同一个分支，PR 随之更新。用合并提交、squash 还是 rebase 由平台与团队规则决定。第一版只在 GitHub 上自动开 PR，其他平台只推分支，给出去网页上开 PR 的链接。
- 默认值：给项目登记远程时（添加项目，或给没有远程的项目设远程）按仓库情况选。GitHub 上的仓库有其他协作者或主线有保护规则时选提交 PR，否则选直接合入；其他平台默认直接合入。选择的理由写在设置里，用户可以改。
- 集成后工作区与线程仍可继续使用，可以多轮讨论后再次集成。提交 PR 的工作区在 PR 合并或关闭后提示归档，PR 的状态随项目同步定时查询。工作区归档后才进入回收流程。

**同步。**工作区开出以后，主线上新合进来的改动（来自别的工作区或别人）不会自动出现在里面。用户在工作区上点「同步」时，宿主拉取主线，先把工作树里没提交的改动提交到工作区分支，再把主线合进来，不推送；网络不通、拉不到远程时合进本机已有的主线，远程要求登录时不同步，请用户绑定令牌；和集成一样要求工作区的线程全部空闲，冲突交给其中的 agent，合完拍一个快照。项目同步定时拉取主线，工作区落后时显示落后几个提交，由用户决定何时同步，不自动合并。

没有写权限、要先 fork 再向上游提交 PR 的协作暂不支持。

## 远程里的 Kite 引用

除分支与标签外，Kite 在项目远程上只用一类引用：`refs/kite/lease/<工作区>`，流转过的工作区的执行权，记录当前持有的工作机与 `epoch`，读取权限就是仓库权限。会话记录与快照不推到项目远程，由工作机之间的工作区副本跟进。

工作机本机的检出里还有：`refs/kite/snapshots/<工作区>`（快照链）、`refs/kite/peers/<工作机>/`（没有远程的项目从其他工作机拉到的分支）、`refs/kite/replica/<工作区>/`（跟进别的工作机上的工作区时取到的快照链与分支）。日常的拉取、推送与集成不读写这些引用；约定见 [工作区流转](Line与工作区流转.md#工作区流转)。

## 凭据

- 凭据是账号级数据，Git 授权、通用密钥、模型 API Key 与语音识别 Key 在工作机之间同步、落地加密，按类型区分取用方式。Git 凭据在一台工作机上绑定，各工作机都能用，不必逐台配置。
- 访问远程的操作（添加项目、建工作区时 clone、集成、同步、设远程、流转）遇到平台要求登录或拒绝了令牌，在发起操作的地方就地绑定令牌，写到出问题的那台工作机，绑好后重试刚才那一步，不用自己去凭据页。接口见 [远程要求登录](kited.md#远程要求登录)。
- 用户自有平台通过 OAuth 授权或填写 token 绑定。GitHub 不接受用账号密码访问 API 与 Git，使用 OAuth App 的设备码授权，在工作机上完成，token 不经过 App；`repo` 权限覆盖该 GitHub 账号下的全部仓库。其他平台手填 token。
- 通用密钥分账号共享与项目专用两种范围，供相应范围内的 agent 共用。模型只获得名称、类型与 `{account.api_key}`、`{project.ssh_key}` 这类引用，宿主在执行时注入。凭据不作为模型参数、上下文或工具结果传递；带凭据的命令隐藏全部输出。管理与执行契约见 [凭据](kited.md#凭据)。
- agent 缺密钥时用 [密钥请求](工具审批与提问.md#密钥请求) 当场向用户要，用户在卡片里填好就存进凭据，不用自己去设置里找。
- 项目专用的文件密钥可以设工作区里的路径，例如 `.env`：宿主每次建出工作树时把它写进去，路径记进 Kite 检出的忽略规则、不会被提交，密钥改了就重写进项目的所有工作区，供开发服务器、测试这类读文件的工具使用，新机器不用手动放。agent 不能直接改这些文件，要加或改其中一项就用密钥请求。这是对「凭据不作为模型上下文传递」的有意例外：写进工作区的文件 agent 能读到，内容可能进入模型上下文。不想让模型看到的密钥不设路径，只在命令里按引用使用。
- 模型 API Key 当前供工作机查询额度与调用 token 计数接口；保存 Key 不会自动把会话切到 API 后端。订阅登录仍由各工作机自行完成，不算凭据。
