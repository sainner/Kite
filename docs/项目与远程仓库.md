# 项目与远程仓库

本文规定项目身份、检出、托管远程、工作区集成与 Git 凭据的需求，适用于 kited、托管服务与 App。本文内容已经确定。账号服务的项目登记、托管远程、迁移与凭据分发已实现，接口见 [托管账号与设备](托管账号与设备.md#项目与-git-远程)；kited 已按远程登记与 clone 检出、跟随迁移，并实现集成推送与现场的提交推送，行为见 [工作机](kited.md#工作区与线程的生命周期)。通用密钥与执行时引用已接入，契约见 [托管凭据](托管账号与设备.md#凭据服务) 和 [shell](harness-主循环.md#shell)。对象关系见 [产品架构](产品架构.md#对象与归属)。

## 项目身份

项目以远程仓库为身份。没有远程仓库的文件夹不是项目，必须先获得远程才能登记。

- 远程地址按 `域名/owner/repo` 归一化，SSH 与 HTTPS 写法指向同一项目。
- 不同工作机上 clone 了同一远程的目录，自动归入同一项目，不再手动关联项目 ID。
- 项目 ID 由账号服务的项目登记表分配，同一账号、同一远程总是得到同一 ID；远程地址是项目当前唯一的地址，迁移远程改变地址，不改变项目 ID。
- 远程可以是用户自有平台（GitHub、GitLab 等），也可以由 Kite 托管。两者在日常使用中没有区别，只是仓库所在位置不同。

## 检出

检出是某台工作机上该远程的一份 clone，包含所属工作机、根目录和主线分支。在另一台工作机上添加检出即 clone 该远程，默认放在 `~/code/<域名>/<owner>/<repo>`，添加时可以改。

## 添加项目

| 入口 | 行为 |
|---|---|
| 远程地址 | 填写地址或从已绑定账号的仓库中选择，选定工作机后 clone 并登记 |
| 本地文件夹，已有远程 | 读取远程地址，归入对应项目并登记 |
| 本地文件夹，没有 Git 仓库或没有远程 | 必要时由 Kite 初始化仓库并提交初始版本，在 Kite 托管服务上创建远程并推送，然后登记 |

## 托管远程

托管远程归属 Kite 账号，用于没有正式远程的本地文件夹，使普通用户无需另外准备 Git 平台账号即可获得版本管理与多机协作。托管仓库由账号服务以 Git 智能 HTTP 协议提供，地址为 `https://hs.sainner.top/git/<项目ID>.git`，鉴权直接使用 Kite 账号签发的凭据，不另设用户体系。

用户为项目指定正式远程地址时执行迁移：

1. 将全部分支推送到新远程；
2. 各检出把远程改为新地址，离线的工作机在上线后更新；
3. 所有检出切换完成后，从托管服务上删除该仓库的内容。

第 1 步由托管服务直接从托管仓库推送，不需要工作机在线。迁移开始后托管仓库只读，避免迁移期间写入的提交丢失。

## 工作区与集成

普通工作区由一个工作树和一个本地分支组成。

- 集成由用户触发。kited 把工作区分支合进检出主线，再推送到远程。主线合并沿用当前采纳的方式，冲突留在工作区，主目录不进入冲突状态。
- 推送被拒时，拉取远程主线，重新合并后再推送；冲突交给该工作区中的 agent 解决。
- 集成后工作区与线程仍可继续使用，用户可以多轮讨论后再次集成。工作区归档后才进入回收流程。

根工作区是特例，即检出现场：直接编辑检出目录，没有独立分支，不经历普通工作区的集成与回收。现场完全由用户自己控制，Kite 不自动提交现场改动。现场有未提交的改动时，阻止普通工作区集成。App 为现场提供由用户触发的「提交并推送」；远程领先且两边分叉时不在现场合并，提示用户新建工作区处理。

## 凭据

- 凭据服务属于账号服务，Git 授权与通用密钥共用加密存储。Git 凭据随 Kite 账号提供给各工作机，不在每台工作机上单独配置；托管远程的访问凭据也由此签发。
- 用户自有平台通过 OAuth 授权或填写 token 绑定。GitHub 不接受用账号密码访问 API 与 Git，使用 OAuth App 的设备码授权，由托管服务代为完成，token 不经过 App；`repo` 权限覆盖该 GitHub 账号下的全部仓库。其他平台手填 token。
- 通用密钥分账号共享与项目专用两种范围，供相应范围内的 agent 共用。模型只获得名称、类型与 `{account.api_key}`、`{project.ssh_key}` 这类引用，宿主在执行时注入。凭据不作为模型参数、上下文或工具结果传递；带凭据的命令隐藏全部输出。管理与执行契约见 [凭据服务](托管账号与设备.md#凭据服务)。
- 模型供应商凭据仍由各工作机自行登录，不纳入凭据分发服务。
