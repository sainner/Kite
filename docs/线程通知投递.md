# 线程通知投递

配置修改、文件变化和插件状态变化共用“来源保存事实 → 按归属提供通知 → 自然请求边界纳入 → 追加历史”的路径。当前已接 agent 配置、执行授权，以及请求边界发现的基础上下文变化。普通文件监听、关注范围合并和自动触发尚未接入。

## 保存与生效

- `PluginInstance.config.agent` 保存绑定的 AgentDefinition，包含模型、工具选择、上下文定义与回合请求预算。目录模板更新只影响新实例；`KITE_MODEL` 在创建时解析，重启不会覆盖绑定配置。
- `GET /instances/:id/agent-config` 返回实例和配置内容摘要 `revision`。`PUT` 接收 `{ expectedRevision, agent }`，完整替换绑定配置；旧摘要返回 409，避免覆盖其他设备的修改。
- SQLite 在同一个事务中保存配置及其通知。通知有稳定 ID、实例归属和递增序号；agent 配置提交不打开 Runner、不调用 send，也不唤醒空闲或暂停线程。
- `config.execution` 保存执行授权，管理入口为 `/instances/:id/execution-grants`。更新前检查实例已停止且没有未知执行，必要时只为恢复检查打开 Runner；运行中拒绝修改。提交 `execution.permissions.changed` 通知后，后续工具读取新策略，下次自然请求追加通知并在 `settings.execution` 保存授权内容与版本。不自动停止、唤醒或重放，细节见 [实例执行授权](实例操作.md#实例执行授权)。
- `prepareRequest({ afterNotification })` 同步读取当前配置和该线程尚未纳入的通知。当前请求使用已经取得的模型、工具和设置；其执行期间的新修改等下一次自然请求。
- `request.started` 同一条 journal 记录保存此次纳入的输入、通知，以及上下文和配置快照引用。只有此记录落盘后才调用模型。恢复从已纳入通知的最大序号继续读取；失败或停止不把已经纳入的通知重新排队。

这里“纳入”表示宿主已把内容固定到一次模型请求，不保证模型服务已经接收、理解或成功回答。网络失败沿用当前回合失败与显式恢复语义。

## 保留已发送的前缀

首次请求的 `instructions` 固定为基础上下文。后续上下文有变化时，继续使用相同的顶部指令，并在历史末尾追加独立的更新条目，明确新内容替代之前的基础上下文。已发送的消息、工具调用、结果和通知保留原顺序，恢复时使用 journal 中保存的内容。

宿主仍在每个自然请求边界读取项目规则和日期，沿用 `ContextDefinition`、`ContextBinding` 及 `context.prepared` 快照。摘要相同不追加通知；变化时追加一次 `context.updated`。配置通知说明设置变更，上下文通知保存实际展开后的新规则，两者各自保留来源。

工具声明在首个请求配置中固定；后续只调整可调用集合。请求传输通过 `tool_choice.allowed_tools` 或 `none` 限制工具选择，宿主 ToolBatch 同时只注册本次获准的执行器。插件清单不能扩大已有定义开放的工具范围。已有工具 schema 或描述发生变化时要求新建会话，动态加载新工具留给后续能力。

`request.configured` 保存内容寻址的模型设置、预算、实例定义 ID、配置摘要、完整工具声明及实际允许集合。模型或推理强度变更目前使用请求参数，可能影响提供方缓存；指令追加与固定工具声明保留了可复用的请求前缀，但实际命中仍取决于提供方。

工具选择格式来自 [OpenAI 官方工具调用文档](https://developers.openai.com/api/docs/guides/function-calling#tool-choice)，缓存原则见 [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)。2026-09-29 已通过当前 ChatGPT 订阅入口验证固定工具列表配合 `allowed_tools` 的最小请求；没有用该次验证推断缓存命中率。

## 公共通知边界

`ThreadNotification` 保留 ID、来源、类型、权限层次和 `context` 组装快照。正文复用上下文场景契约：agent 配置变更使用 `thread.configuration_changed`，执行授权使用 `thread.execution_permissions_changed`，基础上下文更新使用 `thread.context_updated`。来自持久来源的通知带递增序号；宿主在请求边界生成并直接纳入的上下文更新不占来源游标。

配置提交时将通知定义与变量一起组装并保存；请求边界生成的上下文更新同样保存完整快照。Runner 在输入纳入前校验通知快照能完整展开，向模型提供从快照还原的正文。历史和重启恢复不重新读取当前模板或材料，因此通知的段落、条件选择和变量值均可追溯。细节见 [上下文组装器](harness-上下文组装.md#通知正文)。

- `instruction` 仅由宿主根据用户授权的配置或指令材料生成，映射为 developer 消息。
- `observation` 表达环境事实，映射为普通上下文消息；来源及事实提示由场景定义展开，适配器原样传输正文。外部文件或插件数据不能自行选择指令权限。
- 当前只有内部宿主入口，尚未开放任意插件提交通知的 HTTP 接口。后续插件入口需要校验来源、目标及授权。
- 事件到达不属于 `canRun` 条件；主动启动工作的触发器单独实现。
- 来源可以在投递前筛选、合并尚未纳入的状态更新；已经纳入的通知不改写。当前配置通知按提交顺序保留，文件的关注、版本复核和合并策略后续接入。

App 的 SSE 继续负责界面刷新。其进程内游标不作为模型投递凭据；持久来源序号与每个线程自己的 journal 负责模型投递恢复。
