来源：2026-10-11 多窗口缩小、恢复卡顿；2026-10-12 换成 NSTextView 正文后又卡。Mac 上正文、标题两侧单独托管、按图层变换，点阵和光标、交互不参与过渡（见 [[feedback-interaction-quality]]）。2026-10-13 一轮处理后（提交见 git log）：窗口常带 Auto Layout 引擎（`WindowLayoutEngine`），空画板静止主线程 28% → 17%、恢复窗口丢帧 11 → 1；空画板就此结束，用户不要限帧。

基线（2026-10-14，main 4b68dd2 加测量代码，用 `kited/test/manual/measure-perf.ts` 量；Mac mini、60Hz 外接屏、窗口 1200×924，`--threads` 摆「英语入门练习」「测试 Kite 消息收发」两个会话左右分栏，每场景 1～2 次启动、每次 2 轮 90 步；iPad Pro 12.9 第 5 代、120Hz、每次 3 轮）。改动后和改动前的检出交替比（`--base`），这里只留量级；原生外壳合入后，下面 2026-10-13 的拖缝每步数据已过时，只作当时的分项参考：
- Mac 拖缝每步主线程：贴底 14.4、工具行 14.1（另一次 4 轮 13.9～14.3）、长回复 13.3、压缩分界展开 18.9、有调用在跑 14.9、开着操作栏 14.6ms，帧间隔中位除压缩分界展开（33.3ms）外都是 16.7ms。旧测量代码在 ec82993 上测工具行约 12ms，缝的起点和测量代码都不同，不直接比。
- Mac 拖缝工具行的 Time Profiler（挂着它时每步约 14.3ms）：对话列表排版约 5.4、托管视图（标题栏、输入区等）约 2.4、CA 提交约 1.9、其他 AppKit 布局约 1.4、正文文本视图约 1.3ms。
- Mac 侧栏拖宽每步 21.4ms、帧间隔 33.3ms；另一次和当时的 SwiftUI 台面交替跑（Debug 开关 `--swiftui-stage`，已随旧版删掉），原生约 24ms、SwiftUI 台面约 57ms。侧栏改宽时 `WindowLayout.anyResizing` 为假，对话列表不走拖缝时只量可见区附近那条路（看代码得出，未分项量过）。
- Mac 缩小、恢复：动作到第一帧约 51、57ms，到动画走完主线程约 200、190ms，不丢帧。
- Mac 静息主线程：什么也不改 0.2～0.7%、空画板 23.6%、标题栏圆环 0.5%、停靠栏头像脉冲 19.3%、对话里工具调用扫掠 4.8%。
- Mac 打字每键主线程中位约 8ms；发送后 1.5 秒主线程约 255ms，不丢帧。
- iPad 拖缝贴底每步 21.7ms、帧间隔约 22ms（Time Profiler：托管的 SwiftUI 外壳约 9.6、`layoutSubviews` 约 4.1、CA 提交约 3.8、对话列表约 3.1ms）；侧栏拖宽每步约 93ms、帧间隔约 124ms；缩小、恢复到动画走完主线程约 217、305ms。
- iOS 外壳改原生后（2026-10-14，分支 `claude/ios-uikit-shell`，和旧的 SwiftUI 台面、输入区、紧凑布局同一次装机交替跑；切旧版的 Debug 开关已删）：iPad 拖缝贴底每步 16.4ms（旧 21.7）、帧间隔中位 16.7，侧栏拖宽每步约 12ms、帧间隔中位 8.9（侧栏的旧变体不跟 SwiftUI 版的拖法，不可比，改前约 93～117ms），缩小、恢复整段主线程约 134、130ms（旧约 203、196）。拖缝的 Time Profiler 每步：对话列表和行约 2.9、正文文本视图约 1.0、UITextView 内部视口排版（`_UITextLayoutCanvasView`）约 2.5、字的重画约 2.1、外壳各视图合计 2～3ms，剩下的大头在对话自己。iPhone 17：点按拉开、收起侧栏 0.8 秒里主线程约 23～27ms、不掉帧（旧约 350～370ms、掉 8 帧），手指拉侧栏约 91～99ms（旧约 386ms），横滑（换外壳后、改图层透明度前）约 105ms、最长一帧 37ms（旧约 227ms、50ms），键盘升起的第一帧前主线程约 142ms 新旧一样（多半是系统起输入法），键盘收起曾比旧版多掉帧，改法未在真机复测。

2026-10-14 分支 `claude/mac-perf` 第一轮（已合入 3dbae4b，和同时段的 main 交替跑，各 3 次启动的中位）：拖缝每步贴底 14.4 → 12.7、工具行 14.0 → 13.2、长回复 12.7 → 12.2、压缩分界展开 17.7 → 14.3、有调用在跑 14.6 → 12.8、开着操作栏 14.8 → 13.8ms，帧间隔中位都到 16.7ms；侧栏拖宽 19.8 → 17.5ms，帧间隔仍 33.3ms；缩小、恢复整段主线程约 145 → 90ms，首帧约 45ms 没变；静息空画板 23.5 → 14.4%、停靠栏头像在跑约 20 → 5%；打字每键 11.2 → 9.8ms。做法和原因在各提交说明里。量过无效、没留的：拖缝时文档视图只长不缩（改文档视图大小时的几何通知挪到了滚动和摆行上，反而多约 1.5ms，先改文档大小的那次把后面的通知变便宜了）；卡片只在压暗时开 Core Image 滤镜（侧栏拖宽没变化）。

同分支第二轮（和 main 79e9b04 交替跑，各 2 次启动）：侧栏拖宽每步 17.9 → 10.8ms、帧间隔 33.3 → 16.7ms、超 20ms 的步 73 → 1.5；缩小、恢复首帧 40.8 → 23.2、42.3 → 32.5ms，整段主线程不变（约 80ms），拖缝、静息、打字不变。侧栏拖宽慢在两处：台面视图跟着改尺寸时铺满台面的卡片、停靠栏都重排（改法：拖动中台面按侧栏最窄时的宽排、往左伸进侧栏底下，只让出被盖住的一段）；停靠栏里没上过台面的窗口按台面大小排正文，每步换缩放，`sublayerTransform` 一改 AppKit 就把正文所有图层标成重画（第一轮记的「图片视图每步重画」就是它，拖动中改用开始时的大小）。缩小、恢复改为动画开始后的下一帧再按新大小重排跟着变的会话窗口。

未解决：
- 打字每键约 10ms 里大头在字段编辑器本身：插字约 2.2、TextKit 2 每键增删视口元素视图带来的图层树重建约 1.5ms，新旧版都有。
- 缩小、恢复首帧（2026-10-14 第二轮后约 23、33ms，目标一帧 16.7ms 未到）：动作那一轮 SwiftUI 处理排布改动的整轮更新约 8～10ms（停靠栏、窗口按钮、标题栏这些岛读排布模型，跟着更新），台面排卡片约 4～5ms，托管视图排版、提交和画各约 3～4ms（Time Profiler 量级，挂着它时偏大）。要再降得让岛不在动作那一轮跟着排布模型更新，停靠栏的格子要和卡片同一个动画，还没想好怎么拆。之前的记录：2026-10-13 Debug 一列两窗口缩小首帧 84.5 → 77.5ms；单看首帧时长不可靠（部分工作会推到计时之后），同时看整段主线程和丢帧。
- 拖缝调整大小：用户 2026-10-13 定为正文随时跟宽度重排（试过「指针动时定住、停下或松手再排」的方案说明后改回），接受约 30 帧；同日又说拖动时对话不必保持贴底，并让继续优化。-O、60Hz、左右两窗：每帧主线程约 27ms，拿掉对话约 10ms；对话在场的固定成本约 5ms、对话区改尺寸约 5ms、文字重排约 7ms，没有单独的元凶。对话区不改尺寸（定住）约 15ms、接近 60 帧。实测对帧率无效、未提交的：按行冻结、行内代码背景共用排版器、跳过文本视图光标区域重算、只挪位置时不重排、不发几何通知、关滚动条动画、拖缝时不切换可否点击；合并占位组按数据只省零点几毫秒；Codex 同日又排除了固定正文宿主根尺寸、标题只发语义变化、量高时不 setFrameSize、包一层原生容器、替换 VStack、geometryGroup、强制连续排版。
- 拖缝长回复（Codex 2026-10-13 完整 App 真实会话，-O、90 步、每轮清尺寸缓存测首见宽度）：短回复主线程约 2.6 秒/90 步、约 33ms 一帧；滚到含表格、代码的长回复约 4.9 秒、约 66ms。长回复里 TextKit 全文 `ensureLayout` 约 0.83 秒（每个新宽度只量一次，不是重复量），屏外附件内部布局约 0.74 秒；后者已改为屏外推迟改宽、滚入前补齐，降到约 4.1 秒、约 50ms。正文换成空占位仍约 1.2 秒/90 步（含滚动容器、输入区和舞台）。
- TextKit 视口裁切的正确性边界（2026-10-12，当时对话还是 SwiftUI 懒加载）：把部分可见正文的视口裁到真实可见交集能省 10%～12%，但行没排好就露出（LazyVStack 首次只露底部、或顶部被裁时改宽）会大面积错位缺字。现在的原生列表把行放进列表前就整段排好，视口只给露出的那截（`ProseTextView.clipsViewport`）；没事先排好的（表格卡片）仍整段作视口。判对错要在任何主动 ensure/cacheDisplay 之前比首次实际绘制与完整滚入参照（当时的 Lazy 屏幕场景已随 SwiftUI 对话删掉）。Apple 要求视口代理 override 调 super，不能靠截掉屏外 fragment 的 configure 回调省成本。原始测量在 `/private/tmp/kite-codex-perf-audit/`，引用前先确认还在。
- 拖动时只排看得见的（Claude 2026-10-13，分支 `claude/mac-native-transcript` 第四期）：自定义 NSTextContainer 按位置给行宽的做法真实 App 里反而更慢，放弃；改用 TextKit 2 非连续排版——改宽后从可见区上沿那段 `enumerateTextLayoutFragments(from:options: .ensuresLayout)` 排到下沿，上面没排的按 TextKit 估的高占位（估的位置可差上千点，列表按住可见区那截文字对齐，停下整段排准）。坑：往上补排的段会和已排的叠在一起、不推开，文本视图的视口不能越过排好的上沿；估的高带小数时贴底会逐像素抖，要取整。-O 两窗 90 步、与整段排同次启动逐像素一致：长回复 26.5 → 21ms/步、贴底（折叠长消息只排露出）22.5 → 20ms、工具行 19.6 → 19ms，帧间隔仍 33ms。剩余：窗口外壳约 9.4（SwiftUI 根约 3.5、窗口内容约 3）、正文和气泡量高各约 2～2.6、文本视图自己的视口排版约 1.6（`_updateContentSizeIfNeeded`、`locationForPositionInViewport`）、CA 提交约 1.5、代码和表格卡片（SwiftUI 托管）约 0.8ms 一张。测量版原型「两窗隔一帧轮流重排」三个场景都到 16.7ms 帧间隔（每步约 15ms），代价是每个窗口的正文 30Hz 跟宽度；用户随后选了重写外壳（见 [[decision-native-ui]]），这一原型没采用。
- 拖缝的预算与 AppKit 列表原型（Claude 2026-10-13，完整 App、-O、左右两窗、90 步，同一次启动交替）：对话换成同高空白每步 9.4ms、60 帧；对话在场但宽度定住 16.4～17.9ms（约一半帧超时）；原写法长回复场景 30.4ms、短消息场景 19ms。AppKit 滚动视图逐行托管现有行视图：短消息场景每步 36ms，所有行只挪位置不改宽也要 29ms——托管的 SwiftUI 行改宽约 0.8ms 一行、只挪位置约 0.2～0.3ms 一行，比整列一棵 SwiftUI 树（约 0.3ms 一个可见行）还贵。「列表换 AppKit、行仍托管 SwiftUI」不成立，拖动路径上的行必须不经 SwiftUI。
- iPad 宽屏拖缝（2026-10-13 真机 iPad Pro 12.9 第 5 代）：SwiftUI 对话每步 166～317ms；原生对话（UIKit）每步主线程约 21.5ms、帧间隔中位约 22ms，其中 SwiftUI 外壳（beginTransaction 加托管排版）约 9.3ms、对话自己（排列量高、文本视图的视口排版、单行字）约 9～10ms，16.7ms 要等外壳改原生，见 [[decision-native-ui]]。外壳改原生后的真机数据见上面 2026-10-14 那条；Mac 的结论不外推。

完成条件：上述各项处理或经用户确认不做；iPad、iPhone 的结论来自真机测量。测量方法见 [[performance-diagnosis]]。
