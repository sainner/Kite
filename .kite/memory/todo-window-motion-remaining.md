来源：2026-10-11 多窗口缩小、恢复卡顿；2026-10-12 换成 NSTextView 正文后又卡，用户要求优化首帧和结束那一刻。Mac 上正文、标题两侧都已单独托管、按图层变换；动画开始、结束（moving、settling 翻转）只更新读它的叶子层，卡片、正文不再整层重算；点阵和光标、交互不参与过渡（见 [[feedback-interaction-quality]]）。

2026-10-12 Debug 版一列两窗口，同一次启动对照（中位）：结束那一刻缩小 34～39 → 16～23ms、恢复 42～61 → 29～44ms；整段每次少 15～25ms，约 170～220ms，丢帧 4～7。首帧（动作到动画开始计时）两种写法都在 70～95ms。

未解决：
- 首帧：卡片的悬停、窗口按钮组尺寸、正文报回的菜单宽度 2026-10-12 改成只由读它们的几层更新。同日测量版实测（Debug 一列两窗口，新旧写法同一次启动交替，缩小前模拟指针停在窗口上）：缩小首帧卡片重算 6 → 2 次、首帧约 103 → 94ms；恢复 3 → 2 次，耗时在误差内；结束那一刻没差别。缩小首帧仍约 94ms：标题两侧的托管视图首帧更新 9 次（两张卡片各两侧），SwiftUI 按新排版重算悬停约 10ms，面积变了的窗口按新尺寸重排正文。
- 空台面画板（`WindowlessStage`）的风筝场景：2026-10-12 改成只算图形有内容的格子附近、各层位移每帧算一次。同日测量版实测（Debug，新旧点阵同一次启动交替）主线程静止约 64%（44～99%）→ 29%，出现约 70% → 31%，收回约 35% → 20%。当时剩下的约一半还是格表，因为 App 背景在画板后面也算同一个风筝；同日按用户的决定改成画板自己画（见 [[feedback-interaction-quality]]），改后没再量。另一半是取景框逐帧更新的 SwiftUI 开销。缩小最后一个窗口时等停下再出现，打开时的收回保留（见 [[feedback-interaction-quality]]）。
- 拖缝调整大小仍未达到每帧 16.7ms。用户要求可见正文随时重排，不能冻结可见文字。2026-10-13 完整 Mac App、两个真实会话、优化编译下固定 90 步且核对实际宽度序列：短回复主线程约 2.6 秒、回调约 33ms；同一会话滚到含表格和代码的长回复后约 4.9 秒、约 66ms。长回复的 TextKit 全文 ensureLayout 约 0.83 秒，附件宿主额外约 0.74 秒；高度缓存一直命中，不是附件反复量高。10 个附件中 8 个整轮在屏外仍各布局 85 次。保留 TextKit 边界、只推迟屏外附件内部宿主改宽的对照，前两组约 4.8～4.9 → 4.1～4.2 秒、帧间隔约 50ms；第三组只降约 4%，不能合成固定收益保证。去掉测量代码后的完整 App 已验证窄宽拖动、滚走再滚回时表格与代码块按新宽正常显示；原生回归已覆盖真实代码块展开/横滑后，屏外三次改宽、部分滚入首帧尺寸与绘制，以及选区和 Markdown 原文复制保持；不外推为流式附件更新、字体变化或真实滚轮手势已验证。剩余成本包括整段文本量高、正文 SwiftUI 排版和外层舞台更新；这次修复不等于全部卡顿已解决。
- 拖缝归因的适用范围：上述每轮只清尺寸缓存，测首次遇到的宽度，不能替代热缓存拖动、流式更新或移动端结论。短回复的 TextKit ensureLayout 仅约 0.1 秒；删除量高时 setFrameSize、包一层原生容器、替换 VStack、geometryGroup 均未显示稳定收益。保留尺寸传播的正式标题反馈修复已在真实短回复复测：主要减少异步图更新，约少 0.10～0.13 秒/90 步，正文首次宿主布局基本不变。将正文替换为空占位后仍约 1.2 秒/90 步，该数包含滚动容器、输入区和外层舞台，不是纯窗口边框下限。原始对照、trace 与有效性报告当前在 `/private/tmp/kite-codex-perf-audit/`（部分 JSON 为 gzip），再次引用前确认文件仍在；长短场景和采样路径不能相加或直接外推为某个函数的可节约比例。
- TextKit 视口优化的正确性边界：2026-10-13 同一完整 App、同一 90 步实际宽度的交替对照，直接把部分可见正文的视口裁到真实交集，主线程约 4.0 → 3.5～3.6 秒；2090 次量高、3690 次原生布局的时机与几何一致，但原始 Lazy 首次只露底部场景出现大面积错位/缺墨。首次全文视口完成后再裁切，冷滚通过，却在同一顶部裁切正文 720→480 改宽时约 87% 墨迹位置不匹配；不能采纳这两个提速。保持视口从文首到可见底边、或仅在原生 layout 期间扩为全文，两者通过冷滚/改宽像素对照，但没有稳定 CPU 收益，均未进入产品。判别力不能只靠 sizeThatFits、fragment 几何或“有墨”；必须在任何主动 ensure/cacheDisplay 之前比较首次实际绘制与完整滚入参照。手动原生回归入口见 `kited/test/manual/README.md`；本轮负对照与测量证据在 `/private/tmp/kite-codex-perf-audit/contiguous-viewport-contract/`、`viewport-export/`、`first-viewport-export/`、`scoped-viewport-export/`，依赖前先确认仍在。
- 已排除的低收益路径：2026-10-13 同场景将正文宿主根尺寸固定、只发布标题语义变化，均改变了预期触发计数但无稳定耗时收益。两条长正文每个实际新宽度只量一次；短文本不同 proposal 得到同一自然宽的重复测量，即使全部消除也不足总 CPU 的 0.8%。已采样的光标失效约 1～6ms/90 步，完全屏外原生文本 layout 的整体观测预算约 90ms/90 步，都不是主要瓶颈。上层滚动几何和槽高度已经去重，未找到额外整树反馈链；不能以这些排除项宣称没有其他优化空间。Apple 的 [TextKit 视口子类化约束](https://developer.apple.com/documentation/uikit/managing-viewport-layout-and-attachment-reuse-in-a-text-view-subclass) 要求视口代理 override 调用 super；不应通过截断 NSTextView 屏外 fragment 的框架 configure 回调来省成本。
- 拖动换落点时受影响窗口按预览尺寸重排正文，每次 32～82ms（2026-10-11 测，正文托管前）。2026-10-12 用户让直接做，改成指针停下 120ms 再换预览（`WindowLayout.previewDwell`），重排落在头像不动的时候；手感待用户试，不行再换成预览时不重排正文。
- iPad 卡片和 iPhone 侧栏、底栏拉开时的窗口缩放（`WindowShell`）同样是对含 UITextView 的整块内容做几何效果，没在真机上量；Mac 的结论不外推。

完成条件：上述各项处理或经用户确认不做；iPad、iPhone 的结论来自真机测量。测量方法见 [[performance-diagnosis]]。
