2026-09-23 用户决定：Kite 每个会话跑在自己的 git 工作树（worktree）上，完成后自动合并回主线，整体流程形状和 Pigeon 一致。我曾建议「默认在主文件夹直接改、工作树作为可选草稿」，用户否决，理由是自己一定有并行多个改动的需求。

**Why:** 用户是第一用户，需要并行会话；每会话独立工作树也让快照回退按会话隔离，不会撤掉别的会话的改动。

**How to apply:** 不再提议「默认不开工作树」。设计时要解决的四处：工作树放项目外由 Kite 管理；被忽略的必需文件复用 Claude Code 原生格式（`.worktreeinclude` 复制、设置里 `worktree.symlinkDirectories` 软链接，2.1.217 已核实存在），初始化命令用一个项目脚本约定（上游只有接管创建的 WorktreeCreate 钩子，没有建后初始化钩子），Kite 用环境变量告诉脚本主仓库位置、自己记录初始化成功与否，不让脚本自判身份或写状态文件（Pigeon #2322 教训）；依赖目录走全局缓存重装、不软链接（2026-09-23 本机实测 bun 1.3.14 在 APFS 上每棵工作树装 Pigeon 依赖约 1 秒、du 显示 926M 但真实占盘几乎为零，因为默认写时复制克隆；未测 postinstall 产物和 npm/pip 这类整份复制的包管理器）；合并前先把可能有未提交改动的主文件夹存成版本，冲突交 agent，二进制文件让用户二选一；未合并的工作树永不自动删。第 2 步实现时（2026-09-23）改为：采纳是在会话工作树里把主线合进会话分支、主文件夹只快进，采纳后会话继续可用不删工作树，归档才删目录和分支、快照引用保留；已实现的机制见 kited/README.md。不带 Pigeon 的集成队列、验收门、审查轨、中心归档、回收栅栏。完整设计见任务书 §21。关联 [[kite-origin]]。
