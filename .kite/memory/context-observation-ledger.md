用户提出利用快照，在会话“账单”中记录 read 时看到的文件版本；同一机制还可记录 skill 是否加载过，帮助压缩后重组上下文。用户明确指出整文件版本检查可能拒绝互不重叠的局部修改，随后决定文件读取状态与版本变化只用于提示，不阻止有效补丁。完整账本和压缩重组的数据结构尚未确定。

后续评估要区分两个维度：patch 或 write/edit 是修改的表达方式；是否强制先读、检查整文件还是局部内容，是独立的一致性策略。不能从工具名称推断保障强弱或厂商设计动机。

讨论中的建议：账本区分“曾经向模型提供过什么”和“本次请求仍携带什么”，记录内容版本、实际可见范围及是否截断。skill 曾加载过，不代表压缩后全文仍在上下文。快照存内容，账本可引用快照，不必每次 read 都提交整个工作树。

已确定的编辑策略：使用 patch，针对当前内容应用补丁，无法匹配时报错；未读或整文件 hash 不同仅提示，修改与删除都不另加读后版本锁。文本不冲突不等于语义没有冲突，外部改动通过工具结果提示模型按需重读。

当前轻量实现只在本次 localTools 运行内保存 read 或成功 patch 后的内容 hash，恢复进程后重新建立。它不保存已读范围、不表示模型还持有原文，也不是完整的持久化观察账本；后续实现上下文管理时要保持这个区别。
