用户提出考虑统一的事件广播机制：文件变化不必等 patch 碰到相关文件才提示，可由 Kite 界面编辑、机器上其他会话工具编辑等来源主动发现。用户同时担心通知分散模型注意力、打断工作连续性。普通文件监听及主动触发仍留待后续确定。

2026-09-29 用户在 AgentDefinition 实施前指出：配置修改若重写顶部上下文会影响缓存，并认为它与工作区事件通知属于同一个体系。随后同意继续按统一投递方向实施，以配置变更为首个来源。基础指令与已发送历史保持原样，后续上下文变化追加独立通知；修改公共定义默认影响新实例，已有实例须显式应用配置。宿主实际权限和预算独立执行，不能靠通知文字授予工具能力。

讨论建议把事件采集与模型投递分开：事件先进入会话待处理记录，在下一次自然发生的模型请求前筛选、合并，再作为环境事实带入。普通文件变化不取消当前模型请求或工具、不独自触发额外请求、不唤醒空闲或暂停会话。代价是最后一次模型请求之后到达的变化可能留到下一回合，界面可先显示更新。现有 send(input) 会启动空闲会话并解除普通暂停，不能直接拿它承接这种被动通知。

关注范围建议优先已读、已修改和已加载的项目规则等相关文件；只看 git diff 会漏掉模型已依赖但未修改的文件。按实际工作树/文件路由，不向同仓库的所有独立 worktree 广播“你的文件变了”。自身 patch 已返回的变化不重复提示；同一文件的多次变化合并到最新版本，投递前已读到该版本则取消过期提示。

账本需区分磁盘当前版本与已经提供给模型的版本；收到变化事件不能直接覆盖原来的读取记录，否则会失去比较依据。

发现途径可以先用受管编辑事件，加模型请求边界对关注文件的版本复核。shell、格式化器与外部编辑器也会写文件，仅监听 patch 不能覆盖它们。以后如需更及时的 UI 更新再加文件系统监听，监听只标记需要复核的路径，内容版本才是事实。不要为了这个场景先引入分布式消息系统或完整事件框架。

**Why:** 用户希望配置和环境变化自然进入 agent 的工作过程，同时保留已有上下文前缀，减少缓存损失及无关通知干扰。

**How to apply:** 配置、文件和插件状态按同一投递边界设计，保留各自来源与权限语义。区分变化已发生、宿主已应用和请求已纳入；普通通知不调用会启动线程的 send。具体协议以 `docs/线程通知投递.md` 为准，模型或推理参数变更不能承诺保留缓存。
