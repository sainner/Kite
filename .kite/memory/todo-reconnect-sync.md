**来源：** 2026-10-27 用户嫌重连慢，提出保留未归档实例的数据、重连后增量更新；商定先做线程流的增量同步（不落盘），改动前后各量一次。

- 已实现：线程流带 Last-Event-ID 重连只补变过的记录，契约见 [会话显示协议](../../docs/会话显示协议.md) 的 cursor 一段；kited 重启后序号不可比较，仍整份。
- 改前基线（10-27，WorkStation 经组网读 Mac mini 的线程流首帧）：两个长会话 2.9 MB／1166 条、2.8 MB／1131 条，各三次 11.6、2.3、3.1 秒与 1.7、3.4、1.4 秒；目录首帧 647 KB，0.4–0.9 秒。同一路径上 1 KB 的首帧 0.08 秒、107 KB 的 0.15 秒。
- 量法：`GET /events?thread=<id>` 经本机 kite-net 的 HTTP 代理（`/network` 的 `httpProxyPort`）发到对端，读到第一条 `data:` 行为止，记字节和耗时；改后带上次首帧的 cursor 作 `Last-Event-ID` 再连。App 里看 TimingTrace 的「历史已解码：N 条（只补变化）」。
- 待做：Mac mini 的 kited 换上新版后按同一量法量改后，记下对比。
- 待定：第二步，App 把会话记录与完整目录（含实例清单）存到本机，冷启动先显示上次的内容。目录首帧 647 KB 里 566 KB 是实例的 `config`，141 个实例中 135 个已归档，可考虑目录不带已归档实例的配置；另一候选是压缩分界里的记录、大块工具结果展开时再取。

**完成条件：** 改后在真实组网上量过并记下对比；第二步、目录瘦身、按需取各自决定做或不做。
