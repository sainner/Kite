用户希望直接展示特定时机（例如新建会话）上下文如何组装：双击即可编辑对应段落；条件型内容用页签切换查看不同分支；内部动态内容用 chip 作为变量。

用户进一步澄清这里的核心是「契约」，并认可按「创建会话」「会话中文件变化」等业务场景约束定义与可用变量。这个诉求不代表让组装器接管事件监听、通知投递或 agent 调度。

用户确认通知正文同样属于上下文组织，要求配置变更、基础上下文更新等通知复用这份契约。通知应保留当时的定义和变量，后续修改不能改写已投递的历史。事件来源与投递时机仍由宿主管理，正文模板不承担执行权限或模型配置的应用。

2026-10-02 用户确认上下文模板的产品入口：在设置中编辑模板；创建会话时选择模板，也能基于已有模板修改并保存为新模板。创建时沿用新会话窗口内的配置入口。该决定允许可复用上下文模板的管理与选择，替代此前将模板选择排除在入口之外的约束。

2026-10-03 用户明确纠正：统一上下文编排的目的在于给用户提供编辑途径，不能以「只有一个使用点、没有复用收益」为由让提示词继续硬编码。会话标题生成与刷新等轻任务的规则和材料也应进入同一编辑途径；仅调用组装器而没有可用的编辑、保存及运行时读取入口，不算满足这个目的。

**Why:** 用户希望直接看见并编辑上下文的组成；创建会话时也可以从现有模板继续定制。可编辑性本身就是产品需求，不依赖复用次数。

**How to apply:** 设置和新会话使用同一套模板编辑能力，模板内容保持结构化段落、变量与条件。审查提示词时同时检查用户能否编辑、保存，以及下一次执行能否读到修改；不要仅按代码复用价值判断。组装器仍不负责事件监听、线程启动或调度；触发器在组装器之外工作。条件页签用于查看和编辑分支，运行时按真实变量选择。实现现状通过代码和项目文档核验，不在记忆中维护进度。
