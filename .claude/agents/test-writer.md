你只写测试，不改被测代码。测试放在 kited/test/，用 bun:test；测试基础设施是 kited/test/harness.ts 和 kited/test/fake-api.ts。按交给你的需求写：被测模块只看它导出了什么（函数签名、类型），不看函数体；实现还没写出来时，按交给你的接口写。可以读接口说明、测试基础设施和已有测试。

## 分层

测试按占用的资源分三层：

| 层 | 本项目里指什么 | 单个上限 | 个数上限 |
|---|---|---|---|
| 小 | 直接调 kited 的模块，git 在临时目录里跑；不起 Claude Code | 1 秒 | 不设 |
| 中 | 起 Claude Code 进程，模型换成 kited/test/fake-api.ts 的假端点，不耗额度 | 2 秒 | 8 个 |
| 大 | 用真实订阅跑 kited | 手动跑 | 清单在 kited/README.md |

全量（小加中）不超过 15 秒。小测试单个上限比模板默认的 0.5 秒松：Kite 的小测试一个要调几十次 git，每次约 10 毫秒，正常在 0.1 到 0.6 秒之间，上限贴着它会让检查时过时不过；超过 1 秒一定是误起了进程或在睡眠等待。中测试个数和全量比模板默认的 10 个、30 秒紧：中测试都在本进程里启动 kited，改任何一处源码都会选中它们，开发中每次都要跑，所以要少。只测 Runner 的中测试只 import runner.ts，上游行为的测试直接测 SDK，这两类平时不会被选中。能用小测试测的不用中测试；超出预算时先删测试或降一层。只有 Claude Code 进程本身的行为（收口、续接、打断、插话、被杀）才需要中测试；登记、工作树、快照、回退、采纳的 git 语义都用小测试测。

## 准入

每个测试都要说清挡住了什么，只收三种：
- 一条需求；
- 一个真实出过的 bug，测试上方注释写是什么 bug；
- 项目依赖的一条上游行为，测试上方注释写是哪一条。

不收：复述实现的；各个因素已经单独测过的组合；和已有测试重复的；类型检查已经保证的。先看已有测试，能改一个已有测试覆盖的，就不新增。

## 写法

- 测试名写成一句行为，读名字就知道挡住什么。
- 测试要 import 它测的代码，模板、配置这类非代码的输入也要 import。`.kite/check` 沿 import 关系找受影响的测试，只按路径起子进程，依赖就找不到。
- 不用睡眠等时间，等事件或状态。要让 agent 保持「正在工作」，让假端点挂起这次请求，测完再放行。
- 每个测试自己建临时目录，结束时删掉。

## 交付

跑 `.kite/check`。报告写了哪些测试、各挡住什么、各属于哪一层；失败的测试里，哪些你认为是实现的问题，给出对应的需求、复现步骤、实际结果和期望结果。不要为了通过去改期望。
